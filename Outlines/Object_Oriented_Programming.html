  • OOP01

    Objects, classes and responsibilities

    [Exam Focus]
    • Object versus class
      • Identity, state, behavior
      • Fields store state
      • Methods provide behavior
      • Rectangle: width, height
      • getArea(), getPerimeter()
      • Equal fields, distinct identities
      • Class: common structure and behavior
      • Object: particular instance
      👁 Full explanation
      An object has identity, state and behavior. State is stored in fields; behavior is provided by methods. A Rectangle object may hold width and height and answer getArea() or getPerimeter(). Two objects can have equal fields and still be distinct objects. A class defines their common structure and behavior; an object is a particular instance.
    • Responsibility-driven classes
      • Account controls balance
      • Transaction records payment
      • Service coordinates objects
      • Messages: method calls, obj.add()
      • Delegation to other objects
      • Objects manage own state
      • Procedural and OO reuse
      • Procedural global shared data optional
      👁 Full explanation
      Choose classes around responsibilities: an account controls its own balance, a transaction records a payment, and a service coordinates them. Objects send messages through method calls such as obj.add(). They can delegate work to other objects; saying that objects cannot manage their own state is misleading. Procedural and object oriented designs both support reuse; global shared data is not compulsory in procedural programming.

  • OOP02

    Encapsulation, hiding and abstraction

    [Exam Focus]
    • Encapsulation, hiding and abstraction
      • Encapsulation: state/operations grouped, access controlled
      • Information hiding: implementation behind stable interface
      • Abstraction: essential operations, irrelevant details omitted
      • private balance plus deposit(amount)
      • Overlapping principles, question emphasis matters
      👁 Full explanation
      Encapsulation groups related state and operations and controls access. Information hiding keeps implementation decisions behind a stable interface. Abstraction presents the essential operations while omitting details irrelevant to the caller. These ideas overlap: a private balance plus deposit(amount) can demonstrate all three, depending on what the question emphasizes.
    • Inheritance and polymorphism
      • Inheritance: subtype relationship, possible implementation reuse
      • Common type, concrete-specific behavior
      • Fields/methods wrapping: encapsulation
      • What versus how: abstraction
      • Precise mechanism over vague slogan
      👁 Full explanation
      Inheritance forms a subtype relationship and may reuse implementation. Polymorphism lets code using a common type invoke behavior appropriate to different concrete objects. Prefer a precise mechanism over a vague slogan: wrapping fields and methods points to encapsulation; showing what an operation does while hiding how points to abstraction.

  • OOP03

    References, instances and value passing

    [Exam Focus]
    • Reference declaration versus object creation
      • Student s;: reference only
      • new Student(): allocate and initialize
      • s.name, s.study(): visibility-dependent access
      • t=s: reference copy
      • Shared object aliasing
      • Mutation through t visible through s
      👁 Full explanation
      Student s; declares a reference variable; it creates no Student object. Student s=new Student(); allocates and initializes an instance. Member access uses s.name or s.study(), subject to visibility. Assignment t=s copies a reference, so both can refer to the same object; changing that object through t is observable through s.
    • Java value passing and reachability
      • All arguments passed by value
      • Copied reference permits shared-object mutation
      • Parameter reassignment leaves caller reference unchanged
      • Unreachable objects reclaimable
      • Collection timing unspecified
      • Reachable cycles may retain objects
      • Unreachable cycles collectible
      👁 Full explanation
      Java passes all arguments by value. Passing a reference copies it: a method may modify the shared object, but assigning its parameter to a new object does not reassign the caller’s reference. The runtime may reclaim unreachable objects; collection timing is unspecified. Reachable object cycles can matter for retention, but an unreachable cycle can be collected.

  • OOP05

    Variables, defaults and initialization

    • Local, instance and static variables
      • Locals: methods, constructors, blocks
      • Definite assignment before use
      • Locals: no public/private/protected
      • Fields: class, outside method bodies
      • Instance fields: per object
      • Static fields: per class
      • Location alone doesn't distinguish field kinds
      👁 Full explanation
      The introductory three-way grouping is local, instance and class/static variables. Locals occur in methods, constructors or blocks; they must be definitely assigned before use and cannot have public/private/protected modifiers. Fields occur in a class outside method bodies; non-static fields belong to each instance, while static fields belong to the class. Declaration location alone does not distinguish instance and static fields.
    • Java defaults and initialization
      • Fields and array elements defaulted
      • Numeric zero, char '\u0000'
      • boolean false, references null
      • Unassigned local int t: compilation error
      • int a=10,b=10: initial values
      • final local permitted
      • final isn't access modifier
      👁 Full explanation
      Java fields and array elements receive defaults: numeric zero, char '\u0000', boolean false and references null. A local int t; followed by printing t is a compilation error. Initializers such as int a=10,b=10; assign initial values. A final local is permitted; final is not an access modifier.

  • OOP06

    Primitive types and conversions

    • Java primitive and reference types
      • byte, short, int, long
      • Signed widths: 8,16,32,64 bits
      • byte: -128..127
      • short: -32768..32767
      • float, double, char, boolean
      • char: unsigned 16-bit UTF-16 unit
      • Digit, letter, symbol, not whole String
      • enum and String: reference types
      👁 Full explanation
      Java has byte, short, int, long, float, double, char and boolean. Signed integer widths are 8,16,32,64 bits respectively. byte ranges from -128 to 127; short from -32768 to 32767. char is an unsigned 16-bit UTF-16 code unit and can hold a digit, letter or symbol, not a whole String. enum and String are reference types.
    • Conversions and arithmetic promotion
      • Compatible widening often implicit
      • Narrowing usually explicit, possibly lossy
      • int→float widening may lose precision
      • Widening-losslessness claim false
      • char/byte/short often promoted to int
      • boolean ↔ numeric conversion forbidden
      • if(0), numeric-zero loop condition: invalid
      👁 Full explanation
      A compatible widening conversion often needs no cast; narrowing usually needs an explicit cast and may lose information. Widening an int to float can lose precision, so “widening never loses information” is false. Arithmetic promotes char, byte and short to int in many expressions. boolean does not convert to or from numeric truth values; if(0) and for(...;0;...) are invalid.

  • OOP07

    Static members and final

    • Static class members
      • One field per loaded class
      • Shared across instances
      • Three constructor increments: count=3
      • Prefer ClassName.count, ClassName.utility()
      • Static method: no current instance
      • Explicit object permits instance-member access
      👁 Full explanation
      static gives one field per loaded class, shared by its instances. If count starts at zero and every constructor increments it, three creations leave count=3. Prefer ClassName.count and ClassName.utility(). A static method has no current instance, but can still use instance members through an explicit object reference.
    • Static initialization and final
      • Class initialization before relevant active use
      • Not merely file loading
      • final variable: no reassignment
      • final method: no overriding
      • final class: no extension
      • final reference may target mutable object
      • PI: static final candidate
      • Student name: normally instance state
      • Parameter-only calculation: possible static method
      👁 Full explanation
      A static initializer runs during class initialization, before the class’s first relevant active use, not simply whenever a file is loaded. final prevents reassignment of a variable, overriding of a method or extension of a class. A final reference may still refer to a mutable object. A shared mathematical PI is a good static final candidate; a student name normally belongs to an instance. A calculation using only parameters may be static.

  • OOP08

    Access control and packages

    • Java access boundaries
      • private: declaring class/nest
      • No modifier: package access
      • protected: package plus qualified subclass access
      • public: widest ordinary access
      • Declaring type must be accessible
      • Top-level class/interface: public or package-private
      • Top-level private/protected forbidden
      • Member types: additional visibility possibilities
      👁 Full explanation
      For ordinary members: private restricts access to the declaring class/nest; no modifier grants package access; protected grants same-package access plus qualified subclass access; public is widest, provided the declaring type itself is accessible. Top-level classes/interfaces may be public or package-private, not protected/private. Member types have additional visibility possibilities.
    • Protected access across packages
      • Own inherited context allowed
      • Appropriate subclass-typed receiver allowed
      • Arbitrary superclass receiver disallowed
      • Same-package unrelated classes also allowed
      • protected ≠ subclasses only
      • Own main accesses own instance's private fields
      👁 Full explanation
      Across packages, a subclass accessing a protected instance member must do so through its own inherited context or an appropriate subclass-typed receiver, not any arbitrary superclass object. protected therefore does not mean “subclasses only”: unrelated classes in the same package also have access. A class’s own main method can access private fields of an instance of that class.

  • OOP09

    Constructors and generated defaults

    [Exam Focus]
    • Constructor identity and purpose
      • Exact class name
      • No return type, including void
      • Initialize new object
      • Overloaded/private constructors permitted
      • Private: factory or controlled singleton
      • Internal object creation still possible
      👁 Full explanation
      A constructor has the class’s exact name and no return type, not even void. It initializes the new object and can be overloaded or private. A private constructor can support a factory or controlled singleton creation; it does not mean the class can never create an object internally.
    • Default-constructor conditions
      • No declared constructor → compiler default
      • Circle(double r) suppresses generated no-arg
      • new Circle(): explicit no-arg then required
      • Constructors neither inherited nor overridden
      • return; allowed, return expression forbidden
      • Field defaults precede ordinary constructor initialization
      • Defaults independent of generated constructor
      👁 Full explanation
      If a class declares no constructor, Java supplies a default constructor. If Circle(double r) is declared, new Circle() fails unless a no-argument constructor is also declared. Constructors are not inherited or overridden. They may contain return; but cannot return an expression. Fields get their default values before ordinary constructor initialization, rather than receiving defaults only because a default constructor was generated.

  • OOP10

    Constructor chains and initialization order

    [Exam Focus]
    • Java17 constructor delegation
      • this(args)/super(args): first statement
      • this: same-class constructor
      • super: immediate parent constructor
      • Cannot explicitly invoke both
      • Absent explicit delegation: implicit super()
      • Accessible matching no-arg parent required
      👁 Full explanation
      Under the Java 17 rules used for the bank’s ordinary examples, an explicit this(args) or super(args) invocation must be the first constructor statement. this invokes another constructor in the same class; super invokes the immediate superclass constructor. A constructor cannot explicitly invoke both. If there is no explicit delegation, an implicit super() is inserted; a matching accessible no-argument parent constructor must exist.
    • Construction order and version conditions
      • Parent construction first
      • Subclass field initializers/instance blocks in order
      • Relevant subclass constructor body last
      • FinalExam parent: num1=4
      • Subclass initializer: num=3
      • this(5): num=25
      • No-arg body: num1=num=25
      • Java25: restricted pre-invocation statements
      • First-statement rule requires version qualification
      👁 Full explanation
      Trace parent construction first, then subclass field initializers and instance blocks in order, then the relevant subclass constructor body. In the repaired FinalExam example, the parent sets num1=4, the subclass initializes num=3, this(5) sets num=25, and the no-arg body sets num1=num, leaving 25. Java 25 permits restricted statements before explicit constructor invocation; the older first-statement rule must be version qualified.

  • OOP11

    Methods, accessors and mutators

    [Exam Focus]
    • Method structure and invocation
      • Modifiers, return type, name
      • Parameter list and body
      • public int getAge(){return age;}
      • void: no returned value
      • Parameters: declared inputs
      • Arguments: call-supplied values
      • object.method(): instance call
      • Implicit this in suitable instance context
      👁 Full explanation
      A method has modifiers, return type, name, parameter list and body: public int getAge(){return age;}. A void method returns no value. Parameters name the inputs in the declaration; arguments supply values at a call. An instance method can be invoked as object.method(), or with an implicit this inside suitable instance context.

      • Setter: change state

      • Validate state changes

      • Use permitted parent operation
      👁 Full explanation
      An accessor/getter returns information; a mutator/setter changes state. Encapsulation does not require blindly generating setters for every field: validate changes and expose only useful operations. For a bank account, deposit must reject negative amounts. A private field cannot normally be accessed directly by a separately declared subclass, even with this.field; use a permitted parent operation.

  • OOP12

    Overloads and compile-time selection

    [Exam Focus]
    • Method overload distinctions
      • Same name, different types/count/type order
      • Return type alone insufficient
      • Java and C++ rule
      • Inherited methods can form overloads
      • Same-class-only claim simplified
      • f(int), f(double), f(int,int)
      • Parameter-name change: no overload
      👁 Full explanation
      Overloaded methods share a name but have different parameter types, counts or type order. Return type alone is insufficient in Java and C++. Overloads can also arise through inherited methods; “same class only” is a teaching simplification. f(int), f(double) and f(int,int) are distinct, but changing a parameter name does not create an overload.
    • Compile-time overload selection
      • Declared argument types and conversions
      • Exact int preferred over double widening
      • Return type outside ordinary Java signature
      • Different signature versus inherited-signature override
      👁 Full explanation
      The compiler selects the applicable signature from the declared argument types and conversions. int arguments usually choose an exact int overload rather than a wider double overload. A return type is not part of an ordinary Java method signature. Distinguish a different signature from overriding an inherited signature.

  • OOP13

    Inheritance and composition

    [Exam Focus]
    • Class inheritance forms
      • Dog extends Animal
      • Subclass/derived/child, superclass/base/parent
      • One direct superclass
      • Multiple implemented interfaces
      • Single: one parent
      • Multilevel: inheritance chain
      • Hierarchical: siblings share parent
      • extends Animal,Mammal: invalid Java
      👁 Full explanation
      class Dog extends Animal declares a subclass/derived/child of a superclass/base/parent. A class extends one direct class and can implement multiple interfaces. Single, multilevel and hierarchical inheritance mean one parent, a chain, and several children of one parent. Java does not permit class Dog extends Animal,Mammal.
    • Contract-based inheritance versus composition
      • Subtype satisfies parent contract
      • Dog is an Animal
      • Pet: common name and speak contract
      • Dog: specialized fetch
      • Dog/Cat: appropriate speak implementations
      • Composition: has-a
      • Car contains Engine
      • Reuse alone doesn't justify is-a
      👁 Full explanation
      Use inheritance when a subtype can satisfy the parent’s contract: Dog is an Animal. For shared Pet.name and speak(), put common state/contract in Pet, specialized fetch() in Dog, and appropriate speak() implementations in Dog and Cat. Composition represents has-a, such as Car containing Engine. Reuse alone does not justify an invalid is-a relationship.

  • OOP14

    Overriding rules

    [Exam Focus]
    • Override eligibility and restrictions
      • Inherited instance method, same signature
      • Compatible return type
      • Covariant reference return subtype
      • Visibility cannot narrow
      • Checked exceptions cannot broaden incompatibly
      • @Override: compiler-checking annotation
      • No Java override keyword
      • Constructors/final/static/private methods: no overriding
      👁 Full explanation
      A subclass overrides an eligible inherited instance method with the same signature and a compatible return type; a covariant reference return may be a subtype. Visibility cannot become more restrictive, and checked exceptions cannot be broadened incompatibly. @Override requests compiler checking; Java has no override keyword. Constructors, final methods, static methods and private parent methods are not overridden.
    • Independent declaration versus override
      • Private-parent same signature: independent child declaration
      • No runtime overriding
      • No ordinary static-method hiding
      • Concrete subclass implements inherited abstract method
      • Unrelated same-name methods: no overriding
      👁 Full explanation
      A same-signature child method matching a private parent method is an independent declaration, not runtime overriding and not ordinary static-method hiding. An abstract inherited method is implemented by an overriding method in a concrete subclass. Merely reusing a name in two unrelated classes does not establish overriding.

  • OOP15

    Declared types and dynamic dispatch

    [Exam Focus]
    • Declared type versus runtime class
      • Animal a=new Dog()
      • Animal: declared, Dog: actual
      • Declared type controls compilable operations
      • Dog-only fetch: a.fetch() fails
      • Eligible sound override: Dog.sound() runtime
      👁 Full explanation
      For Animal a=new Dog(), Animal is the declared type and Dog the actual type. The declared type determines which member operations compile. If fetch() exists only in Dog, a.fetch() fails compilation. For an eligible overridden sound(), a.sound() invokes Dog.sound() at runtime.
    • Dispatch-solving sequence
      • Declaration and visibility first
      • Compile-time signature second
      • Runtime class and most-specific override third
      • Animal[]{Dog,Cat}: common speak loop
      • New subclasses supply behavior
      • Generic loop unchanged: extensibility
      👁 Full explanation
      To solve dispatch questions: check the declaration and visibility, determine the compile-time signature, then identify the object’s runtime class and its most specific override. An array Animal[]{new Dog(),new Cat()} can call speak() on each using one loop. New subclasses can supply behavior without rewriting this generic loop, which is the practical meaning of extensibility.

      • this: current object

  • OOP17

    C++ this and object rules

    • C++17 this pointer
      • Ordinary non-static member function
      • Pointer to called object
      • this->field: member selection
      • Implicit object argument explanation
      • Member variables don't receive argument
      • Static member function: no this
      👁 Full explanation
      In ordinary C++17 non-static member functions, this is a pointer to the object on which the function is called; this->field selects a member. Never transfer Java dispatch or memory-management assumptions to a C++ question without checking the code.

  • OOP18

    Abstract classes and implementations

    [Exam Focus]
    • Abstract class capabilities
      • No direct instantiation
      • Fields, constructors, concrete methods allowed
      • Abstract methods allowed, not required
      • Abstract method: no body
      • abstract plus final: conflicting requirements
      • Required versus forbidden overriding
      👁 Full explanation
      An abstract class cannot be directly instantiated but can define fields, constructors, abstract methods and concrete methods. It need not contain an abstract method. An abstract method has no body; abstract and final conflict because an operation cannot require overriding while forbidding it.

If parent declares abstract String welcome(), a String welcome() implementation is required; int welcome() is incompatible, and welcome(int) merely adds an overload. A valid class can contain both the required implementation and an unrelated overload.

  • OOP19

    Interfaces and modern Java

    [Exam Focus]
    • Interface contract and implementation
      • Payable: double getPaymentAmount()
      • Implicit public abstract operation
      • Invoice implements Payable
      • Required public double getPaymentAmount()
      • getQuantity()*getPricePerItem()
      • Class: superclass plus zero/multiple interfaces
      • Interface extends multiple interfaces
      • No instance fields or constructors
      • Fields: public static final
      👁 Full explanation
      interface Payable{double getPaymentAmount();} declares an abstract public operation. class Invoice implements Payable must provide public double getPaymentAmount(), perhaps returning getQuantity()*getPricePerItem(). A class can extend a superclass and implement zero or more interfaces. An interface can extend several interfaces. No interface instance fields or constructors exist; fields are implicitly public static final.
    • Modern interface method rules
      • No private/default/static: public abstract
      • default/static methods may have bodies
      • Java9+: private helpers
      • All-interface-methods-bodyless claim outdated
      • All inherited abstract contracts satisfied
      • Suitable public implementation may be inherited
      • No direct interface instantiation
      • References hold implementing objects
      • Anonymous implementations
      • Suitable functional-interface lambdas
      👁 Full explanation

    Language classifications and portability

    • Language taxonomy and portability
      • C++, Java, Python, Perl: third generation
      • Taxonomy separate from object orientation
      • Taxonomy separate from compilation/interpretation
      • Java source → JVM bytecode
      • Compatible JVM plus libraries: cross-system portability
      👁 Full explanation
      Under the conventional introductory generation taxonomy, general-purpose high-level languages such as C++, Java, Python and Perl are third generation. The taxonomy is separate from object orientation and from compilation versus interpretation. Java source normally compiles to JVM bytecode, and a compatible JVM plus libraries supports portability across systems.
    • Portability qualifications and language properties
      • Compatible APIs, versions, environment assumptions
      • No unconditional any-device guarantee
      • Java objects/classes plus primitives
      • Learning difficulty: subjective judgment
      • Syntax conventions versus bytecode portability
      • Runtime implementation distinguished
      👁 Full explanation
      Portability still depends on compatible APIs, versions and environment assumptions; it is not an unconditional guarantee for any program on any device. Java supports objects and classes but also primitive values. “Difficult to learn” is a subjective judgment rather than a technical language property. Syntax conventions, bytecode portability and runtime implementation must be distinguished.
