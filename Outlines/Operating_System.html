    Objectives and resource management

    [Exam Focus]
    • OS objectives and services
      • CPU, memory, storage allocation
      • Device and communication resources
      • Convenience: interfaces, files, device abstractions
      • Efficiency: effective resource use
      • Efficiency ≠ every process’s fastest response

      👁 Full explanation
      An OS allocates CPU time, memory, storage, devices and communication resources, and provides services to programs.       • Updates/monitoring: administrative help
      • Automatic updates: not universally defining
      👁 Full explanation
      Ability to evolve means adding hardware support, features and repairs through maintainable interfaces/modules. Backward compatibility preserves supported older application behavior; it is not a promise that every old binary works. Scalability means handling greater workload/resources; portability means adapting to other platforms. Fault tolerance continues correct service despite specified failures; recovery restores service afterward. Updates and monitoring help administration, but automatic updates are not a defining property of every OS.

  • OS02

    Batch, sharing and real time

    [Exam Focus]
    • Execution organization
      • Batch: little post-submission interaction
      • Multiprogramming: CPU work during another job’s wait
      • Several available jobs
      • Multiprogramming ≠ fixed time slices
      • Time-sharing: rapid scheduling/preemption, interaction
      • Single CPU: interleaved execution
      • Multiple CPUs: true parallelism
      • Shared memory ≠ mandatory private memories
      👁 Full explanation
      Batch jobs run with little interaction after submission. Multiprogramming keeps several jobs available so another can use the CPU while one waits; it does not require fixed time slices. Time-sharing uses rapid scheduling/preemption to support interactive users. A single CPU interleaves execution; multiple CPUs can execute work truly in parallel. Shared-memory multiprocessors do not require each CPU to have private main memory.
    • System categories and timing
      • Single/multiuser: concurrent users, not applications
      • Network systems: remote services
      • Distributed systems: coordinated machines
      • Location hiding possible
      • Real-time correctness: timing included
      • Hard deadlines: mandatory
      • Soft misses: degraded service
      • Real time ≠ simply fast
      • Spooling/multitasking: mechanisms, not generation proofs
      👁 Full explanation
      Single-user and multiuser describe concurrent user access, not the number of applications. Network systems expose remote services; distributed systems coordinate work across machines, sometimes hiding location. Real-time correctness includes timing: hard deadlines must be met, while soft deadline misses degrade service. “Real time” does not simply mean fast. Spooling and multitasking are mechanisms, not proof of a particular OS generation.

  • OS03

    Kernel, shell, privilege and boot

    [Exam Focus]
    • OS components and privilege
      • Kernel: resources, protection, system calls
      • Shell: command interpretation
      • GUI: another interface
      • Browsers, office tools, editors: applications
      • Drivers: commonly kernel, sometimes user-space
      • Kernel mode: privileged operations
      • Supervisor/kernel mode: often synonyms
      • Exclusive mode options: ambiguity
      👁 Full explanation
      The kernel implements core resource management, protection and system-call handling. A shell reads/interprets user commands; a GUI is another interface. Browsers, office tools and editors are applications. Device drivers are commonly kernel components, although user-space drivers also exist. Kernel mode has privileged operations; supervisor mode often means the same privileged mode, so offering both as exclusive answers is ambiguous.
    • Boot sequence and resident components
      • Firmware/bootloader before kernel
      • Kernel loaded into RAM
      • First core OS component
      • Kernel ≠ first power-on program
      • Loadable modules: running-kernel driver additions
      • Modular systems allow runtime loading
      • Resident kernel: session-long activity
      • Antivirus/disk tools: utilities
      • User processes plus privileged components
      👁 Full explanation
      Firmware/bootloader stages execute before transferring control to a kernel loaded into RAM. The kernel is the first core OS component, not the first program ever executed at power-on. Loadable modules can add drivers to a running kernel; “kernel modules cannot be loaded while running” is false in modular systems. A resident kernel remains active through the session. Utilities such as antivirus and disk tools can combine user processes with privileged components.

    APIs, system calls and virtualization

    [Exam Focus]
    • System call versus library API
      • System call: protected kernel-service request
      • Process creation, file read, socket opening
      • API/library wrappers
      • Library function ≠ mandatory kernel entry
      • Application API versus user/kernel boundary
      • OS-service interface: scope required
      👁 Full explanation
      A system call requests a protected kernel service, such as creating a process, reading a file or opening a socket. A user-facing API/library may wrap that request; not every library function enters the kernel. Therefore a stem asking merely for the interface to OS services must distinguish the application API from the direct user/kernel boundary.
    • Services and virtual machines
      • Process control
      • File/device management
      • Information retrieval and communication
      • Video editing: application operation
      • write_database(): application-specific, not generic syscall
      • Virtualization: virtual machine environment
      • Hypervisor: guests on one host

      • Kernel/shell/API/VM: distinct labels
      👁 Full explanation
      Process control, file/device management, information retrieval and communication are service categories. Video editing and a database-specific write_database() are application operations, not standard generic syscall categories/names. Virtualization presents a virtual machine environment, often allowing guest operating systems on one host through a hypervisor. It differs from virtual memory, which translates a process’s addresses. Kernel, shell, API and VM are not interchangeable labels.

  • OS05

    Processes, programs and context

    • Program versus process
      • Program: stored instructions
      • Process: executing instance
      • Address space and resources
      • Process ≠ universal application manager/UI
      • PCB: identity and state
      • Saved PC/registers: resume execution
      • Scheduling information
      • Memory/accounting details
      • I/O and open-resource state
      👁 Full explanation
      A program is stored instructions; a process is an executing instance with address space and resources. A process does not universally “manage applications” or “provide a user interface.” The PCB records identity, state, PC/registers, scheduling information, memory/accounting details and I/O/open-resource state. A saved PC identifies where execution resumes.
    • Context switch and task terminology
      • Save one context, restore another
      • Application-work interruption: overhead
      • Interrupt/syscall: privilege-only switch possible
      • Privilege switch ≠ process switch
      • Task: OS-specific meaning
      • Process/thread/schedulable entity
      • Process-versus-task: no universal distinction
      👁 Full explanation
      A context switch saves one execution context and restores another; useful application work is interrupted by this overhead. An interrupt or system call can switch privilege without switching process. Task is OS-specific terminology: it may mean process, thread or schedulable entity. No universal process-versus-task distinction follows from the word alone.

  • OS06

    Process states, queues and schedulers

    • Process-state transitions
      • New: created/admitted
      • Ready: eligible, not running
      • Running: CPU in use
      • Waiting/blocked: event required
      • Terminated: execution ended
      • Running→ready: quantum expiry/preemption
      • Running→waiting: blocking I/O
      • I/O completion: waiting→ready
      • Completion ≠ immediate running guarantee
      👁 Full explanation
      New processes are created/admitted; ready means eligible for CPU but not currently running. Running uses a CPU. Waiting/blocked means unable to proceed until an event; terminated means execution has ended. Running→ready follows time-slice expiry or another preemption. Running→waiting follows blocking I/O. I/O completion normally gives waiting→ready, not a guaranteed immediate running state.
    • Queues and scheduling roles
      • Ready queue: eligible work
      • Device queues: blocked requests
      • Job queue: system processes
      • Admission queue: awaiting memory/admission
      • Long-term: job admission
      • Medium-term: suspension/swapping
      • Short-term: ready-work selection
      • Dispatcher: handoff/context restore
      • Priority preemption: policy-dependent running→ready
      👁 Full explanation
      The ready queue contains eligible work; device queues hold blocked requests. The broad textbook job queue contains processes in the system, while an admission queue more narrowly holds jobs awaiting memory/admission. Long-term scheduling admits jobs; medium-term scheduling suspends/swaps them; short-term scheduling selects ready work. The dispatcher performs the handoff/context restore after selection. A bare “priority” causes running→ready only if a preemptive policy chooses another process.

  • OS07

    Creation, fork/exec and termination

    • Process creation mechanisms
      • Initialization, user requests, service requests
      • Running process’s creation call
      • POSIX fork(): child creation
      • Child return: 0
      • Parent return: child PID
      • Success assumption
      • Distinct address spaces
      • Explicit resource sharing possible
      • exec: current image replacement
      • exec ≠ new process creation
      👁 Full explanation
      Processes arise during initialization, user requests, service requests or a running process’s creation call. In POSIX-style systems fork() creates a child: zero is returned in the child and the child PID in the parent on success. The two have distinct address spaces, although resources may be shared through explicit mechanisms. exec replaces the current process image; it does not itself create another process.
    • Termination categories
      • Voluntary: normal completion/program-detected error
      • Involuntary: unrecoverable fault/killing
      • exit(): normal runtime termination
      • abort(): abnormal termination request
      • Nonexistent/protected memory: fatal fault
      • Bad-input exit: application decision
      • Terminate exit: imprecise category
      • Parent exit ≠ universal descendant killing
      👁 Full explanation
      Normal completion and a program-detected error exit are voluntary; an unrecoverable fault or being killed is involuntary. exit() terminates normally through the runtime; abort() requests abnormal termination. A reference to nonexistent/protected memory is a fatal fault, unlike an application deciding to exit after bad input. “Terminate exit” is not a precise standard category. Parent termination does not universally kill all descendants.

  • OS08

    Threads and mapping models

    • Thread ownership and sharing
      • Own PC, registers, stack
      • Shared code and address space
      • Usually shared open files
      • Process: potentially many threads
      • Thread: one process at a time
      • Threads ≠ group of processes
      • Thread execution need not be sequential
      • Independent versus cooperating processes
      • Cooperation: communication/shared data
      👁 Full explanation
      A thread has its own PC, registers and stack. Threads in a process share code, address space and usually open-file resources. A process can contain many threads; a thread belongs to one process at a time. Threads are not a group of processes and need not execute sequentially. Independent processes can exist; cooperating ones communicate/share data.
    • Thread management and mappings
      • User-level: library management
      • Kernel threads: OS-known
      • Many-to-one: blocking call blocks all
      • One context: no simultaneous multi-CPU use
      • One-to-one: another thread runs when blocked
      • Many-to-many: users multiplexed over kernel threads
      • Speed/reliability: implementation-dependent
      • Management layer ≠ guarantees
      • Browser/Excel names ≠ threading-model proof
      👁 Full explanation
      User-level threads are managed by a library; kernel threads are known to the OS. In many-to-one mapping, a blocking kernel call can block all user threads and one kernel execution context cannot use multiple CPUs simultaneously. One-to-one permits another kernel thread to run when one blocks. Many-to-many multiplexes user threads over several kernel threads. Speed and reliability depend on implementation; the management layer alone guarantees neither. Application names such as browser or Excel do not prove a particular version’s threading model.

  • OS09

    IPC and blocking semantics

    • IPC mechanisms
      • Shared memory: common region
      • Conflicting updates require synchronization
      • Message passing: send/receive
      • Pipes: streams
      • Message queues: message boundaries
      • Sockets: endpoints
      • RPC: remote operation
      • HTTP: application communication protocol
      • HTTP can carry IPC
      👁 Full explanation
      Shared memory lets processes access a common region and requires synchronization for conflicting updates. Message passing exchanges data through send/receive operations. Pipes provide streams; message queues preserve messages; sockets connect endpoints; RPC requests a remote operation. HTTP is an application protocol over a communication mechanism and can carry interprocess communication, so it is not universally “not IPC.”
    • Blocking and nonblocking contracts
      • Blocking send: API-defined wait condition
      • Handoff, buffering or receipt
      • Blocking receive: wait for message
      • Nonblocking: prompt data/progress/would-block
      • Rendezvous: sender waits until receipt
      • File locks: access coordination
      • Locks ≠ arbitrary payload transfer
      • Locking: IPC synchronization
      • Asynchronous messaging ≠ synchronization-free
      👁 Full explanation
      Blocking send waits for the required handoff/buffering/receipt condition defined by its API. Blocking receive waits for a message. Nonblocking operations return promptly with data, progress or a would-block result. “Sender blocked until received” identifies blocking send under rendezvous semantics. File locks coordinate access rather than transfer arbitrary payloads, though locking is synchronization within IPC. Do not equate asynchronous messaging with no synchronization ever.

  • OS10

    Races and critical-section correctness

    • Race and critical-section criteria
      • Race: conflicting uncoordinated interleavings
      • Critical section: protected shared-state code
      • Critical section ≠ resource itself
      • Mutual exclusion: safety property
      • Progress
      • Bounded waiting
      • Stated correctness assumptions
      • Failures: races, starvation, deadlock
      👁 Full explanation
      A race occurs when results depend on uncoordinated interleaving of conflicting accesses. A critical section is code accessing shared state that needs protection, not the resource itself. A correct exclusion solution requires mutual exclusion, progress and bounded waiting under stated assumptions. Mutual exclusion is a desired safety property; races, starvation and deadlock are possible failures.
    • Synchronization structure
      • Small critical regions
      • Same protection for every conflicting access
      • Barrier: defined participants reach point
      • Monitor: encapsulated protected operations
      • Condition synchronization
      • Inconsistent lock order: deadlock risk
      👁 Full explanation
      Keep critical regions small and ensure every conflicting access uses the same protection. A barrier waits until a defined set of participants reaches a point; a monitor encapsulates protected operations with condition synchronization. Locking can itself introduce deadlock if acquisition order is inconsistent.
    • Worked example Lost-update example
      • Two reads: counter=0
      • Each computes/stores 1
      • Two increments → 1, not 2
      • Entire read-modify-write under one lock
      👁 Full explanationWorked microexample
      Two threads read counter=0, each computes 1 and each stores 1. Two increments produce 1 instead of 2. Protecting the entire read-modify-write with one lock prevents that lost update.

  • OS11

    Semaphores and resource counts

    • Semaphore operations and models
      • Atomic wait/P/down
      • Atomic signal/V/up
      • Nonnegative wait: consume token or block
      • Signal: token supply, possible wakeup
      • Negative counts: alternative waiter encoding
      • State the count model
      • Binary semaphore: one permit
      • Counting semaphore: several permits
      • Mutex: ownership rules
      • General semaphore: no equivalent ownership requirement
      👁 Full explanation
      A semaphore provides atomic wait/P/down and signal/V/up operations. Under the nonnegative-token model, wait consumes one available token or blocks when none is available; signal supplies a token and may wake a waiter. Implementations using negative internal counts encode waiters differently, so state the model. A binary semaphore represents one permit; a counting semaphore tracks several. A mutex normally has ownership rules that a general semaphore lacks.
    • Worked example Semaphore and bounded-buffer example
      • Mutex initial value: 1
      • wait(m); critical work; signal(m)
      • N slots: empty=N, full=0, mutex=1
      • Producer: wait empty, then mutex
      • Insert; unlock; signal full
      • Holding mutex while waiting empty
      • Consumer unable to free slot
      👁 Full explanationWorked microexample
      Initialize a mutex semaphore to 1. Each thread does wait(m); critical work; signal(m). For a buffer of N slots use empty=N, full=0 and mutex=1: producer waits empty then mutex, inserts, unlocks then signals full. Waiting for empty while already holding mutex can prevent the consumer from freeing a slot.

  • OS12

    Turn variables and atomic primitives

    • Strict alternation and lock-variable races
      • turn=0/1
      • Process i: wait while turn≠i
      • Enter, then hand turn over
      • Alternation enforces turns
      • Outside peer: progress violation
      • Separate test/set: race
      • Both may observe free
      👁 Full explanation
      Strict alternation uses turn=0/1: process i waits while turn≠i, then enters and sets turn to the other process on leaving. It enforces turns but can violate progress if the other process stays outside its critical region. A naive lock-variable test followed by a separate set races because both processes can observe free before either sets it.
    • Atomic synchronization primitives
      • Test-and-set; compare-and-swap
      • Atomic check/update
      • Ordinary check-then-write: non-atomic
      • Peterson: flags plus turn
      • Two processes; memory-model assumptions
      • Semaphore: more than two possible
      • Local interrupt disabling excludes no other CPUs
      • Not general user-space locking
      • Interrupts: event notification/synchronization
      • Interrupt synchronization exclusions: overbroad
      👁 Full explanation
      Test-and-set and compare-and-swap combine checking/updating atomically; ordinary check-then-write does not. Peterson’s classic algorithm uses flags plus turn for two processes under its memory-model assumptions; a semaphore can coordinate more than two. Disabling local interrupts does not exclude other CPUs and is not a general user-space locking solution. Interrupts can notify/synchronize events, so they cannot be universally excluded from every synchronization-related classification.

  • OS13

    Scheduling metrics and calculations

    [Exam Focus]
    • Scheduling equations and goals
      • A: arrival; S: start; C: completion
      • Response=S−A
      • Turnaround=C−A
      • Single burst B, no I/O
      • Waiting=C−A−B
      • I/O: subtract CPU and blocked time
      • Ready-queue waiting only
      • Throughput=completed_jobs/elapsed_time
      • CPU_utilization=busy_time/elapsed_time
      • Goal-dependent response/turnaround/wait minimization
      • Useful throughput/utilization maximization
      👁 Full explanation
      For arrival A, first start S and completion C, response=S−A and turnaround=C−A. For a single CPU burst B with no I/O, waiting=C−A−B. With I/O, subtract all CPU and blocked time to isolate ready-queue waiting. Throughput=completed jobs/elapsed time; CPU utilization=busy time/elapsed time. Minimize response/turnaround/waiting under the selected goal and maximize useful throughput/utilization.
    • Timeline-first calculation method
      • Arrivals and idle gaps
      • Preemptions and overhead
      • Per-process values before averages
      • First response ≠ final completion
      👁 Full explanation
      First construct a time line with arrivals, idle gaps, preemptions and overhead, then calculate per-process values before averages. Do not confuse first response with final completion.
    • Worked example Scheduling-metric example
      • A=2; S=5; B=4; C=9
      • Uninterrupted CPU burst
      • Response=3; turnaround=7; waiting=3
      • Six completions/two hours=3 jobs/hour
      👁 Full explanationWorked microexample
      A job arrives at 2, starts at 5, uses 4 CPU units without interruption and finishes at 9: response=3, turnaround=7, waiting=3. Six completions in two hours means throughput=3 jobs/hour.

  • OS14

    Preemptive and non-preemptive decisions

    [Exam Focus]
    • CPU scheduling variants
      • Non-preemptive: completion/block/yield ends burst
      • Preemptive: running→ready allowed
      • Timer quantum or urgent arrival
      • FCFS/non-preemptive SJF: non-preemptive
      • RR/SRTF: preemptive
      • Priority: either variant
      • Cooperative: voluntary release
      👁 Full explanation
      Non-preemptive scheduling keeps a running CPU burst until completion, blocking or voluntary yielding. Preemptive scheduling can return running work to ready, usually after a timer quantum or a more urgent arrival. FCFS and non-preemptive SJF are non-preemptive; RR and SRTF are preemptive. Priority can be either, so its name alone cannot decide. Cooperative describes relying on voluntary release.
    • CPU versus resource preemption
      • Save context, reallocate CPU time
      • Occupied printer/lock: unsafe withdrawal possible
      • Time-slicing ≠ removing no-resource-preemption
      • Frequent switches: overhead
      • Non-preemptive long bursts delay interaction
      👁 Full explanation
      CPU preemption saves a context and reallocates processing time; taking an occupied printer or lock may be unsafe. This is why time-slicing does not automatically remove the no-resource-preemption condition for deadlock. Frequent switches have cost; non-preemptive policies can delay interactive work behind long bursts.

  • OS15

    FCFS and convoy effects

    [Exam Focus]
    • FCFS behavior and limits
      • Ready bursts: arrival order
      • Ordinarily non-preemptive
      • Idle CPU: jump to next arrival
      • Convoy: long burst delays short jobs
      • Finite work ahead: eventual start
      • Eventual service ≠ small waiting
      • FCFS ≠ universally worst turnaround
      👁 Full explanation
      FCFS runs ready bursts in arrival order and ordinarily does not preempt. If the CPU is idle, jump to the next arrival. Long CPU-bound work can make many short jobs wait: the convoy effect. A finite burst with finitely many jobs ahead eventually starts, but waiting can still be large. FCFS does not universally have the worst turnaround for every possible workload.
    • Worked example FCFS simultaneous-arrival example
      • All arrive 0; P1=24,P2=3,P3=3
      • Tie order: P1,P2,P3
      • P1:0–24; P2:24–27; P3:27–30
      • Waiting 0,24,27 → mean 17
      • Turnaround 24,27,30 → mean 27
      • Different arrivals: recompute actual times
      👁 Full explanationWorked microexample
      All ready at time 0, tie order P1=24,P2=3,P3=3: schedule 0–24 P1,24–27 P2,27–30 P3. Waiting times 0,24,27 average to 17. Turnarounds 24,27,30 average to 27. If arrivals are not simultaneous, recompute using their actual times.

  • OS16

    SJF/SJN and remaining time

    [Exam Focus]
    • Shortest-job scheduling rules
      • SJF/SJN: shortest ready next burst
      • Non-preemptive selection
      • SRTF: reconsider arrivals
      • Shortest remaining work; newcomer may preempt
      • Future bursts: estimates needed
      • SJF minimum-average-wait theorem
      • Fixed simultaneous ready set
      • Known bursts; no preemption/switch cost
      • Theorem ≠ universal preemptive-policy comparison
      👁 Full explanation
      Non-preemptive SJF/SJN chooses the shortest next burst among currently ready jobs. SRTF reconsiders on arrivals and selects the shortest remaining work; a shorter newcomer can preempt. Future burst lengths normally need estimates. SJF minimizes average waiting for the usual fixed simultaneous ready set with known bursts and no preemption/switch cost; that theorem is not a workload-independent comparison against every preemptive policy.
    • Shortest-job traps
      • Repeated short arrivals: long-job starvation
      • Original burst ≠ remaining burst
      👁 Full explanation
      Repeated short arrivals can starve a long job. The shortest total original burst is not necessarily the shortest remaining burst after execution has begun.
    • Worked example SRTF example
      • P1: arrival 0, burst 8
      • P2: arrival 1, burst 2
      • P1:0–1; P2:1–3; P1:3–10
      • Waiting: P1=2, P2=0
      • Non-preemptive SJF: no P1 interruption
      👁 Full explanationWorked microexample
      P1 arrives 0 with burst 8; P2 arrives 1 with burst 2. SRTF runs P1 0–1, P2 1–3, P1 3–10. P1 waiting=2 and P2 waiting=0. Non-preemptive SJF cannot interrupt P1 once it has started.

    Priority, starvation and aging

    [Exam Focus]
    • Priority scheduling assumptions
      • Highest-priority ready job

      • Controller: hardware status/control/data registers
      • Driver: OS requests→device operations
      • Device independence and uniform naming
      • Hide brand-specific details
      • Error handling: supported reports/retries
      • Polling: repeated readiness checks
      • Interrupts: CPU attention requests
      • DMA: setup then block transfer
      • No per-byte CPU work
      👁 Full explanation
      A controller is device hardware exposing status, control and data registers. A driver converts OS requests into device-specific operations. Device independence and uniform naming hide brand-specific details; error handling reports/retries supported failures. Polling checks readiness repeatedly; interrupts request CPU attention; DMA transfers blocks after setup without CPU work for every byte.
    • I/O responsibility boundaries
      • Kernel/driver answer: abstraction scope required
      • Plug-and-play: compatible hardware discovery/configuration
      • Driver may still be needed
      • Input/output/storage/NIC: managed hardware
      • Accounts: identities
      • Paper/network errors: report/handle
      • Total power loss: hardware support required
      • OS software alone insufficient
      👁 Full explanation
      A broad question can name both the kernel and drivers as responsible for I/O; specify the abstraction level. Plug-and-play discovers/configures compatible new hardware but may still require a driver. Input/output/storage/NIC devices are OS-managed hardware; user accounts are identities. Printer-paper and network errors can be handled/reported, but continued operation during total power loss requires hardware support, not OS software alone.

    Buffering, caching, spooling and clocks

    • Buffering versus caching versus spooling
      • Buffer: temporary in-transit data
      • Absorb speed/transfer-size differences
      • Cache: copies for faster reuse
      • Spool: queued device jobs
      • Printer jobs: usually disk-backed
      • Producers avoid continuous device ownership
      • Combined implementation, different purposes
      👁 Full explanation
      Buffering temporarily holds data in transit to absorb speed/transfer-size differences. Caching retains copies to accelerate reuse. Spooling queues jobs for a device such as a printer, usually on disk, so producers need not own it throughout job creation. These have different purposes even if one implementation combines them.
    • Timers, monitoring and disk responsibilities
      • Timer: timekeeping and timeouts
      • Accounting and preemptive scheduling
      • Monitor: CPU/memory/storage/network usage
      • Measurement ≠ resource creation
      • Disk initialization/filesystem creation: OS/tools
      • Boot begins: firmware
      • Bad-sector remapping: drive firmware possible
      • OS-all-disk-functions claim: scope boundaries
      👁 Full explanation
      The clock/timer supports timekeeping, timeouts, accounting and preemptive scheduling. A system monitor reports CPU, memory, storage and network usage; it measures rather than directly creating more resources. Disk initialization/filesystem creation is OS/tool work, firmware begins boot, and drive firmware may remap bad sectors. A broad “OS does all disk functions” claim needs these responsibility boundaries.

    Files, descriptors and operations

    • File content, metadata and handles
      • Metadata: name, size, owner
      • Permissions and timestamps
      • open: obtain reference
      • read/write: byte transfer
      • seek: offset change
      • close: release reference
      • truncate: size change
      • unlink: name removal
      • Descriptor: process-local integer handle
      • Open-file state: offset/access mode
      • Descriptor ≠ offset
      👁 Full explanation
      A file has content and metadata such as name, size, owner, permissions and timestamps. open obtains an open-file reference, read/write transfer bytes, seek changes an offset, close releases a reference, truncate changes size and unlink removes a name. A file descriptor is a process-local integer handle; the associated open-file state contains the current offset and access mode. Descriptor and offset are not synonyms.
    • Read semantics and filesystem formats
      • Seekable read: offset advances
      • Short reads possible
      • Zero read: normally EOF
      • Sockets: ordinary read/write supported
      • socket/connect/send: socket operations
      • read ≠ uniquely non-network call
      • FAT32/NTFS/ext4: filesystem formats
      • HTTP: application communication protocol
      👁 Full explanation
      Read advances the offset on seekable files and may return fewer bytes than requested; zero normally indicates end-of-file. Sockets also support ordinary read/write, alongside socket/connect/send operations, so read is not uniquely “not a network call.” FAT32, NTFS and ext4 are filesystem formats; HTTP is an application communication protocol.

    Directories, mounts and links

    • Directory organizations
      • Single-level: unique names, one namespace
      • Two-level: users separated
      • Tree: nested directories
      • Absolute and relative paths
      • Links: shared graphs
      • Modern systems: commonly hierarchical
      • Feature label ≠ excluding simpler arrangements
      👁 Full explanation
      A single-level directory requires unique names in one namespace. Two-level directories separate users. A tree allows nested directories and absolute/relative paths; links can create shared graphs. Modern general-purpose systems commonly present hierarchical namespaces, but a feature name alone does not prove that every system excludes simpler arrangements.
    • Links and filesystem attachment
      • Hard link: same file, another name
      • Usually within one filesystem
      • Symlink: stored pathname
      • Cross-filesystem targets; dangling links possible
      • Unlink one name ≠ content deletion
      • Remaining names/open references retain content
      • Mount: attach filesystem at mount point
      • Mount ≠ format
      • NFS: remote filesystem access
      • FTP: transfer, not itself mounting
      👁 Full explanation
      A hard link is another name for the same underlying file object, usually within one filesystem; a symbolic link stores a pathname and can point across filesystems or become dangling. Removing one hard link does not erase content while other names/open references retain it. Mounting attaches a filesystem at a mount point; it does not format the device. NFS provides remote filesystem access; FTP transfers files rather than itself mounting a local filesystem.

    File-block allocation methods

    • Contiguous, extent and linked allocation
      • Contiguous: consecutive blocks
      • Logical block i→start+i
      • Direct access
      • Growth and external fragmentation problems
      • Extents: several contiguous runs
      • Linked: block chains
      • Growth without whole-file contiguous reservation
      • Block i: traverse preceding links
      • FAT: chains in table
      • Cached FAT ≠ direct arithmetic mapping
      👁 Full explanation
      Contiguous allocation uses consecutive blocks; logical block i is start+i and supports direct access, but growth and external fragmentation are problems. Extents allow several contiguous runs. Linked allocation chains blocks and supports growth without reserving a complete contiguous file; locating block i requires traversing preceding links. FAT stores chains in a table; caching that table does not change the chain into a direct arithmetic mapping.
    • Indexed allocation and inode lookup
      • Per-file pointer array/tree
      • Direct lookup; metadata overhead
      • Unix inode: direct and indirect pointers
      • Pointer size and block size
      • Index capacity
      • Metadata-read caching assumptions
      👁 Full explanation
      Indexed allocation uses a per-file array/tree of block pointers and supports direct lookup with metadata overhead. A Unix inode can combine direct pointers with indirect levels. Check pointer size, block size, index capacity and whether metadata reads are cached.
    • Worked example Index-capacity example
      • 1024-byte index; 4-byte pointers
      • 1024/4=256 block addresses
      • Data blocks: 1024 bytes
      • One level: 256 KiB data
      • Exclude metadata/reserved entries
      👁 Full explanationWorked microexample
      A 1024-byte index block with 4-byte pointers holds 256 block addresses. With 1024-byte data blocks, one such index level addresses 256 KiB of file data, excluding metadata and any reserved entries.

    Protection, authentication and threats

    • Identity and access control
      • Authentication: verify identity
      • Authorization: permitted operations
      • ACL: principals and rights
      • Owner/group/other: simpler bit model
      • Owner full access: not universal
      • Everyone read: not universal
      • Read/write/execute/append/delete: distinct rights
      • Filesystem-specific permission rules
      👁 Full explanation
      Authentication verifies identity; authorization checks permitted operations. An ACL lists principals and rights; owner/group/other bits are a simpler policy model, not universal defaults granting all owners full access or everyone read. Read, write, execute, append and delete are different rights, with filesystem-specific rules.
    • Security controls, threats and interfaces
      • Least privilege: limited damage
      • Password hashing: no stored plaintext
      • One-time passwords: expire after use
      • Encryption: confidentiality with correct keys
      • Encryption ≠ automatic integrity
      • Trojan: useful-software disguise
      • Worm: independent propagation
      • Virus: attached host
      • DoS: availability harm
      • Cryptography/authentication/firewalls: product-dependent support/configuration
      • Interfaces: CLI, GUI, speech/natural language, VR
      • Interface list: not closed
      👁 Full explanation
      Least privilege limits damage. Password hashing verifies secrets without storing plaintext; one-time passwords expire after use. Encryption protects confidentiality under correct key use but does not automatically provide integrity. Trojans masquerade as useful software, worms propagate independently and viruses attach to hosts; denial of service harms availability. Modern OS families can support cryptography, authentication and firewalls, but support/configuration depends on product. CLI, GUI, speech/natural language and VR are possible interfaces, not a closed list excluding the last two.

    Linux, Android and history limits

    • Kernel, distributions and product licensing
      • Linux: Unix-compatible, written from scratch
      • Linus Torvalds
      • Distribution: kernel/userland/libraries/tools
      • Android base kernel: Linux
      • Framework/applications: higher layers
      • AOSP: open source
      • Devices: proprietary apps/services possible
      • Windows/macOS: proprietary products
      • macOS: open-source components too
      • Both proprietary options: ambiguous answer
      • Microsoft Office: application suite
      👁 Full explanation
      Linux is a Unix-compatible kernel written from scratch by Linus Torvalds; a distribution combines it with userland, libraries and tools. Android’s base kernel layer is Linux; its framework and applications are higher layers. AOSP is open source, while a shipped device can include proprietary applications/services. Windows and macOS are both proprietary products, although macOS contains open-source components, so “which is not open source?” offering both is ambiguous. Microsoft Office is an application suite.
    • Product and historical-claim limits
      • Windows: Microsoft, after MS-DOS desktop era
      • Solaris: Sun origin
      • First widely used: definition/evidence required
      • First multitasking: definition/evidence required
      • UNIX ≠ first ever multitasking
      • Generation/function pairing: historical evidence
      • Mobile majority: population/date required
      • Architecture facts ≠ market-share proof
      👁 Full explanation
      Windows is the Microsoft family commonly described as succeeding the MS-DOS desktop era; Solaris originated at Sun. “First widely used OS,” “first multitasking OS,” and generation/function pairings require a definition and historical evidence; UNIX was not the first system ever to multitask. “Most mobile devices” needs a population and date; architecture facts do not prove market share.

    • Missing or multiple answer concepts
      • Requested concept omitted
      • Several valid examples: reject uniqueness
      • System call: kernel-service request
      • Process: executing program
      • CPU/memory/I/O: multiple managers
      • Device/process/file/security choices: missing umbrella
      • Virtual memory: isolation, translated space
      • Virtual memory ≠ unlimited memory
      👁 Full explanation

Virtual memory provides isolation and translated space; it does not remove every memory constraint.

      • Specify OS versus API
      • Scheduling variant
      • Arrivals and quantum

      • Comparison scope
      • Marked answer ≠ evidence
      • Missing edges: unrecoverable from theory

Keep missing diagrams distinct from concepts that have now been taught: additional theory cannot reconstruct absent process/resource edges.
