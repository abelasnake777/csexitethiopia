  • CP01

    Problem-to-program workflow

    [Exam Focus]
    • Problem-to-program workflow
      • Inputs, outputs, legal ranges, edge cases
      • Manual small-case solution
      • Algorithm → pseudocode or flowchart
      • Implement → test → maintain
      • Largest-of-three: best=first input
      • Compare second, then third
      • Zero initialization fails all-negative inputs
      👁 Full explanation
      Identify inputs, outputs, legal ranges and edge cases before coding. Solve one small case manually, choose an algorithm, express it as pseudocode or a flowchart, implement, test and maintain.       • Writing, testing, debugging, maintaining

  • CP02

    Algorithms and paradigms

    [Exam Focus]
    • Algorithm properties
      • Precise executable steps
      • Termination for every legal input
      • Definiteness: unambiguous meaning
      • Effectiveness: performable steps
      • Optional inputs, specified result
      • Correctness against specification
      • Efficiency: desirable, measurable
      • Inefficient terminating algorithms still qualify
      • Module's desirable-efficiency listing
      👁 Full explanation
      An algorithm gives precise, executable steps and terminates for every legal input. Definiteness means each step has an unambiguous meaning; effectiveness means a step can actually be performed. Inputs may be absent, but a useful algorithm specifies a result. Correctness means the result meets the specification. Efficiency is desirable and measurable, but an inefficient terminating algorithm is still an algorithm. The module sometimes lists efficiency among its desirable properties.
    • Programming paradigms
      • Procedural: procedures organize operations
      • Structured: sequence, selection, iteration
      • Object oriented: state and behavior
      • Functional: function evaluation
      • Conditional: construct, not paradigm
      👁 Full explanation
      Procedural programming organizes operations in procedures; structured programming combines sequence, selection and iteration; object oriented programming organizes state and behavior in objects; functional programming emphasizes function evaluation. A conditional statement is a construct, not a separate programming paradigm.

  • CP03

    Language generations and portability

    • Language generations
      • First: machine instructions
      • Second: symbolic assembly
      • Third: C++, Java, general high-level
      • Fourth: SQL, queries, application generators
      • Fifth: loose historical category
      • Declarative logic, constraints, AI/expert systems
      • Generation independent of interpretation
      👁 Full explanation
      Machine instructions are conventionally first generation; symbolic assembly is second; general high-level languages such as C++ and Java are third. Database query and application generators such as SQL are conventionally fourth generation. Fifth generation is a loose historical category associated with declarative logic, constraints and AI/expert systems. Generations do not determine whether an implementation uses an interpreter.
    • Language portability and conventions
      • Machine/assembly: instruction-set dependence
      • Readable high-level source
      • Recompile without platform assumptions
      • Humans write assembly and high-level
      • Python, Perl, PHP: conventional scripting
      • C++: conventionally compiled
      • Usage labels, not technical prohibitions
      👁 Full explanation
      Machine and assembly code depend on an instruction set. High-level source is easier to read and often portable after recompilation, provided it avoids platform assumptions. People can write both assembly and high-level programs. Python, Perl and PHP are commonly called scripting languages; C++ is conventionally compiled. These labels describe common use, not an absolute technical prohibition.

  • CP04

    Compilation, linking and loading

    [Exam Focus]
    • Conventional C++ toolchain
      • Source → preprocessing → compilation proper
      • Assembly → object files → linking
      • Executable → loading → execution
      • #include: preprocessing directive
      • Compiler may emit assembly
      • Assembler: object-file machine instructions
      • Linker: external-symbol resolution
      • Object files and libraries combined
      • Loader: memory placement and startup
      👁 Full explanation
      In the conventional C++ toolchain: source → preprocessing → compilation proper → assembly → object files → linking → executable → loading → execution. Preprocessing handles directives such as #include; compilation may emit assembly; the assembler emits machine instructions in an object file. The linker resolves external symbols and combines object files and libraries. The loader places an executable and required components in memory and starts it.
    • Translation caveats
      • GCC: first four stages
      • Compiler output needn't be executable/native
      • Java javac → bytecode
      • JVM: interpretation or runtime compilation
      • Interpreters execute program representations
      • Line-by-line: beginner approximation
      • Multiple compilation passes
      • Whole-program one-step claim overbroad
      👁 Full explanation
      GCC documents the first four stages explicitly. A compiler need not emit a complete executable or even native machine code. Java javac produces bytecode, which a JVM interprets or compiles at runtime. Interpreters execute a program representation; “one source line at a time” is a beginner approximation. Compilation uses multiple passes, so “whole program in one step” is not literally universal.

    Identifiers, keywords and comments

    • ASCII identifier rules
      • Initial letter or underscore
      • Subsequent letters, digits, underscores
      • Keywords forbidden
      • Case sensitivity: exitExam ≠ ExitExam
      • delete, float: keywords
      • FLOAT, variable_1234: valid
      • 4thInput, T-3, spaces: invalid identifiers
      • Reserved underscore patterns avoided
      👁 Full explanation
      In the basic ASCII identifier rules, start with a letter or underscore; continue with letters, digits or underscores. Do not use a keyword. C++ is case sensitive: exitExam and ExitExam differ; delete and float are keywords, but FLOAT is a legal identifier. variable_1234 is valid; 4thInput, T-3 and names containing spaces are not single identifiers. Avoid reserved underscore patterns in application code.

      • // line comments
      • /* ... */ block comments
      • Intent, assumptions, maintenance

      • No automatic speed/reliability/portability improvement
      • main: entry function, not keyword
      👁 Full explanation
      Comments use // to the line end or /* ... */ for a block. They explain intent and assumptions for maintenance; ordinary comments do not execute or automatically improve speed, reliability or portability. main is the conventional entry function name, not a C++ keyword.

  • CP06

    Declarations, constants and types

    [Exam Focus]
    • Declaration versus initialization
      • type name;
      • type name = value;
      • int age = 20;
      • Declaration: name and type
      • Initialization: initial value
      • Later assignment replaces value
      • Scalar a=b copies value
      • Later b changes leave a unchanged
      • Pointer assignment copies address
      • Java object-reference assignment copies reference
      👁 Full explanation
      Write type name; or type name = value; for ordinary variables: int age = 20;. Declaration introduces a name and type; initialization gives its initial value; later assignment replaces a value. a=b copies a scalar value, so later changes to b do not change a. A pointer or Java object reference instead copies an address/reference.
    • Types, constants and aliases
      • int: whole numbers
      • float/double: fractional approximations
      • char: character
      • bool: logical values
      • Implementation-dependent C++ sizes
      • Java widths don't transfer
      • short n ≡ short int n
      • int short n: same signed short
      • const int ≡ int const
      • Ordinary const int requires initialization
      • typedef: alias, not distinct type
      👁 Full explanation
      Use int for whole numbers, float/double for fractional approximations, char for a character and bool for logical values in C++. Type sizes depend on the implementation; do not import Java widths into C++. short n, short int n and int short n denote the same signed short type. const int n=5 and int const n=5 are equivalent; an ordinary const int needs initialization. typedef creates an alias, not a distinct new type.

  • CP07

    Literals, conversions and sizeof

    • Literals and storage sizes
      • 'A': character literal
      • "A": string literal
      • Terminator storage beyond visible characters
      • sizeof: bytes
      • sizeof(char)==1
      • Byte width and sizes implementation-dependent
      • sizeof(array): total before pointer conversion
      👁 Full explanation
      Single quotes denote a character literal, such as 'A'; double quotes denote a string literal, such as "A". A string includes more storage than just its visible characters when a terminator is required. sizeof reports size in bytes, with sizeof(char)==1; the byte width and other sizes are implementation dependent. sizeof(array) gives total array storage before conversion to a pointer.
    • Conversion timing
      • int x=5,y=2: x/y=2
      • Double assignment after division: 2.0
      • static_cast<double>(x)/y=2.5
      • Cast before fractional operation
      • In-range float→int: toward-zero truncation
      👁 Full explanation
      With int x=5,y=2, x/y is 2. Assigning that quotient to double gives 2.0, not 2.5. static_cast<double>(x)/y performs floating division and yields 2.5. Converting an in-range fractional floating value to int truncates toward zero. Cast before the operation if a fractional result is needed.

  • CP08

    Arithmetic and compound updates

    • Arithmetic grouping and validity
      • *, /, % before +, -
      • Equal-precedence arithmetic: left grouping
      • Integer division: toward-zero truncation
      • a == (a/b)*b + a%b
      • Identity requires valid division
      • %: integral operands only
      • (8.0*3)%5: invalid
      • Division by zero: no ordinary output
      • Signed overflow: no ordinary output
      👁 Full explanation
      Multiplication, division and remainder have higher precedence than addition and subtraction; equal-precedence arithmetic groups left to right. Integer division truncates toward zero. For integers, a == (a/b)*b + a%b when the division is valid. % requires integral operands in C++; (8.0*3)%5 is invalid. Division by zero and signed integer overflow cannot be given ordinary numeric outputs.
    • Compound assignment traces
      • +=, -=, *=, /=, %=
      • Operation then conversion to x's type
      • Simple x op= y: x=x op y
      • p=q=n=8: p+=n → 16
      • p/=q → 2
      • x=10: +=5, /=2 → 7
      • x=x+x doubles, not generally increments
      👁 Full explanation
      x+=y, x-=y, x*=y, x/=y and x%=y update x using the operation and conversion to its type. For simple variables, trace them as x=x op y. Starting p=q=n=8, p+=n gives 16 and p/=q gives 2. Starting x=10, x+=5 then x/=2 gives 7. x=x+x doubles; it does not generally add one.

  • CP09

    Increment operators and sequencing

    • Prefix versus postfix
      • Expression value versus stored value
      • ++x: increment, yield new
      • x++: yield old, increment
      • a=8,b=5: a++ + --b=12
      • Final a=9,b=4
      • x=1,y=10,z=-3: (x++*y--)+ ++z=8
      • Final x=2,y=9,z=-2
      👁 Full explanation
      Prefix ++x changes x and yields the new value; postfix x++ yields the previous value and also increments x. Separate the value used in the expression from the stored value after it. Starting a=8,b=5, a++ + --b uses 8+4, gives 12, and leaves a=9,b=4. Starting x=1,y=10,z=-3, (x++*y--)+ ++z gives 8 and leaves x=2,y=9,z=-2.
    • Grouping versus evaluation order
      • Repeated unsequenced modifications unsafe
      • C++17 operator-form stream sequencing
      • cout<<x++<<" "<<++x: 5 7
      • Before C++17: undefined behavior
      • Bank options omit correct C++17 output
      👁 Full explanation
      Precedence determines grouping, not a universal evaluation order. Avoid expressions that modify a variable multiple times without sequencing. In C++17 and later, chained operator-form stream insertions are sequenced left to right: with x=5, cout<<x++<<" "<<++x prints 5 7. Before C++17 this expression has undefined behavior. None of the bank options 5 6, 5 5, 6 5, 6 6 is a correct C++17 answer.

  • CP10

    Boolean, bitwise and precedence rules

    • Truth-value operations
      • Relational and equality tests
      • && conjunction, || disjunction
      • ! negation
      • C++ zero=false, nonzero=true
      • Default bool output: 0/1
      • boolalpha changes Boolean formatting
      • a=3,b=5: (a==b) prints 0
      👁 Full explanation
      Relational and equality operators test values; && and || combine truth values; ! negates. In C++, zero converts to false and a nonzero number to true. Streams display bool as 0 or 1 unless boolalpha is set. With a=3,b=5, cout<<(a==b) prints 0.
    • Short circuit versus bitwise
      • &: bits, no short circuit
      • && right only after true left
      • || right only after false left
      • false && dangerousCall(): skipped
      • x=1,y=0,z=4: (x&y)||++z
      • Final z=5, Boolean result=1
      • Grouping/postfix → unary → multiplicative
      • Additive → shifts → relations → equality
      • Bitwise & → ^ → |
      • && → || → conditional
      • Assignment → comma
      👁 Full explanation
      && evaluates its right operand only if the left is true; || only if the left is false. Thus false && dangerousCall() skips the call. Bitwise & operates on bits and does not short circuit. With x=1,y=0,z=4, (x&y)||++z evaluates ++z, leaving z=5 and the Boolean result 1. The precedence ladder is grouping/postfix, unary, multiplicative, additive, shifts, relations, equality, bitwise &, ^, |, &&, ||, conditional, assignment, comma.

  • CP11

    Conditional and comma expressions

    • Conditional and comma operators
      • condition ? yes : no
      • Condition then exactly one alternative
      • Comma: left then right
      • Comma result: right operand value
      • Argument separators differ from comma operator
      👁 Full explanation
      condition ? yes : no evaluates the condition and exactly one alternative. The comma operator evaluates its left expression, then its right, and yields the right value. Do not confuse it with commas separating function arguments.
    • Conditional-comma trace
      • a=6,b=8,x=2,y=4
      • x>y false: (b--,y)
      • Final b=7,c=4,a=6
      • Unselected alternative unexecuted
      • Internal semicolon: invalid syntax
      • Comma restoration requires labeled interpretation
      👁 Full explanation
      For a=6,b=8,x=2,y=4, c=(x>y ? (a--,x) : (b--,y)) takes the false branch. b becomes 7, c receives 4 and a remains 6. Both alternatives are not executed. A semicolon in place of the internal comma is invalid syntax; restoring it must be stated as an interpretation.

  • CP12

    Decisions and flowcharts

    [Exam Focus]
    • Decision grouping
      • Independent consecutive if statements
      • else: nearest unmatched if
      • else-if: first true branch
      • Nested S2: c1 && !c2
      • Braces determine grouping
      👁 Full explanation
      A standalone if may execute independently of the following if. An else binds to its nearest unmatched if; an else-if ladder executes the first true branch only. In nested if(c1){if(c2) S1; else S2;}, S2 requires c1 true and c2 false. Braces determine grouping.
    • Decisions and flowchart evidence
      • ph=15.3: warning plus Alkaline
      • Separate range check and classification
      • else/early return creates exclusivity
      • Diamond: decision
      • Rectangle: processing
      • Parallelogram: input/output
      • Terminator: start/end
      • Pre-test: check before body
      • Post-test: check after body
      • Missing arrows/condition placement: indeterminate loop
      👁 Full explanation
      With ph=15.3, an invalid-range if can print its warning, and a separate classification ladder can also print Alkaline. They are not mutually exclusive unless linked by else or an early return. A flowchart decision is a diamond, processing a rectangle, input/output a parallelogram and start/end a terminator. A pre-test loop checks before its body; a post-test loop checks after. Without the actual arrows and condition placement, a missing flowchart cannot identify a particular loop.

  • CP13

    Switch and fall-through

    • Traditional C++ switch
      • Integral or enumeration selector
      • case: constant expressions
      • Matching label starts execution
      • Fall-through until break/return/end
      • default: unmatched value
      • default needn't be last
      👁 Full explanation
      A traditional C++ switch selects using an integral or enumeration value. case labels are constant expressions. Execution starts at the matching label, then continues through subsequent statements until a break, return or the end. default handles an unmatched value but need not be the last physical label.
    • Switch fall-through trace
      • Input 2: Bus.Truck.
      • Case 2 enters, case 3 continues
      • break: nearest switch or loop
      • break doesn't terminate whole program
      • case label: entry point
      • No automatic branch isolation
      👁 Full explanation
      If case 2 prints Bus. and case 3 prints Truck. before the first break, input 2 prints Bus.Truck. A break exits the nearest switch or loop; it does not by itself terminate the entire program. A case label is an entry point, not an automatically isolated if branch.

  • CP14

    Loop mechanics

    [Exam Focus]
    • Pre-test versus post-test loops
      • while: condition before each body
      • while: possibly zero executions
      • do-while: body before condition
      • do-while: at least once
      • Repeat while condition true
      • Menu/input attempt use case
      👁 Full explanation
      while(condition) checks before each body execution and may run zero times. do {body;} while(condition); runs the body once before checking; it repeats while the condition remains true. Use it when a menu or input attempt must occur at least once.
    • for execution order
      • Initialization once
      • Condition → body → update → condition
      • for(;;): absent condition=true
      • Known-count convenience, condition-control flexibility
      • Indices 0..n-1: i=0,i<n,++i
      • i=0,i<5,i+=2: 0 2 4
      👁 Full explanation
      for(initialization; condition; update) executes initialization once, then condition → body → update → condition. A missing condition in for(;;) acts as true. A for loop is convenient for a known count but can also be condition controlled. To print indices 0 through n-1, use i=0; i<n; ++i. Starting i=0 with i<5 and i+=2 prints 0 2 4.

  • CP15

    Control transfers

    • Control-transfer scope
      • break: nearest loop or switch
      • continue: skip current iteration remainder
      • for continue → update
      • while continue → condition
      • return: leave current function
      • Optional return result
      • main return: normal program end
      👁 Full explanation
      break exits the nearest enclosing loop or switch. continue skips the rest of the current loop iteration: a for loop then runs its update; a while loop goes directly to its condition. return leaves the current function and may supply a result. In main it ends the program normally.
    • goto label tracing
      • Transfers within same function
      • Follow reached labels
      • a → b → end
      • Graduating fourth
      • Year unreachable from entry a
      • Structured alternatives ease reasoning
      👁 Full explanation
      A goto transfers to a label within its function; follow the label reached rather than reading lines in source order. In the bank sequence a: print Graduating; goto b; c: print Year; goto a; b: print fourth;, entry at a prints Graduating fourth and reaches the end. Year is not printed. Structured alternatives usually make such logic easier to reason about.

  • CP16

    Iteration counts and nontermination

    • Loop state tables
      • Condition inputs, body output, updated values
      • i=0,j=8: i<j, i++,j--
      • Entries (0,8),(1,7),(2,6),(3,5)
      • Odd-i continue: two prints
      • Outer i=1,i<5,i+=5: once
      • Inner j=10,j>i,--j: nine prints
      👁 Full explanation
      Make a table with condition inputs, body output and updated values. For i=0,j=8; i<j; i++,j--, body entries are (0,8),(1,7),(2,6),(3,5). If odd i triggers continue, printing occurs twice. With outer i=1; i<5; i+=5, the outer loop runs once; an inner j=10; j>i; --j prints nine times.

      • n=1,n<=18,n+=2
      • Break before multiples of seven
      • Output: 1 3 5
      • Fixed a=6>b=5: infinite while

      • Conditional-only increment: no progress
      • No output, infinite loop
      • <=10→<10 alone insufficient
      👁 Full explanation
      For n=1; n<=18; n+=2, print n unless n%7==0 then break: output is 1 3 5. A while(a>b) with fixed a=6,b=5 never changes its true condition. In data[10]={5,10,...,50}, i=0, advancing i only if data[i]%10==0 causes no progress because data[0]=5. It prints nothing and loops indefinitely; changing <=10 to <10 alone does not repair progress.

  • CP18

    Value, reference and pointer parameters

    [Exam Focus]
    • Pass-by-value isolation
      • Separate parameter object from argument
      • func: a*=5,b+=5,return a+b
      • func(9,3)=53
      • Caller values remain 9,3
      👁 Full explanation
      A C++ value parameter is a separate object initialized from the argument. In func(int a,int b){a*=5;b+=5;return a+b;}, calling func(9,3) returns 53 and leaves the caller values 9 and 3 unchanged.
    • Aliasing and copied addresses
      • int& aliases caller variable
      • Reference swap changes originals
      • int*: copied address
      • *p=value mutates pointed object
      • p=anotherAddress changes local pointer
      • int a[] parameter adjusts to int*
      • Element mutation possible
      • Array length passed separately
      • Java always passes by value
      • Object reference copied, caller variable unaliased
      👁 Full explanation
      An int& parameter aliases the caller variable, so swap(int& a,int& b) changes both originals. An int* parameter copies an address; *p=value changes the pointed-to object, but p=anotherAddress only changes the local pointer. An array parameter int a[] is adjusted to int*: elements can change, and the length must be passed separately. Java always passes by value, including a copy of an object reference; it does not pass caller variables by reference.

  • CP19

    Overloads, defaults and inline

    • Overload resolution and defaults
      • Same name, different parameter count/types/order
      • Return type alone insufficient
      • Argument types then required conversions
      • No unique best match: ambiguity
      • sum(x,y,z=0): two/three arguments
      • Ordinary defaults occupy trailing positions
      👁 Full explanation
      Overloads share a name but differ in parameter count or types/order. Return type alone cannot distinguish them. Choose a candidate using argument types, then required conversions; report ambiguity if there is no unique best match. int sum(int x,int y,int z=0) allows two or three arguments; defaults occupy trailing positions in ordinary declarations.
    • inline meaning
      • No compulsory call-site expansion
      • Small frequent functions: optimization candidates
      • Optimizer decides expansion
      • Linkage/definition rules also matter

    • Pointer identity versus pointed value
      • int x=10, int* p=&x

    Proofs and loop invariants

    [Exam Focus]
    • Proof methods
      • Direct P⇒Q: assume P, derive Q
      • Contrapositive: ¬Q⇒¬P
      • Contradiction: false claim assumption → impossibility
      • Counterexample refutes universal claim
      • Induction: base case
      • P(k) assumption → P(k+1)
      👁 Full explanation
      To prove an implication P⇒Q, a direct proof derives Q assuming P; a contrapositive proves not Q⇒not P; a contradiction assumes the claim false and derives an impossibility. A single counterexample disproves a universal claim. Induction proves a base case and proves P(k+1) assuming P(k).
    • Loop-invariant summation proof
      • Initial sum=0,i=1
      • Guard: i<=n
      • Invariant: sum=(i-1)*i/2
      • Initialization establishes invariant
      • Add i → i*(i+1)/2
      • Increment i restores invariant
      • Exit: i=n+1
      • Result: sum=n*(n+1)/2
      • Termination measure: n-i+1
      • Nonnegative, decreasing while guard holds
      • Assumptions: n>=0, no overflow
      👁 Full explanation
      For sum=0,i=1; while(i<=n){sum+=i;++i;}, use invariant sum=(i-1)*i/2. It holds initially. Adding i gives i*(i+1)/2, then incrementing i restores the invariant. Exit gives i=n+1 and sum=n*(n+1)/2. Termination needs a separate decreasing nonnegative measure n-i+1 while the guard holds. Assume n>=0 and no arithmetic overflow. This connects mathematical proof to actual code.
