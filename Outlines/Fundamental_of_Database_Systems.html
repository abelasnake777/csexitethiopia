  • FDB01

    Database approach, benefits and costs

    • Database versus DBMS
      • Coherent related application facts
      • DBMS defines/stores/retrieves/updates
      • DBMS protects/shares
      • Content versus management software
      • Database system applications/people/infrastructure
      👁 Full explanation
      A database is a coherent collection of related facts with meaning for an application. A DBMS is software that defines, stores, retrieves, updates, protects and shares that data. The database is the content; the DBMS manages it. A database system also includes applications, people and infrastructure.
    • File approach versus DBMS
      • Application-specific formats/access procedures
      • Repeated facts/update disagreement
      • Data isolation
      • Shared integrity difficulties
      • Concurrent update difficulties
      • Centralized metadata
      • Multiple views/authorization/transactions
      • Backup/recovery
      • Controlled redundancy ≠ zero duplication
      • Complexity/administration/storage/licensing costs
      • Tiny fixed application tradeoffs
      • Lightweight embedded DBMSs
      • Useful concurrent access
      • Uncontrolled concurrency → anomalies
      👁 Full explanation
      Traditional file applications define their own formats and access procedures. Separate files can repeat facts, disagree after updates, isolate useful data and make shared integrity or concurrent updates difficult. A DBMS centralizes metadata and supports multiple views, authorization, transactions, backup and recovery. It controls redundancy rather than guaranteeing zero duplication. Complexity, administration, storage and licensing can outweigh benefits for a tiny fixed application; lightweight embedded DBMSs also exist. Concurrent access itself is useful; uncontrolled concurrent access causes anomalies.
    • Database personnel
      • DBA access authorization
      • Backup/recovery/availability
      • Monitoring/tuning/routine maintenance
      • Coordinating database use
      • Designers → schema
      • Developers → user-facing programs
      👁 Full explanation
      The DBA manages access authorization, backup/recovery, availability, monitoring, tuning and routine maintenance, coordinating database use; designers define the schema and application developers build user-facing programs.

  • FDB02

    Data models and product names

    • Data model choices
      • Structure/relationships/constraints/operations
      • Conceptual ER → entities/relationships
      • Relational → tables
      • Hierarchical → parent–child tree
      • Network → pointer-based owner/member links
      • Network permits multiple parents
      • Objects → identity/state/behavior
      • Physical → layouts/access paths
      • Representations ≠ query stages
      👁 Full explanation
      A data model supplies concepts for structure, relationships, constraints and operations. Conceptual ER models describe entities and relationships. Relational models use tables; hierarchical models organize records in a parent–child tree; classic network models connect records through pointer-based owner/member links, allowing multiple parents. Object models represent objects with identity, state and behavior. A physical model specifies record layouts and access paths. These are different representation choices, not stages of one query.
    • Products versus vendor/language
      • Relational PostgreSQL/MySQL/Oracle Database
      • Relational Microsoft SQL Server/IBM Db2
      • MongoDB → document DBMS
      • Java → programming language
      • IBM → vendor
      • IBM answer needs product name
      👁 Full explanation
      PostgreSQL, MySQL, Oracle Database, Microsoft SQL Server and IBM Db2 are relational DBMS products. MongoDB is a document DBMS. Java is a programming language. IBM alone names a vendor, not a database product. Distinguish a vendor such as IBM from a specific database product.

  • FDB03

    Relations, schemas, instances and metadata

    • Relation terminology
      • Relation → set of tuples
      • Tuple/row/record → attribute values
      • Attribute/column/field → property
      • Degree → columns
      • Cardinality → rows
      • Classical distinct tuples
      • Atomic cells/attribute domains
      • Meaningless row order
      • Named attributes → meaningless column order
      • SQL duplicates unless constrained
      👁 Full explanation
      A relation is a set of tuples, represented as a table. A tuple/row/record contains related attribute values; an attribute/column/field describes a property. Degree counts columns; cardinality counts rows. Classical relations have distinct tuples, atomic cells and domains for attributes; row order has no meaning. Column order has no logical meaning when attributes are identified by name. SQL tables can contain duplicate rows unless constrained.
    • Schema versus instance
      • Schema → names/structures/constraints
      • Instance/state/snapshot → current data
      • Student insertion → state change
      • Column addition → schema change
      • Metadata → data describing data
      • Catalog/data dictionary
      • Definitions/types/constraints
      • Privileges/optimizer statistics
      • Schema diagram → tables/key references
      • Database diagram terminology overlap
      👁 Full explanation
      A schema describes names, structures and constraints; an instance, state or snapshot is the data at a particular time. Inserting a student changes the state, while adding a column changes the schema. Metadata is data describing data. The catalog or data dictionary records table definitions, types, constraints and often access privileges and optimizer statistics. A schema diagram draws tables and key references; labels such as database diagram can overlap.

  • FDB04

    Three-schema architecture and data independence

    [Exam Focus]
    • Three-schema abstraction
      • External → user-group views
      • Conceptual → whole logical database
      • Entity types/relationships/types/constraints
      • Internal → files/placement/access paths
      • Abstraction levels ≠ deployment tiers
      👁 Full explanation
      The external level gives each user group a selected view. The conceptual level describes the whole logical database: entity types, relationships, data types and constraints. The internal/physical level describes files, record placement and access paths. These are abstraction levels, distinct from client/server deployment tiers.
    • Data independence
      • Physical → internal changes
      • Index addition preserves conceptual schema
      • Logical → conceptual changes
      • Preserved external views/application interfaces
      • Table split with compatible view
      • Logical independence harder
      • Applications depend on logical meaning
      • Abstraction hides irrelevant detail
      • Program–data insulation separates definitions/code
      👁 Full explanation
      Physical data independence permits changing internal storage without changing the conceptual schema, for example adding an index. Logical data independence permits conceptual changes while preserving affected external views and application interfaces, for example splitting a table while maintaining a compatible view. It is harder because applications depend on logical meaning. Data abstraction hides irrelevant details; program–data insulation separates data definitions from application code.

  • FDB05

    Requirements through implementation

    [Exam Focus]
    • Requirements through implementation
      • Business facts/transactions/reports
      • Volumes/privacy/quality targets
      • Conceptual design → ER/EER
      • Logical design → relations/keys/constraints
      • Logical normalization check
      • Physical → organization/indexes/storage
      • Implementation → create/load objects
      • Testing → requirements
      👁 Full explanation
      First collect business facts, required transactions, reports, volumes, privacy rules and quality targets. Conceptual design turns them into an ER/EER model. Logical design maps the conceptual model to relations, keys and constraints and checks normalization. Physical design chooses file organization, indexes and storage. Implementation creates and loads the actual objects; testing checks requirements.
    • Design methodology qualifications
      • Logical design tied to model
      • Potential DBMS independence
      • Later vendor-specific refinement
      • Universal dependence claims need methodology
      • Conceptual enterprise view → downward
      • Normalization dependencies → upward
      • Useful approaches ≠ mandatory directions
      👁 Full explanation
      Logical relational design is tied to a data model but can remain independent of a particular DBMS. Vendor-specific implementation details may be introduced during later refinement. Whether logical design is DBMS-dependent depends on the stated design methodology. Conceptual design usually proceeds from a whole enterprise view downward; normalization can refine structures from dependencies upward. These are useful approaches rather than mandatory directions for every modeling activity.

  • FDB06

    Entities, attributes and ER notation

    [Exam Focus]
    • ER concepts and Chen notation
      • Entity → distinguishable real/conceptual thing
      • Student/course instances
      • Entity type → common properties
      • Entity set → current collection
      • Relationship → entity association
      • Rectangle → entity type
      • Diamond → relationship
      • Ellipse → attribute
      • Double ellipse → multivalued
      • Dashed ellipse → derived
      • Inspect diagram legend
      👁 Full explanation
      An entity is a distinguishable real or conceptual thing, such as one student or one course. An entity type describes common properties; its current collection of entities is an entity set. A relationship associates entities. In Chen notation rectangles represent entity types, diamonds relationships and ellipses attributes; double ellipses denote multivalued attributes and dashed ellipses derived attributes. Always inspect the diagram legend.
    • Independent attribute dimensions
      • Simple versus composite
      • Address → City/Street
      • Single-valued versus multivalued
      • Student → several phone numbers
      • Composite single-valued address
      • Age derived from BirthDate
      • Derived can also be single-valued
      • Names alone cannot establish multiplicity
      👁 Full explanation
      Simple versus composite asks whether a value has meaningful components: Address may split into City and Street. Single-valued versus multivalued asks how many values one entity may have: a student may have several phone numbers. These dimensions differ: one address may be composite and single-valued. Age derived from birth date is derived, even if also single-valued. Attribute names alone do not establish multiplicity.

  • FDB07

    Superkeys, candidate keys and primary keys

    [Exam Focus]
    • Key hierarchy
      • Superkey → tuple uniqueness
      • Candidate key → minimal superkey
      • Remove component → uniqueness lost
      • Minimal ≠ globally fewest columns
      • Primary → selected candidate
      • Alternate → remaining candidate
      • Composite → multiple attributes
      • Composite need not be primary
      👁 Full explanation
      A superkey uniquely identifies a tuple. A candidate key is a minimal superkey: removing any component loses uniqueness. Minimal means no unnecessary attribute, not necessarily the fewest columns among all keys. A primary key is one selected candidate key; remaining candidates are alternate keys. A composite key contains multiple attributes and need not be the chosen primary key.
    • Key assumptions and traps
      • Unique ID → {ID} superkey
      • {ID,City} nonminimal superkey
      • Several candidates/foreign keys
      • At most one primary-key constraint
      • Multicolumn primary key allowed
      • String keys allowed
      • Prefer stable compact identifiers
      • Email/SSN/EmployeeID uniqueness needs rules
      • Single-column options ≠ composite example
      👁 Full explanation
      If ID is unique, both {ID} and {ID,City} are superkeys, but only {ID} is minimal. A table can have several candidates and foreign keys but at most one declared primary-key constraint, possibly containing several columns. String columns can be keys. Prefer stable, compact identifiers when practical, but Email, SSN or EmployeeID is a candidate only if business rules guarantee uniqueness. A composite-key example must include multiple columns; a single-column key is not composite.
    • Worked example Eligible versus preferred primary keys
      • CustID/Email/ContactNo candidate keys
      • All eligible
      • CustID preference needs stability/size policy
      • Uniqueness alone cannot choose
      👁 Full explanationWorked example
      Given candidate keys CustID, Email and ContactNo, all are eligible primary keys. CustID is preferable only with an explicit stability/size policy; uniqueness alone does not choose it.

  • FDB08

    Weak entities and identifying relationships

    [Exam Focus]
    • Weak entity identification
      • No independent complete key
      • Owner normally strong entity
      • Owner/strong entity-set terminology overlap
      • Partial key = discriminator
      • Distinguishes same-owner weak entities
      • Owner key + partial key
      👁 Full explanation
      A weak entity lacks a complete independent key. Its owner is normally a strong entity, so owner entity set and strong entity set may both describe the associated set. Its partial key, also called discriminator, distinguishes weak entities of the same owner. Identification combines the owner key and partial key.
    • Dependent weak-entity mapping
      • Names unique within employee
      • Key (EmployeeID,DependentName)
      • EmployeeID foreign key
      • Total identifying participation
      • Chen double rectangle
      • Double identifying diamond
      • Partial-key dashed underline
      • Foreign key alone ≠ weak entity
      👁 Full explanation
      For Dependent(EmployeeID,DependentName,BirthDate), suppose names are unique only within one employee's dependents. Then (EmployeeID,DependentName) is the key, and EmployeeID is a foreign key. The weak entity participates totally in its identifying relationship. Chen notation uses a double rectangle, double identifying diamond and dashed underline for a partial key. A weak entity is not merely any table with a foreign key.

  • FDB09

    Cardinality, participation and direction

    [Exam Focus]
    • Relationship cardinality and degree
      • Maximum → 1:1/1:N/M:N
      • Minimum zero → optional/partial
      • Minimum ≥1 → mandatory/total
      • Maximum one ≠ compulsory participation
      • Degree → entity roles
      • Unary recursive/binary/ternary
      👁 Full explanation
      Cardinality specifies maximum associated occurrences: 1:1, 1:N or M:N. Minimum cardinality specifies optional/partial participation (zero permitted) or mandatory/total participation (at least one). A maximum of one does not mean participation is compulsory. Relationship degree counts participating entity roles: unary recursive, binary or ternary.
    • Direction and notation assumptions
      • Employee→Department N:1
      • Department→Employee 1:N
      • Building→Location possibly N:1
      • Names alone insufficient
      • Advisor arrows to both entities
      • Common convention → maximum-one both ends
      • Resulting 1:1
      • Unknown convention → unsafe arrow inference
      👁 Full explanation
      Read business rules in both directions. If each employee belongs to one department and each department has many employees, Employee→Department is N:1; Department→Employee is 1:N. Building→Location could also be N:1, so names alone cannot select a unique example. Under the common arrow convention, arrows from advisor to both Instructor and Student impose maximum-one at both ends, giving 1:1. Without a notation convention, arrows are unsafe evidence.

  • FDB10

    Map entities, composite and multivalued attributes

    [Exam Focus]
    • Strong-entity mapping
      • One relation per entity type
      • Preserve simple attributes
      • Select candidate key
      • Expand composite components
      • Flat atomic relational design
      • Calculate derived values
      • Avoid stale stored copies
      👁 Full explanation
      Create one relation per strong entity type, preserve its simple attributes and select a candidate key. Expand composite attributes into their useful simple components; do not copy a composite ER structure unchanged into a flat atomic design. Derived values can usually be calculated, avoiding stale stored copies.
    • Multivalued-attribute mapping
      • Separate owner-key/value relation
      • StudentPhone(StudentID,Phone)
      • Primary key (StudentID,Phone)
      • StudentID foreign key
      • Separate phone rows
      • No comma-separated lists
      • No Phone1/Phone2 repetition
      • Explicit omitted mapping step
      • Entity-based table names valid
      👁 Full explanation
      Map each multivalued attribute to a separate relation containing the owner key and one value. StudentPhone(StudentID,Phone) has primary key (StudentID,Phone) and a foreign key to Student. Store separate rows for two phone numbers, not a comma-separated list or repeated Phone1/Phone2 columns. Include the relational mapping step when translating an ER/EER design into tables. Table names may follow entity names; naming does not invalidate a mapping.

  • FDB11

    Map 1:1 and 1:N relationships

    [Exam Focus]
    • 1:N relationship mapping
      • One-side key → many-side FK
      • Relationship attributes on many side
      • Department/Employee DeptID reference
      • HireDate relationship attribute
      • Total participation → NOT NULL
      • Partial → nullable unassigned reference
      👁 Full explanation
      For 1:N, place the one-side key as a foreign key in the many-side table; store relationship attributes there. Department(DeptID) and Employee(EmpID,DeptID,HireDate) implement many employees per department. If participation is total, make the reference NOT NULL. If partial, a nullable reference can represent no assignment.
    • 1:1 relationship mapping
      • Foreign key plus UNIQUE
      • Prefer totally participating side
      • Reduce NULLs
      • NOT NULL → mandatory reference
      • Merge only compatible lifecycles/participation
      • A→B many-to-one reference in A
      • Total or partial participation allowed
      • Total-only mapping claim overstated
      👁 Full explanation
      For 1:1, one side may hold the other key with a UNIQUE constraint. Prefer the totally participating side to reduce NULLs; NOT NULL enforces that side's mandatory reference. Merging entities is reasonable only when their lifecycle and participation rules permit it. For A→B many-to-one, A can absorb the relationship reference under either total or partial participation; requiring total participation as the only possible case overstates the rule.

  • FDB12

    Map M:N, recursive and n-ary relationships

    [Exam Focus]
    • M:N association table
      • Enrollment(StudentID,CourseID,Grade)
      • References Student and Course
      • One enrollment/pair → composite key
      • Repeated attempts → Term/AttemptNo key
      • Ordinarily three tables
      👁 Full explanation
      A binary M:N relationship needs an association table in addition to the two entity tables. Enrollment(StudentID,CourseID,Grade) references Student and Course; (StudentID,CourseID) is a key if one enrollment per pair is allowed. Repeated attempts require Term or AttemptNo in the key. This ordinarily produces three tables.
    • Recursive and ternary mapping
      • UserLink(UserID,OtherUserID)
      • Two User foreign keys
      • Directed versus undirected links
      • Self-link policy
      • Employee nullable SupervisorID
      • Recursive 1:N supervision
      • Supply(SupplierID,PartID,ProjectID,Quantity)
      • Preserve participating references/triples
      • Binary replacements can lose triples
      • Association key from actual cardinalities
      • All references not automatically necessary
      👁 Full explanation
      A recursive M:N friendship uses UserLink(UserID,OtherUserID), two foreign keys to User; decide whether links are directed and whether self-links are allowed. A recursive 1:N supervision uses a nullable SupervisorID reference in Employee. For a ternary Supply(SupplierID,PartID,ProjectID,Quantity), preserve all participating references; binary replacements can lose which triple occurred. Choose the association key from actual cardinalities rather than automatically assuming every reference is necessary.

  • FDB13

    EER inheritance and category constraints

    [Exam Focus]
    • EER inheritance constraints
      • Superclass/subclass
      • Inherited attributes/relationships
      • Specialization → Undergraduate/Graduate
      • Generalization → common Student properties
      • Disjoint → no overlap
      • Overlapping → shared members
      • Total → every superclass member
      • Partial → membership not compulsory
      👁 Full explanation
      EER extends ER with superclass/subclass structure. A subclass inherits the superclass attributes and relationships. Specialization divides Student into Undergraduate and Graduate; generalization combines common properties into Student. Disjoint subclasses cannot overlap; overlapping subclasses can. Total specialization requires every superclass member in some subclass; partial specialization does not.
    • Inheritance and category mapping
      • Person(PersonID,Name)
      • Student(PersonID,Program)
      • Subclass PersonID both PK/FK
      • Preserved inherited identity
      • Category/union → Person or Company
      • Intersection → both superclasses
      • Object inheritance also supported
      • ER answer requires EER scope
      • Structural inheritance ≠ executable methods
      👁 Full explanation
      Map Person(PersonID,Name) and Student(PersonID,Program) with Student.PersonID both primary key and foreign key to Person. This preserves inherited identity. A category/union subclass draws members from a union of different superclasses, such as Owner drawn from Person or Company; it differs from an intersection subclass requiring membership in both. Object models also support inheritance; distinguish basic ER notation from EER when comparing models. Structural EER inheritance alone does not define executable object methods.

  • FDB14

    Fan traps and chasm traps

    • Fan trap
      • Common entity fans into two 1:N
      • Department→Employee and Department→Project
      • Path cannot determine WorksOn
      • Department join → every employee/project pair
      • Record WorksOn explicitly
      👁 Full explanation
      A fan trap occurs when two 1:N relationships fan from a common entity and a path suggests an association it cannot determine. Department→Employee and Department→Project do not reveal which employee works on which project; joining through Department pairs every employee with every project in that department. Record WorksOn explicitly when that is the fact needed.
    • Chasm trap
      • Optional relationship breaks path
      • Unstaffed branch property disappears
      • Add required direct relationship
      • Or revise model
      • Multiple 1:N relationships legitimate
      • Eliminating all fans ≠ universal repair
      • Missing path → chasm
      • Fan → association ambiguity
      👁 Full explanation
      A chasm trap occurs when an apparently useful path fails for some occurrences because an optional relationship breaks it. For example, a branch's property may be lost from a path that requires an assigned staff member when some properties have none. Add the required direct relationship or revise the model. Multiple 1:N relationships are legitimate; eliminating all fans is not a universal repair. A missing path describes a chasm, not the defining ambiguity of a fan.

  • FDB15

    Integrity and constraint taxonomy

    [Exam Focus]
    • Integrity categories
      • Domain → type/allowed values
      • Key → uniqueness
      • Entity → every PK component non-NULL
      • Referential → non-NULL FK matches key
      • Eligible unique/candidate referenced key
      • Self-references allowed
      • Parent need not have child
      👁 Full explanation
      Domain integrity restricts type and allowed values. Key integrity enforces uniqueness. Entity integrity requires every primary-key component to be non-NULL. Referential integrity requires a non-NULL foreign-key value to match an eligible referenced unique/candidate key; self-references are allowed. A parent need not have a child.
    • Constraint mechanisms and interpretation
      • Inherent → data model
      • Schema-based → DDL
      • Semantic/application → triggers/application logic
      • DDL expressiveness limits
      • Integrity → validity
      • Authorization → allowed access
      • Uniqueness/domain validation both integrity
      • NULL Department PK → entity violation
      • Manager=107 missing employee
      • Declared FK → referential violation
      • One INSERT → multiple violations
      👁 Full explanation
      Inherent constraints come from the data model; schema-based constraints are declared through the DDL; semantic/application rules may need triggers or application logic when DDL cannot express them. Integrity improves data validity; authorization controls who may access it. Uniqueness and domain validation are both integrity mechanisms. If a Department primary key is NULL and Manager=107 lacks a referenced employee, entity integrity certainly fails and referential integrity also fails if that foreign key is declared. One INSERT can violate multiple constraints.

  • FDB16

    Write and enforce SQL constraints

    [Exam Focus]
    • SQL constraint declaration
      • Enrollment StudentID/CourseID INTEGER NOT NULL
      • REFERENCES Student(StudentID)/Course(CourseID)
      • Grade INTEGER CHECK
      • Grade BETWEEN 0 AND 100
      • PRIMARY KEY (StudentID,CourseID)
      • Column name then type
      • Commas separate declarations
      • CHECK clause ≠ standalone GRANT-like statement
      • POSITIVE not general SQL keyword
      • CHECK (Amount > 0)
      👁 Full explanation
      Example: CREATE TABLE Enrollment (StudentID INTEGER NOT NULL REFERENCES Student(StudentID), CourseID INTEGER NOT NULL REFERENCES Course(CourseID), Grade INTEGER CHECK (Grade BETWEEN 0 AND 100), PRIMARY KEY (StudentID,CourseID)); Each column declaration gives its name then type, with commas between declarations. CHECK is a constraint clause, not a standalone GRANT-like statement. POSITIVE is not a general SQL constraint keyword; CHECK (Amount > 0) expresses positivity.
    • Constraint NULL and reference behavior
      • PRIMARY KEY → unique/non-NULL
      • UNIQUE need not imply NOT NULL
      • UNIQUE NULL treatment DBMS-dependent
      • CHECK unknown can pass
      • NOT NULL forbids missing values
      • NO ACTION/RESTRICT
      • CASCADE
      • SET NULL
      • Referenced keys can change
      • Children/action determine legality
      👁 Full explanation
      PRIMARY KEY implies uniqueness and non-NULL. UNIQUE does not generally imply NOT NULL; NULL treatment differs by DBMS. A CHECK can pass when its result is unknown, so add NOT NULL if missing values must be forbidden. Parent updates/deletes may use NO ACTION/RESTRICT, CASCADE or SET NULL. A referenced key is not inherently unchangeable: legality depends on matching children and the declared action.

  • FDB17

    Functional dependencies and attribute closure

    [Exam Focus]
    • Functional dependencies
      • X→Y: agreeing X implies agreeing Y
      • Every legal tuple pair
      • Business constraint ≠ sample correlation
      • Full → all determinant attributes
      • Partial → proper determinant subset
      • Prime → some candidate key
      • Nonprime → no candidate key
      👁 Full explanation
      X→Y means every legal pair of tuples agreeing on X also agrees on Y. It is a business constraint, not a correlation observed in one sample. Full dependency requires all determinant attributes; partial dependency holds through a proper subset. A prime attribute belongs to some candidate key; a nonprime attribute belongs to none.
    • Closure and Armstrong axioms
      • Start X+ with X
      • Applicable FD → add RHS
      • Repeat until fixed point
      • X+ covers relation ↔ superkey
      • Remove/recompute → minimality
      • Reflexivity: Y⊆X ⇒ X→Y
      • Augmentation: X→Y ⇒ XZ→YZ
      • Transitivity: X→Y,Y→Z ⇒ X→Z
      👁 Full explanation

    Records, pages and primary file organization

    • Pages and blocking calculations
      • Page/block → I/O unit
      • Several records/page

      A page/block is a unit of database I/O and holds several records. For fixed unspanned records of size r in usable page space B, the blocking factor is floor(B/r), and n records occupy ceil(n/blocking factor) pages. Page headers and slots reduce usable space.

      • Heap → unordered/simple inserts
      • Heap search → possible full scan
      • Sorted → range scans/binary search
      • Ordering-field search
      • Costly inserts/overflow handling

      • Replication → copy
      • Migration → move

      • Space overhead

      👁 Full explanation
      CAST('42' AS INTEGER) converts an expression to a requested type if the value permits it. CONVERT is vendor-specific and can also perform type conversion; specify the SQL dialect when comparing it with CAST. In SELECT xyz FROM table1 UNION xyz FROM table2, the second SELECT is missing. In the corrected query, xyz is a selected column/expression, not a table name.

  • FDB35

    Relational algebra: calculate results

    • Relational algebra operators
      • Selection σ → tuple filtering
      • Projection π → attributes
      • Set projection removes duplicates
      • Rename ρ → relation/attribute names
      • Union/difference/intersection → compatible schemas
      • R−S not commutative
      • Union/intersection commutative
      • Inner joins commutative with adjusted predicates
      • Up to attribute order
      • LEFT OUTER not generally commutative
      • Vague join needs variant
      👁 Full explanation
      Selection σ filters tuples; projection π retains attributes and removes duplicate tuples under set semantics. Rename ρ changes relation or attribute names. Union, difference and intersection require union-compatible schemas. Difference R−S is not commutative; union and intersection are. Inner joins are commutative up to attribute order when predicates are adjusted; left outer joins are not generally commutative. Identify the join variant before predicting its behavior.
    • Product counts and algebra basis
      • |R×S| = |R|×|S|
      • Product degree = degree(R)+degree(S)
      • Rename conflicting attributes
      • 200×100=20,000
      • 5×7=35
      • Join = selection over product
      • Intersection derivable from difference
      • Basis σ/π/union/difference/product/rename
      • Assignment useful, not indispensable
      • Textbook primitive lists vary
      👁 Full explanation
      A Cartesian product has |R|×|S| tuples and degree degree(R)+degree(S), renaming conflicting attributes if necessary. Thus 200×100=20,000 and 5×7=35. Join equals selection over a product; intersection can be derived from difference. A common minimal basis contains selection, projection, union, difference, product and rename. Assignment is a useful notation, not an indispensable primitive; lists of basic operations vary across textbooks.

  • FDB36

    Relational calculus: state the desired facts

    • Algebra versus calculus
      • Algebra → operation sequence
      • Procedural at logical level
      • Calculus → desired-result predicate
      • Declarative/nonprocedural
      • Tuple variables → tuples
      • Domain variables → attribute values
      • Safe/range-restricted expressions
      • Results bounded by active domain
      👁 Full explanation
      Relational algebra specifies a sequence of operations and is procedural at the logical level. Relational calculus specifies a predicate describing desired results and is declarative/nonprocedural. A tuple variable ranges over tuples; a domain variable ranges over individual attribute values. Safe/range-restricted expressions produce results bounded by the database's active domain.
    • Calculus forms and quantifiers
      • {s | Student(s) AND s.Major='CS'}
      • Tuple result → CS students
      • Domain result → names n
      • ∃i,m (Student(i,n,m) AND m='CS')
      • Existential → some matching tuple
      • Universal → every required case
      • SQL declarative
      • Optimizer chooses procedural execution plan
      👁 Full explanation
      Tuple form {s | Student(s) AND s.Major='CS'} selects student tuples with that major. A domain form can request names n satisfying ∃i,m (Student(i,n,m) AND m='CS'). Existential quantification means some matching tuple exists; universal quantification means every required case meets a condition. SQL is declarative even though an optimizer later chooses a procedural execution plan.

  • FDB37

    Transactions and ACID

    • Transactions and ACID
      • Transaction → logical operation unit
      • Atomicity → all effects or none
      • Consistency → correct invariant preservation
      • Isolation → concurrent interference control
      • Serializable → equivalent serial execution
      • Durability → committed crash survival
      • Durable logging typical
      • Immediate page forcing unnecessary
      👁 Full explanation
      A transaction groups operations into one logical unit. Atomicity applies all its effects or none. Consistency means a correct transaction preserves declared invariants. Isolation controls interference between concurrent transactions; serializable isolation provides behavior equivalent to some serial execution. Durability preserves committed effects after a crash, typically through durable logging rather than forcing every data page immediately.
    • Transfer and transaction control
      • Subtract/add 100 commit together
      • Lost half → atomicity violation
      • Possible total-balance invariant violation
      • BEGIN → start
      • COMMIT → complete
      • ROLLBACK → undo uncommitted work
      • SAVEPOINT → intermediate rollback point
      • Other committed transactions remain
      • Syntax/error-handling DBMS-dependent
      • @@ERROR/IF SQL Server-specific
      👁 Full explanation
      For a transfer, subtracting 100 from one balance and adding 100 to another must commit together; losing either half violates atomicity and may violate the total-balance invariant. BEGIN starts work, COMMIT completes it, ROLLBACK undoes uncommitted work and SAVEPOINT marks an intermediate rollback point. A failed transaction may roll back while other users' committed transactions remain. SQL transaction syntax and error-handling constructs differ by DBMS; @@ERROR/IF is SQL Server-specific.

    Choose techniques from requirements

    [Exam Focus]
    • Match technique to requirement
      • Normalization → dependency anomalies
      • Indexing → search paths
      • Denormalization → repeat/precompute facts
      • Lower selected read costs
      • Higher maintenance cost
      • Partitioning → rows/columns divided
      • Replication → copies
      • Locality/availability benefits
      • Update complexity
      • Techniques can coexist
      • E-commerce/gaming label insufficient
      👁 Full explanation
      Normalization reduces dependency-driven anomalies. Indexing supplies search paths. Denormalization deliberately repeats or precomputes facts to reduce selected read costs, increasing maintenance work. Partitioning divides rows or columns; replication creates copies to improve locality or availability while complicating updates. These techniques can coexist. An e-commerce or gaming label alone does not select one.
    • Security and quality requirements
      • Privacy → threat model
      • Authentication → identity
      • Role authorization → records/actions
      • Encryption → at rest/in transit
      • Auditing → activity records
      • Patient data → encryption/access control
      • Scalability/availability/retrieval speed
      • Redundancy control/security
      • Functional → behavior
      • Nonfunctional → quantified quality
      • 99.9% uptime/response time
      • Mechanisms alone cannot classify requirement
      👁 Full explanation
      Privacy requires a threat model. Authentication verifies identity; role-based authorization limits allowed records/actions; encryption protects data at rest or in transit; auditing records activity. Both encryption and access control can protect patient data. Scalability, availability, fast retrieval, redundancy control and security are all reasonable design considerations. Functional requirements describe behavior; nonfunctional requirements quantify qualities such as 99.9% uptime or response time. Authentication and encryption mechanisms alone do not uniquely establish that distinction.
    • CMS meaning versus integrity
      • Tags/categories → meaning
      • Foreign keys → valid references
      • ContentTag(ContentID,TagID)
      • Multiple tags/item
      • Complementary functions
      👁 Full explanation
      In a CMS, tags/categories describe meaning, while foreign keys preserve valid references between content and tags. A ContentTag(ContentID,TagID) association models multiple tags per item; these functions complement each other.

    Registration and dormitory design

    [Exam Focus]
    • Registration/dormitory business rules
      • Student → one department
      • Student/course → many-to-many
      • Student → at most one current dorm
      • Dorm → at most six students
      • Department/Student/Course/Dorm entities
      • Enrollment relationship with Grade
      👁 Full explanation
      State the rules first: each student belongs to one department, may enroll in many courses, and has at most one current dorm assignment. Each course accepts many students; each dorm holds at most six students. Identify Department, Student, Course and Dorm entities; Enrollment is the M:N relationship with Grade.
    • Integrated schema and capacity enforcement
      • Department(DeptID,Name)
      • Student(SID,Name,DeptID,DormID)
      • Course(CID,Title)
      • Enrollment(SID,CID,Grade)
      • Dorm(DormID,FloorNumber)
      • Entity IDs → primary keys
      • Student DeptID/DormID → parent FKs
      • Enrollment PK (SID,CID)
      • Enrollment → both parent references
      • Nullable DormID until assignment
      • StudentPhone(SID,Phone) → multiple contacts
      • Department/course facts in owning tables
      • FK alone cannot enforce six capacity
      • Concurrency-safe trigger/allocation transaction
      • Or six unique slots/dorm
      👁 Full explanation
      Use Department(DeptID,Name), Student(SID,Name,DeptID,DormID), Course(CID,Title), Enrollment(SID,CID,Grade) and Dorm(DormID,FloorNumber). Declare all entity IDs primary keys; Student.DeptID and Student.DormID reference their parents; Enrollment has composite key (SID,CID) and both references. Make DormID nullable until assignment. Separate StudentPhone(SID,Phone) for multiple contacts. Normalize repeated department/course facts into their owning tables. A simple foreign key does not enforce the six-student capacity; use a concurrency-safe trigger, allocation transaction or explicit slot design with six unique slots per dorm.
    • Worked example Dorm reference direction
      • FOREIGN KEY (DormID) REFERENCES Dorm(DormID)
      • STUDENT → referencing child
      • DORM → referenced parent
      • Consistent names
      • Student.DormID required before execution
      👁 Full explanationWorked example
      Complete the reference as FOREIGN KEY (DormID) REFERENCES Dorm(DormID). STUDENT is the referencing child; DORM is referenced. Consistent names and an added Student.DormID column are required before execution.
