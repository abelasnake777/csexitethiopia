  • WEB01

    Browser, server and technology roles

    [Exam Focus]
    • Internet, Web and service roles
      • Internet: connected networks
      • Web: resource system, commonly HTTP
      • Browser/user agent: requests and HTML/CSS rendering
      • Permitted JavaScript execution
      • HTTP server: requests→representations
      • Server may invoke application code
      • Client/server roles can share one machine
      👁 Full explanation
      The Internet connects networks; the Web is a resource system commonly using HTTP. A browser/user agent requests resources and renders HTML/CSS, then runs permitted JavaScript. A web/HTTP server receives requests and returns representations, sometimes invoking application code. Client and server are roles and can run on the same machine.
    • Technology responsibilities
      • HTML: structure/meaning; CSS: presentation
      • JavaScript: programmable interactivity
      • PHP; Python; JSP/Java; ASP.NET
      • Server responses and database access
      • C#: commonly ASP.NET
      • Node.js: JavaScript runtime, not language
      • JavaScript on client or server
      • Browser sandbox; permission-based file/device APIs
      • Nontrivial programs possible
      • No unrestricted arbitrary client-hardware access
      👁 Full explanation
      HTML supplies structure/meaning; CSS controls presentation; JavaScript supplies programmable interactivity. PHP, Python, JSP/Java and ASP.NET applications generate server responses and access databases; C# is commonly used with ASP.NET. Node.js is a JavaScript runtime, not a separate language. JavaScript can run on either side. Browser scripts are sandboxed, but may access selected files/devices through permission-based APIs. They are not inherently limited to trivial programs, nor can they freely access arbitrary client hardware.

    [Exam Focus]

      • DNS: names→network records
      • ISP: connectivity
      • URL: scheme, host, optional port
      • Path; query; fragment
      • Host: machine/service name

      Hosting supplies an environment where a site is served; domain registration reserves a name, and DNS maps names to network records. An ISP provides connectivity. Static pages can still run interactive browser scripts, and dynamic generation need not change visible text every time. A website groups resources; a page is one document/resource. Open standards do not guarantee identical support for every feature in every browser. Historical editor-name items refer to Microsoft FrontPage and Macromedia HomeSite5, not languages or required modern tools.

  • WEB03

    Read an HTTP/1.1 exchange

    [Exam Focus]
    • HTTP/1.1 message anatomy
      • Request: method, request-target, version
      • Headers→blank line→optional body
      • GET /courses?id=7 HTTP/1.1
      • Host: example.edu; terminating blank line
      • Body may be absent
      • Response: version, status, optional reason
      • Headers→blank line→permitted content
      • Request line ≠ response status line
      👁 Full explanation
      An HTTP/1.1 request begins with method, request-target and version, followed by header fields, a blank line, and an optional body. For example, GET /courses?id=7 HTTP/1.1 followed by Host: example.edu and a terminating blank line can have no body. A response begins with version, status code and optional reason phrase, then headers, blank line and permitted content. Request lines are not response status lines.
    • HTTP representation, framing and state
      • Content-Type: representation format
      • Content-Length/transfer framing: message boundaries
      • Stateless request semantics
      • Sessions/databases maintain application state
      • HTTP2/3 encode differently
      • Request-line universality requires HTTP/1.x scope
      • Asynchronous client use still receives responses
      👁 Full explanation
      Content-Type describes representation format; Content-Length or transfer framing establishes message boundaries when applicable. HTTP is stateless in its request semantics, but applications maintain state through sessions/databases. HTTP2/3 encode messages differently, so an “always contains a request line” question needs HTTP/1.x context. Asynchronous use is a client programming choice, not proof that HTTP has no responses.

  • WEB04

    Methods, status and GET/POST reasoning

    [Exam Focus]
    • HTTP methods and intended effects
      • GET: safe representation retrieval
      • Intentional state changes: avoid GET links
      • POST: process supplied content
      • PUT: create/replace identified representation
      • DELETE: remove resource association
      • Safe: intended state effects
      • Idempotent: repeated same intended effect
      • Same response not required
      • GET/PUT/DELETE idempotent; arbitrary POST not
      👁 Full explanation
      GET retrieves a representation with safe semantics; do not implement an intentional state-changing action as a GET link. POST asks the target to process supplied content. PUT creates/replaces the identified resource representation; DELETE requests removal of its association. Safe describes intended state effects; idempotent means repeating the same request has the same intended effect, not necessarily the same response. GET/PUT/DELETE are idempotent; arbitrary POST is not.
    • Status codes and form transport
      • 200 success; 201 creation; 204 no-content
      • 301 permanent redirect; 400 malformed request
      • 401 missing/invalid authentication; 403 refusal
      • 404 unavailable/not found; 500 unexpected failure
      • GET forms: URL query name/value pairs
      • POST forms: body name/value pairs
      • Neither method encrypts
      • POST body visible in developer tools
      • Server/configuration imposes size limits
      👁 Full explanation
      200 indicates success, 201 creation, 204 success without content, 301 permanent redirection, 400 malformed request, 401 missing/invalid authentication, 403 refusal, 404 unavailable/not found, and 500 an unexpected server failure. GET forms usually put name/value pairs in the URL query; POST forms put them in the body. Neither method encrypts data. POST bodies are visible to developer tools and subject to server/configured size limits.

    [Exam Focus]

Represent errors consistently and evaluate retry safety before repeating a request. Store durable application facts server-side; stateless API requests can still operate on persistent database state.

  • WEB06

    HTML document, text and metadata

    [Exam Focus]
    • HTML document structure and metadata
      • HyperText Markup Language
      • <!DOCTYPE html>: modern standards mode
      • html root; head metadata; body content
      • title: page/tab title

      👁 Full explanation
      HTML means HyperText Markup Language. <!DOCTYPE html> selects modern standards mode; <html> is the document root, <head> holds metadata, and <body> contains document content. <title> supplies the page/tab title.       • Tags: boundaries; element: content/attributes

      👁 Full explanation
      <p> marks paragraphs; <br> is a line break and <hr> a thematic break. <pre> preserves source whitespace; <code> marks code. <strong> indicates importance and <em> stress; <b>/<i> have other text semantics and are not identical to importance/emphasis. <sub>/<sup> mark sub/superscripts. <!-- comment --> is not displayed but remains visible in source. Entities include &copy;, &lt;, &gt; and &amp;. Tags mark boundaries; an element includes content and attributes, or is a void element such as img.

Width/height reserve dimensions; title is not a replacement for alt. An anchor may wrap an image. Give controls programmatic labels, clear link text and keyboard access; visual styling alone does not establish accessibility. Attributes belong in opening tags, with unique IDs when used for document identification.

    CSS attachment and selector meaning

    • CSS attachment and syntax
      • External: link rel="stylesheet" href="styles.css"
      • External link in head
      • Internal: style; inline: style attribute
      • External reuse, consistency, caching
      • No universal smaller-page/accessibility guarantee

  • WEB12

    Resolve cascade, specificity and inheritance

    [Exam Focus]
    • Cascade winner procedure
      • Origin, importance, layer context first
      • Then specificity and source order
      • Same-origin/layer author context assumed
      • ID>class/attribute/pseudo-class>type/pseudo-element
      • Counts compared lexicographically
      • Not unlimited base-ten total
      • Equal specificity: later applicable rule
      • Important beats normal within relevant context
      👁 Full explanation
      First compare applicable declarations in their cascade origin, importance and layer context; then compare specificity and order within the relevant context. In an ordinary same-origin/same-layer author example, an ID outweighs class/attribute/pseudo-class selectors, which outweigh type/pseudo-element selectors. Compare counts lexicographically, not as an unlimited base-ten total. Equally specific applicable rules use later source order. An important declaration outranks a competing normal declaration in that context.
    • Specificity, importance and inheritance
      • p#intro.note example
      • #intro blue beats .note red
      • p green!important beats both normal rules
      • Inherited color/fonts: no stronger specified value
      • Margin/padding/border normally not inherited
      • :not(): argument specificity
      • Module universal-zero simplification incorrect
      👁 Full explanation
      For <p id="intro" class="note">, #intro{color:blue} beats .note{color:red}. A competing p{color:green!important} beats those normal declarations. Inherited color/fonts apply when the element lacks a stronger specified value; margin/padding/borders do not normally inherit. :not() contributes the specificity of its argument rather than universally zero, correcting the module simplification.

  • WEB14

    Layout, alignment and responsive design

    [Exam Focus]
    • Flow, flex, grid and alignment
      • Normal flow: blocks/inlines
      • Flexbox: direct children, main axis
      • justify-content: main; align-items: cross
      • Horizontal row: vertical cross-axis alignment
      • Grid: explicit rows and columns
      • grid-template-columns:1fr 2fr
      • vertical-align: inline/table-cell contexts
      • vertical-align ≠ universal block centering
      • align-content: extra-space track/line distribution
      • align-content ≠ arbitrary single-child centering
      👁 Full explanation
      Normal flow lays out blocks/inlines. Flexbox arranges direct children on a main axis; justify-content follows that axis, align-items the cross axis. With row direction in ordinary horizontal writing, cross-axis alignment is vertical. Grid organizes rows and columns with explicit tracks, such as grid-template-columns:1fr 2fr. vertical-align applies to inline/table-cell contexts and does not center every block. align-content distributes tracks/lines when there is applicable extra space, not arbitrary single-child centering.
    • Positioning and responsive design
      • Relative: offset, retained flow space
      • Absolute: removed from flow, containing block
      • Positioned ancestor often establishes containing block
      • Fixed: commonly viewport
      • Flexible layout/images; viewport metadata; media queries
      • @media(max-width:600px){.cards{grid-template-columns:1fr}}
      • min-width768px: wider viewports, not mobile-only
      • Compatibility: feature tests and fallbacks
      • Compatibility ≠ responsive size handling
      👁 Full explanation
      Relative positioning offsets a box while retaining its flow space; absolute removes it and uses its containing block, often established by a positioned ancestor; fixed commonly uses the viewport. Responsive design combines flexible layout, images, viewport metadata and media queries, for example @media(max-width:600px){.cards{grid-template-columns:1fr}}. A min-width768px query targets wider viewports, not mobile alone. Browser compatibility requires feature testing and fallbacks; responsive size handling is a different issue.

  • WEB15

    JavaScript syntax, inclusion and declarations

    • JavaScript inclusion and language identity
      • External .js: <script src="app.js"></script>
      • JavaScript source: no HTML closing-tag syntax
      • defer: after parsing, before DOMContentLoaded
      • Originated at Netscape; distinct from Java
      • Prototype-based objects; first-class functions
      • Sophisticated applications supported
      👁 Full explanation
      Use <script src="app.js"></script> for an external .js file; script content has no HTML closing-tag syntax inside its JavaScript source. A deferred script runs after parsing and before DOMContentLoaded. JavaScript originated at Netscape; it is distinct from Java and supports sophisticated applications through prototype-based objects and first-class functions.
    • JavaScript lexical and declaration rules
      • Case-sensitive identifiers
      • Initial letter/underscore/$; no digits/spaces
      • var: function/global scope
      • let/const: block scope
      • const: no rebinding, object mutation allowed
      • // line comments; /* */ blocks
      • Semicolons and automatic insertion
      • Newlines can affect parsing after return
      • "use strict": directive string, not keyword
      • Parse syntax before output computation
      👁 Full explanation
      Identifiers are case-sensitive and may start with letters, underscore or $, not digits or spaces. var has function/global scope; let/const are block-scoped. const prevents rebinding but not mutation of an object’s contents. // comments end at line end; /* */ span a block. Semicolons delimit statements, although automatic insertion exists. Whitespace usually separates tokens but newlines can affect parsing, especially after return. “use strict” is a directive string, not a reserved statement keyword. Parse syntax before computing outputs.
