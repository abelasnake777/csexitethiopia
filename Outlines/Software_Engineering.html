  • SE01

    Engineering processes and work products

    [Exam Focus]
    • Software engineering and process
      • Systematic development, operation, maintenance
      • Product: executable code plus artifacts
      • Requirements, designs, test assets
      • Configuration and user documentation
      • Process: activities, ordering, roles, products
      • Entry/exit conditions
      • Specification → design/implementation → validation → evolution
      👁 Full explanation
      Software engineering applies systematic methods to development, operation and maintenance. A software product includes executable code and relevant requirements, designs, test assets, configuration and user documentation. A process defines activities, ordering, roles, products and entry/exit conditions. Its four broad activities are specification, design/implementation, validation and evolution.
    • Decomposition and programming approaches
      • Procedural: functions
      • Object oriented: state/behavior objects
      • Either iterative or sequential
      • OOP doesn't guarantee shorter projects
      • Reuse, encapsulation, consistent models
      • Reduced duplication, easier change
      • Poor object design still complex
      • Functional: function evaluation, controlled side effects
      • Event-driven: reacts to events
      👁 Full explanation
      Procedural decomposition organizes functions; object oriented decomposition organizes objects with state and behavior. Either can use iterative or sequential development. OOP does not automatically shorten every project. Reuse, encapsulation and consistent models can reduce duplication and ease change; poor object design can still be complex. Functional programming emphasizes function evaluation and controlled side effects; event-driven programs react to events.

  • SE02

    Lifecycle and process selection

    [Exam Focus]
    • Lifecycle phases and design levels
      • Requirements → design → implementation → testing
      • Deployment → maintenance
      • Analysis: clarify problem
      • System design: architecture
      • Object/detail design: interfaces, algorithms
      • Implementation: code
      • Testing: behavior evaluation
      • Deployment: into service
      • Activities overlap and repeat
      👁 Full explanation
      A common lifecycle names requirements, design, implementation, testing, deployment and maintenance. Analysis clarifies the problem; system design chooses architecture; object/detail design specifies interfaces and algorithms; implementation writes code; testing evaluates behavior; deployment puts it into service. These activities may overlap and repeat.
    • Contextual process selection
      • Requirement stability and technical risk
      • Delivery urgency, stakeholder availability
      • Team skills and assurance needs
      • Inexperience alone insufficient
      • Risk-driven cycle, prototype, planned stages
      • Choice depends on actual uncertainty
      • Testing/documentation required in every process
      👁 Full explanation
      Select a process using requirement stability, technical risk, delivery urgency, stakeholder availability, team skills and assurance needs. “Team has little experience” alone does not uniquely identify a process. A risk-driven cycle, prototype or carefully planned staged process may each help, depending on the actual uncertainty. No process eliminates the need for testing or documentation.

  • SE03

    Waterfall and V-model

    • Classical and modified waterfall
      • Planned phases, reviewed deliverables
      • Stable understood requirements, familiar technology
      • Late feedback raises change cost
      • Controlled revisiting remains possible
      • Modified waterfall: explicit feedback
      • Milestone visibility
      • Risk of frozen incorrect assumptions
      👁 Full explanation
      Classical waterfall separates planned phases with reviewed deliverables. It fits well-understood, stable requirements and familiar technology; late feedback makes changes costly. It does not make change physically impossible: real projects revisit work under control, and modified waterfall explicitly includes feedback. Rigidity offers milestone visibility but can freeze incorrect assumptions.
    • V-model stage/test pairing
      • Requirements → acceptance tests
      • System design → system tests
      • Component/detail design → integration/unit tests
      • Coding at bottom
      • Early test planning
      • Stable requirements, strong assurance fit
      • Shape/process guarantees neither safety nor correctness
      👁 Full explanation
      The V-model pairs specification/design stages with later test levels. Requirements inform acceptance tests; system design informs system tests; component/detail design informs integration/unit tests. Coding lies at the bottom. Test planning starts early. Stable requirements and strong assurance may favor this organization, but neither a V shape nor waterfall guarantees safety or correctness.

  • SE04

    Iteration and incremental delivery

    • Iteration versus increment
      • Iteration: revisit and improve
      • Increment: add usable functionality
      • Processes may combine both
      • Registration → payments → reporting: incremental
      • Registration-prototype feedback revisions: iterative
      • Each increment: design, implement, test
      👁 Full explanation
      Iteration revisits and improves a solution; an increment adds usable functionality. A process may do both. Delivering registration first, then payments, then reporting is incremental; revising a registration prototype after feedback is iterative. Each increment still needs design, implementation and testing.
    • Incremental-delivery benefits and limits
      • Prioritized partial capability delivered early
      • Smaller changes: easier debugging, feedback
      • Architecture/integration still planned
      • Iteration needn't rebuild whole system
      • Increments needn't be independent modules
      • Early version: prototype/iterative/Agile possibilities
      • Purpose determines classification
      👁 Full explanation
      Choose incremental delivery when prioritized partial capability must reach users early. Smaller changes can be easier to debug and permit feedback, though architecture and integration still require planning. Iteration need not rebuild the whole system every time, and increments need not be perfectly independent modules. Broad descriptions of early working software can fit prototypes, iterative or Agile processes; identify the purpose of that early version.

  • SE05

    Agile values and Scrum

    • Agile values and work descriptions
      • People/collaboration over rigid procedures
      • Working results over exhaustive documents
      • Customer participation over contracts
      • Adaptation over fixed plans
      • Right-hand values still matter
      • Planning/documentation still needed
      • User story: small need and value
      • Acceptance criteria support story
      • Epic: broader work grouping
      👁 Full explanation
      Agile favors people collaborating, useful working results, customer participation and adaptation over rigid adherence to procedures, exhaustive documents, contracts or fixed plans. The latter still have value. Agile does not mean no planning or no documentation. A user story states a small user need and value, supported by acceptance criteria; an epic groups broader work.
    • Scrum timeboxes and assurance
      • Sprints: at most one month
      • Sprint Goal, selected work, usable Increment
      • Increment meets Definition of Done
      • Scope discussion before/during planning allowed
      • Fixed timebox, adapted content
      • Sprint Goal protected
      • Agile with assurance/documentation possible
      • Safety-critical alone doesn't prove unsuitability
      👁 Full explanation
      Scrum uses timeboxed Sprints of at most one month, with a Sprint Goal, selected work and a usable Increment meeting a Definition of Done. Scope is discussed before and during planning; it is not forbidden to agree scope. Timeboxes tend to stay fixed while content is adapted without endangering the goal. Agile can be combined with required assurance/documentation; safety-critical context alone cannot prove it is unsuitable.

  • SE06

    Spiral development and risk

    • Risk-driven spiral cycle
      • Objectives and alternatives
      • Assess/reduce important risks
      • Develop/verify appropriate next result
      • Plan further commitment
      • Prototype risky technology before large investment
      • Risk determines work amount/type
      👁 Full explanation
      Spiral development is risk driven. Each cycle identifies objectives and alternatives, assesses and reduces important risks, develops/verifies an appropriate next result, and plans further commitment. A prototype may test a risky technology before a large investment. The amount and type of work depend on the risks.
    • Spiral selection and limitations
      • Risk emphasis distinguishes spiral
      • Changing requirements alone insufficient
      • Incremental/prototyping/sequential activities incorporable
      • Uniquely most-general: textbook convention
      • Not universal theorem
      • Risk analysis needs skill
      • Low-risk small projects: excessive overhead possible
      👁 Full explanation
      Use risk emphasis to distinguish spiral from a generic changing-requirements scenario. Spiral can incorporate incremental, prototyping or sequential activities, but calling it the uniquely “most general” process is a textbook convention rather than a universal theorem. Risk analysis requires skill and may impose excessive overhead on a small low-risk project.

  • SE07

    Prototypes, RAD and reuse

    • Prototyping purpose and lifecycle
      • Requirements, usability, technical feasibility
      • Throwaway: discard after learning
      • Evolutionary: deliberately refine toward production
      • Quick versions may omit robustness/security/architecture
      • Evaluate before unchanged deployment
      • Prototyping may include coding
      • Construction label doesn't exclude coding
      👁 Full explanation
      A prototype explores requirements, usability or technical feasibility. A throwaway prototype is discarded after learning; an evolutionary prototype is deliberately refined toward production. A quick prototype may omit robustness, security or architecture, so do not deploy it unchanged without evaluation. Coding may occur during prototyping even if a diagram labels that activity construction rather than coding.
    • RAD and reuse-oriented development
      • RAD: rapid construction, timeboxing
      • User participation, reusable components
      • Available users, skilled designers/developers
      • Reuse: search components → evaluate fit
      • Possible requirements adjustment
      • Design around interfaces, build gaps
      • Product-line requirements/architecture/components/tests reusable
      👁 Full explanation
      RAD uses rapid construction, timeboxing, user participation and often reusable components; it requires available users and skilled designers/developers. Reuse-oriented development searches components, evaluates fit, may adjust requirements, designs around interfaces and builds missing parts. Product-line assets may include requirements, architecture, components and tests; all are potentially reusable.

  • SE08

    Feasibility and requirement levels

    [Exam Focus]
    • Feasibility versus system analysis
      • Worth doing and deliverable?
      • Technical, economic, operational, schedule constraints
      • Existing limitations, organizational impacts
      • Benefits, cost, available skills
      • Integration risk
      • System analysis: detailed problem/behavior
      • Activities inform each other
      👁 Full explanation
      Feasibility asks whether a proposal is worth doing and can be delivered within technical, economic, operational and schedule constraints. Examine existing limitations, organizational impacts, benefits, cost, available skills and integration risk. System analysis studies the problem and needed behavior in more detail; the activities inform each other.
    • Requirement levels and SRS
      • Business: purpose and goals
      • User: high-level stakeholder needs
      • System: detailed services and constraints
      • Software Requirements Specification: agreed requirements
      • Module natural language: client communication
      • Analysis models: technical formalization
      • Real specifications may include diagrams
      👁 Full explanation
      Business requirements explain why the project exists and its goals. User requirements describe stakeholder needs at a useful high level; system requirements specify detailed services and constraints. The Software Requirements Specification (SRS) organizes the agreed requirements. In the module, a natural-language specification communicates with clients while analysis models formalize it for technical discussion; real specifications can also contain diagrams.

  • SE09

    Functional rules and prohibitions

    [Exam Focus]
    • Functional obligations and prohibitions
      • Observable service or behavior
      • Input/error reactions
      • Forbidden actions included
      • Intrusion sensor → alert
      • Manager-only refund approval: functional
      • Negative statement ≠ automatically nonfunctional
      👁 Full explanation
      A functional requirement states an observable service or behavior, including reactions to inputs, errors and forbidden actions. “When the sensor detects intrusion, send an alert” is functional. “Only a manager may approve refunds” also specifies permitted/prohibited behavior. A negative statement is not automatically nonfunctional.
    • Precise requirement formulation
      • Actor/trigger, action, observable result
      • Generate PDF report: functional
      • No other-customer balance disclosure: functional security
      • Broad security quality versus implementing functions
      • Must/should/not-work wording: classification may remain ambiguous
      👁 Full explanation
      Write one clear obligation with an actor/trigger, action and observable result. “The system shall generate a PDF report” is functional. “The system shall not reveal another customer’s balance” can be a security-related functional rule. Security as a broad quality goal and the functions implementing it must be distinguished. The bank’s must/should/not-work wording often fails to establish a unique classification.

  • SE10

    Nonfunctional qualities and constraints

    [Exam Focus]
    • Nonfunctional attributes and constraints
      • Performance: response time/throughput/resource use
      • Reliability: failure-free service
      • Availability: ready for use
      • Usability: task success/ease of learning
      • Security: protection
      • Compatibility: cooperating environments
      • Portability: moving environments
      • Maintainability/supportability: change, diagnosis, evolution
      👁 Full explanation
      Nonfunctional requirements include quality attributes and constraints. Performance concerns response time, throughput and resource use; reliability concerns failure-free service; availability concerns being ready for use; usability concerns task success and ease of learning. Security concerns protection; compatibility concerns cooperating environments; portability concerns moving environments; maintainability/supportability concern change, diagnosis and evolution.
    • Measurable qualities and classification traps
      • Search ≤2 seconds, 100 concurrent users
      • Performance requirement
      • New-user checkout ≤1 minute, unaided
      • Usability requirement
      • Use Java: technology/pseudo-requirement
      • Often separately classified system constraint
      • Dependability: reliability, safety, robustness
      • Portability not usual central dependability category
      • Peak-load degradation: primarily performance
      • Not automatically reliability
      👁 Full explanation
      “Search responds within two seconds under 100 concurrent users” is measurable performance. “New users finish checkout within one minute without help” is usability. “Use Java” is a technology/pseudo-requirement, often separately classified as a system constraint. Dependability includes reliability, safety and robustness; portability is not its usual central category. Performance degradation at peak load primarily concerns performance, not automatically reliability.

  • SE11

    Requirement quality and traceability

    [Exam Focus]
    • Requirement quality criteria
      • Correct: actual stakeholder needs
      • Complete: agreed scope, normal/exceptional behavior
      • Consistent: no contradictions
      • Clear/unambiguous: one intended interpretation
      • Feasible/realistic: achievable within constraints
      • Verifiable: objective fulfillment evidence
      • Replace vague fast/most users
      • Defined metric, workload, threshold
      👁 Full explanation
      Correct requirements reflect actual stakeholder needs. Complete requirements address the agreed scope, normal and exceptional behavior. Consistency excludes contradictions. Clarity/unambiguity gives one intended interpretation; feasibility/realism means achievable within constraints. Verifiability means objective evidence can check fulfillment. Replace “fast for most users” with a defined metric, workload and threshold.
    • Traceability and conflict negotiation
      • Backward: source/rationale
      • Forward: design, code, tests
      • Requirement dependencies recorded
      • Traceability matrix links artifacts
      • Impact analysis support
      • Not merely cost/schedule ledger
      • Negotiate incompatible stakeholder demands
      • Independent incompatible approvals insufficient
      • Elicitation difficulties: scope, understanding, volatility
      👁 Full explanation
      Trace each requirement backward to its source/rationale and forward to design, code and tests. Record dependencies among requirements. A traceability matrix links these artifacts and helps impact analysis; it is not just a cost/schedule ledger. Stakeholders must negotiate conflicting requirements rather than independently approving incompatible demands. Scope, understanding and volatility are distinct elicitation difficulties.

  • SE12

    Elicitation, FAST and QFD

    [Exam Focus]
    • Elicitation techniques
      • Interviews: stakeholder needs
      • Document analysis: manuals, contracts, records
      • Observation/ethnography: actual daily work
      • Prototypes: tacit expectations
      • Workshops/JAD: users, managers, developers
      • Facilitator and recorder
      • Consensus-building
      • Multiple sources, observed-work assumption checks
      👁 Full explanation
      Interviews ask stakeholders about needs; document analysis examines manuals, contracts and current records; observation/ethnography studies actual daily work. Prototypes reveal tacit expectations. Workshops/JAD bring users, managers and developers together with a facilitator and recorder to build consensus. Use several sources and check assumptions against observed work.
    • FAST, QFD and brainstorming
      • FAST: environment elements, outputs, inputs lists
      • Consolidate lists → smaller specifications
      • QFD: customer-value prioritization
      • Normal needs: explicit
      • Expected needs: assumed
      • Exciting needs: unanticipated benefit
      • Brainstorm ideas before evaluation/prioritization
      • Not every idea becomes committed requirement
      👁 Full explanation
      In the taught FAST technique, participants list environment elements, outputs and inputs, consolidate lists and develop smaller specifications. QFD prioritizes customer value: normal needs are explicitly stated, expected needs are assumed, and exciting needs provide unanticipated benefit. Brainstorm first to generate ideas, then evaluate and prioritize; do not confuse that with letting every idea become a committed requirement.

  • SE13

    Scenarios and analysis objects

    [Exam Focus]
    • Scenarios, models and analysis objects
      • Scenario: one concrete execution
      • Use case: related success/alternative scenarios
      • Functional model: use cases/scenarios
      • Structural/object model: classes
      • Dynamic model: states/interactions
      • Entity: domain information, Incident
      • Boundary: interaction mediation, ReportForm
      • Control: use-case coordination
      • UI form normally boundary, not entity
      👁 Full explanation
      A scenario is one concrete execution; a use case abstracts the related successful and alternative scenarios. Analysis integrates functional (use cases/scenarios), structural/object (classes) and dynamic (states/interactions) models. Entity objects represent domain information such as Incident; boundary objects mediate interaction, such as ReportForm; control objects coordinate a use case. A UI form is normally boundary, not entity.
    • Object identification and CRC
      • Nouns → candidate objects
      • Possessives → candidate attributes
      • Verbs manages/reports-to → candidate associations
      • Heuristics, not automatic parsing rules
      • CRC: Class, Responsibilities, Collaborators
      • Control per use-case/actor: starting heuristic
      • Not mandatory UML rule/fixed lifetime
      👁 Full explanation
      Use nouns as candidate objects, possessive descriptions as candidate attributes, and verbs such as manages/reports-to as candidate associations. These are heuristics, not automatic parsing rules. CRC means Class, Responsibilities, Collaborators. A control per use case or participating actor can be a useful starting point, not a mandatory UML rule or fixed object lifetime.

  • SE15

    Use-case flows and guarantees

    [Exam Focus]
    • Complete use-case specification
      • Name/goal, actors, trigger
      • Preconditions
      • Main success flow
      • Alternatives/exceptions
      • Postconditions
      • Active subject–verb steps
      • Consistent abstraction level
      • Errors separated from normal flow
      👁 Full explanation
      Record name/goal, actors, trigger, preconditions, main success flow, alternatives/exceptions and postconditions. Use active subject–verb steps at one abstraction level; separate errors from the normal flow.
    • Submit Incident scenario
      • Precondition: authenticated officer
      • Officer supplies location/description
      • System validates → records → returns ID
      • Missing location: problem and correction request
      • Failure: save nothing
      • Success: incident and ID persist
      • Failure guarantee: no partial record
      • Alternate flow: conditional variation
      • Exception flow: failure
      • Preconditions before entry, trigger starts execution
      👁 Full explanation
      Example: Submit Incident. Precondition: officer authenticated. 1 Officer supplies location and description. 2 System validates details. 3 System records the incident. 4 System returns its ID. Alternative 2a: location missing → report the problem and request correction; save nothing. Success postcondition: incident and ID persist; failure guarantee: no partial record. An alternate flow is a conditional variation; an exception flow handles a failure. Preconditions hold before entry, while a trigger starts the use case.

  • SE16

    Include, extend and generalization

    [Exam Focus]
    • Include versus extend
      • Include: required reused behavior
      • Submit Order includes Validate Order
      • Dashed include arrow: base → included
      • Extend: conditional extension-point behavior
      • Apply Discount extends Checkout
      • Extend arrow: extension → base
      • Base meaningful independently
      • Withdrawal extends Print Receipt: reversed example
      👁 Full explanation
      Include factors required reused behavior: Submit Order includes Validate Order, with the dashed arrow from the including/base use case to the included one. Extend adds conditional behavior at extension points: Apply Discount extends Checkout, with the arrow from the extension to the base. The base is meaningful independently. The short note’s receipt example reverses this direction if it says Withdrawal extends Print Receipt.
    • Generalization and abstract use cases
      • Specialized actor/use case → general
      • Hollow triangle toward general
      • Abstract: behavior for specialization
      • Not directly instantiated complete use case
      • Reuse alone insufficient definition
      • No direct actor line insufficient definition
      • Included behavior executes when inclusion reached
      • Base conditional branches not necessarily all executed
      👁 Full explanation
      Generalization relates a specialized actor/use case to a more general one, with a hollow triangle toward the general element. An abstract use case specifies behavior for specialization and is not directly instantiated as a complete use case. It is not defined merely by reuse or lack of a direct actor line. Included behavior is incorporated where the inclusion is reached; do not infer every conditional branch in the base always executes.

  • SE17

    UML classes and multiplicity

    [Exam Focus]
    • Class diagrams and UML
      • Class name, attributes, operations
      • + public, - private, # protected
      • ~ package visibility
      • Class diagram: static types/relationships
      • Object diagram: particular instances/links
      • OMG maintains/standardizes UML
      • Modeling language, not lifecycle process
      • Structural things: conceptual/physical structural elements
      👁 Full explanation
      A class box lists name, attributes and operations; + public, - private, # protected and ~ package indicate visibility. A class diagram shows static types and relationships, while an object diagram shows particular instances/links. UML is maintained and standardized by OMG; it is a modeling language, not a lifecycle process. Structural things describe conceptual or physical structural elements.
    • Multiplicity interpretation
      • One end: objects per opposite-end object
      • 1: exactly one
      • 0..1: optional
      • 0..*: any nonnegative number
      • 1..*: at least one
      • Read each end separately
      • One-to-many doesn't imply composition
      👁 Full explanation
      Multiplicity at one end counts how many objects there may correspond to one object at the opposite end: 1 exactly one, 0..1 optional, 0..* any nonnegative number, 1..* at least one. A one-to-many association does not automatically mean composition. Read each end separately before choosing cardinality.

  • SE18

    Association, aggregation and composition

    • Association, dependency and aggregation
      • Association: related instances
      • Dashed dependency: client uses supplier
      • Generalization: solid line, hollow triangle
      • Triangle toward superclass/general element
      • Shared aggregation: hollow diamond
      • Diamond at whole end
      • Weak whole-part meaning
      • No detailed lifecycle policy implied
      👁 Full explanation
      Association connects related instances. A dashed dependency arrow means a client uses a supplier. Generalization uses a solid line and hollow triangle pointing to the superclass/general element. Shared aggregation uses a hollow diamond at the whole end and weak whole-part meaning; it does not by itself define a detailed lifecycle policy.
    • Composition ownership and diamond placement
      • Filled diamond at whole end
      • At most one composite per part
      • Owned parts destroyed with composite
      • Defined detachment/transfer possible
      • Never-independent claim oversimplified
      • Car composing Engine: diamond beside Car
      • Points-to-Engine wording imprecise
      • Bank intended relationship: composition
      👁 Full explanation
      Composition uses a filled diamond at the whole end and strong ownership: a part is in at most one composite at a time, and parts still owned are destroyed with that composite. Parts may be detached/transferred under a defined model. Thus “cannot ever exist independently” is an oversimplification. For Car composing Engine, the diamond belongs beside Car; saying it points to Engine is imprecise. The intended bank relationship is composition.

    Sequence diagrams and emergency reporting

      • EF=ES+duration

    Statement, decision and branch coverage

    • Structural coverage and limitations
      • Statement coverage=distinct exercised statements/total executable statements
      • Declared test scope determines denominator
      • Unreachable statements can prevent 100%
      • Document justified exclusions/adjusted scope
      • Decision coverage: decision outcomes
      • Branch coverage: control-flow edges
      • Unconditional edges under stated convention
      • Nested decisions may need >2 tests
      • Exercised structure ≠ behavioral proof
      👁 Full explanation
      Statement coverage is the number of distinct executable statements exercised divided by the total executable statements in the declared test scope. Unreachable statements can prevent100%; any justified exclusions must be documented with the adjusted scope. Decision coverage counts decision outcomes; branch coverage counts control-flow edges, including unconditional edges under the stated convention. Testing both true and false of each decision may need more than two overall test cases when branches nest. Coverage is evidence of exercised structure, not proof of all behavior.

      • Outer true: inner true and false

      • Four tests required

      • All paths may be infeasible
      • Loops may create infinite paths
      • State chosen coverage target

    Design trade-offs and economical improvement

    • Goal-based design trade-offs
      • Fine-grained self-contained components
      • Producer/consumer separation
      • Limited shared mutable data
      • Often improve maintainability
      • Interfaces may add latency
      • Isolation may complicate transactions
      • Global state: local simplicity, wider coupling
      • Measurable quality scenarios
      • Component counts alone insufficient
      👁 Full explanation
      Choose designs by their effect on stated goals. Fine-grained self-contained components, separation of producers/consumers and limited shared mutable data often improve maintainability. Trade-offs remain: interfaces can add latency, isolation can complicate transactions, and global state can simplify one operation while coupling many others. Prefer measurable quality scenarios to counting components alone.
    • Pareto and economical improvement
      • 80/20: prioritization heuristic
      • Few causes may dominate observed impact
      • No exact 80%-defects/20%-effort guarantee
      • Refactoring: behavior preserved, structure improved
      • Optimize against measured needs
      • Record rationale
      • Update traceability/regression evidence after change
      👁 Full explanation
      Pareto’s 80/20 rule is a prioritization heuristic: a small subset of causes may account for much of the observed impact. It does not guarantee 80% of defects can be fixed with exactly 20% effort. Refactor to preserve behavior while improving structure; optimize only against measured needs; record rationale and update traceability and regression evidence after change.
