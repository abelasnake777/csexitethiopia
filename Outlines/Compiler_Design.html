  • COMP01

    Translation, Interpretation and Compilation Timing

    • Compiler translation contract
      • Source → equivalent target representation
      • Defined observable behavior preserved
      • Machine code; assembly; bytecode; source targets
      • Transpiler: source-to-source compiler
      • Language semantics versus unstated programmer intention
      👁 Full explanation
      A compiler translates a source program into an equivalent target representation while preserving defined observable behavior. The target may be machine code, assembly, bytecode or another source language. A transpiler is a source-to-source compiler, not a fundamentally separate noncompiler technology. A compiler preserves language semantics, not the programmer’s unstated intention.
    • Interpretation, AOT and JIT
      • Interpreter: executes program representation
      • Line-at-a-time misconception
      • Bytecode compilation then interpretation/JIT
      • AOT: before execution
      • JIT: during execution, runtime profiles
      • Speed: startup, optimization, workload
      • No universally faster method
      👁 Full explanation
      An interpreter executes a program representation; it need not work one source line at a time. Systems can compile to bytecode and then interpret or JIT-compile it. AOT compilation happens before execution; JIT compilation happens during execution and may use runtime profiles. Neither is universally faster; startup cost, optimization and workload matter.

  • COMP02

    Tools, host, target and incremental work

    • Translation toolchain
      • Preprocessor: inclusion and macros
      • Assembler: assembly → object code
      • Linker: objects and libraries
      • External-symbol resolution and relocation
      • Loader: executable mapping and start
      • Compilation alone ≠ ready executable
      👁 Full explanation
      A preprocessor handles directives such as file inclusion and macros. An assembler translates assembly to object code. A linker combines object files and libraries, resolves external symbols and performs relocation. A loader maps an executable into memory and starts it. Compilation alone does not necessarily produce a ready executable.
    • Host, target and compilation organization
      • Cross-compiler: host differs from target
      • Multiple targets: appropriate backends
      • Retargetable: changeable target descriptions
      • Incremental: affected fragments and dependent units
      • Incremental ≠ changed-line replacement only
      • One/multipass: traversal counts, not targets
      👁 Full explanation
      A cross-compiler runs on a host platform and generates code for a different target. Multiple targets require appropriate backends, not a special definition of cross-compilation. A retargetable compiler supports changing target descriptions. Incremental compilation recompiles affected fragments or dependent units after edits; it is more than literally replacing changed lines. One-pass versus multipass counts traversals, not supported targets.

  • COMP03

    Compiler phases and shared services

    [Exam Focus]
    • Conventional compiler pipeline
      • Lexical → syntax → semantic analysis
      • IR generation → optimization → target generation
      • Scanning: characters → tokens
      • Parsing: structure
      • Semantics: declarations and types
      • Synthesis: implementation code
      • Phase: logical activity
      • Pass: traversal, possibly combined activities
      👁 Full explanation
      The conventional sequence is lexical analysis → syntax analysis → semantic analysis → intermediate-code generation → optimization → target-code generation. Scanning turns characters into tokens; parsing builds structure; semantics checks declarations and types; synthesis produces implementation code. A phase is a logical activity; a pass is a traversal that can combine activities.
    • Compiler organization and services
      • Front end: source-language rules
      • Middle end: IR analysis/transformation
      • Backend: target details
      • Shared symbol tables and error reporting
      • No mandatory seventh final phase
      • Optimization at multiple levels
      • Post-instruction-selection optimization possible
      • Standard six-phase final: code generation
      👁 Full explanation
      The front end handles source-language rules; a middle end analyzes and transforms IR; the backend handles target details. Symbol-table management and error reporting support multiple phases rather than forming one mandatory seventh final phase. Optimization can occur at several levels, including after instruction selection. “Final phase” means code generation in the standard six-phase teaching pipeline.

  • COMP04

    Token, lexeme and pattern

    • Token, lexeme and pattern
      • Token: category plus optional attribute
      • (ID,symbol-entry); (INT_LITERAL,42)
      • Lexeme: actual characters total or 42
      • Pattern: token-class membership specification
      • Scanner output: ordered token stream
      • Unordered-set trap
      👁 Full explanation
      A token is a category with optional attribute, such as (ID, symbol-entry) or (INT_LITERAL,42). A lexeme is the actual character sequence, such as total or 42. A pattern specifies which lexemes belong to a token class. The scanner emits an ordered token stream, not an unordered mathematical set.
    • Token classes and scanner boundaries
      • Keywords; identifiers; literals; operators; punctuation
      • Usually skipped whitespace/comments
      • Retained line/column positions
      • Indentation/newlines may carry tokens
      • Parse trees: parser responsibility
      • Scanning may intern identifier spellings
      • Scope/types: later analysis
      👁 Full explanation
      Keywords, identifiers, literals, operators and punctuation are token classes. Whitespace and comments are usually skipped while line/column positions are retained. In indentation-sensitive or newline-sensitive languages, layout can carry tokens. Parse-tree construction is a parser task; scanning can intern identifier spellings, but declaration scope and types need later analysis.
    • Worked example Five-token declaration
      • int x = 42;
      • keyword; ID; assignment; integer; semicolon
      👁 Full explanationScan a statement
      int x = 42; gives keyword(int), ID(x), assignment(=), integer(42), semicolon(;): five tokens.

  • COMP05

    Regular expressions for lexical structure

    [Exam Focus]
    • Identifier regular expressions
      • Concatenation; alternation r|s
      • Kleene r*: zero-or-more
      • r+: one-or-more
      • Letter(Letter|Digit)*
      • Single letter allowed; leading digit forbidden
      • C-like ASCII underscore convention
      • [A-Za-z_][A-Za-z0-9_]*
      • Language-specific identifier rules
      👁 Full explanation
      Regular expressions use concatenation, alternation r|s, Kleene star r* for zero or more, and r+ for one or more. In a simplified alphabet, identifier = Letter(Letter|Digit)*; it permits a single letter and forbids a leading digit. A C-like ASCII rule commonly also allows underscore: [A-Za-z_][A-Za-z0-9_]* State the convention instead of claiming this covers every language’s identifiers.
    • Equivalent patterns and nesting limits
      • Letter(Letter+|Digit*)* = Letter(Letter|Digit)*
      • Repeated letter/digit blocks
      • Equivalent-option trap
      • Regular patterns: ordinary tokens
      • Arbitrary balanced nesting: grammar/stack
      👁 Full explanation
      Letter(Letter+|Digit*)* denotes the same language as Letter(Letter|Digit)* under ordinary regular-expression semantics: repeated blocks can contain any trailing letter/digit sequence. Thus two such options are equivalent. Regular patterns handle ordinary tokens; arbitrary balanced nesting generally needs grammar/stack structure.

  • COMP06

    Construct and run a scanner automaton

    [Exam Focus]
    • Scanner-generator automata pipeline
      • RE → Thompson NFA → subset DFA
      • Optional minimization
      • Concatenation: final-to-start ε edge
      • Alternation: branching ε paths
      • Star: skip and repetition ε paths
      👁 Full explanation
      A common generator pipeline is regular expressions → NFA using Thompson construction → DFA using subset construction; minimization is optional. For concatenation rs, connect r’s final state to s’s start by ε. Alternation introduces branching ε paths; star adds a way to skip and repeat the fragment.
    • Scanner subset construction
      • ε-closure: zero-or-more ε reachability
      • DFA state: NFA-state set
      • Transition: ε-closure(move(set,a))
      • Start: NFA start closure
      • Repeated unseen-subset discovery
      • Accepting subset contains NFA final
      • Token identity and rule-priority annotations
      • Empty subset: dead state
      👁 Full explanation
      The ε-closure of states includes those reachable by zero or more ε edges. A DFA state is a set of NFA states; its a-transition is ε-closure(move(set,a)). Start with the NFA start closure, repeatedly add unseen subsets, and mark subsets containing an NFA final state as accepting. Token identity and rule priority annotate accepting states; the empty subset acts as a dead state.

  • COMP07

    Longest match and counting tokens

    • Maximal munch and rule priority
      • Longest matching lexeme
      • Equal-length flex matches: earliest rule
      • ifx: identifier, not if+x
      • <= and ++: single operators
      • Identifier recognition then keyword-table lookup
      👁 Full explanation
      At each input position, choose the longest matching lexeme; if equal lengths match multiple flex rules, choose the earliest rule. Thus ifx is an identifier rather than if followed by x; <= and ++ are each one operator token. An implementation may recognize an identifier first and then consult a keyword table.
    • Loop-header token count
      • for (int i = 0; i<=10; i++)
      • for,(,int,i,=,0,;
      • i,<=,10,;,i,++,)
      • Fourteen tokens irrespective of spacing
      • Increment: one token
      • Comments: no ordinary post-preprocessing parser token
      • Choices 4,5,9,10: correct result omitted
      👁 Full explanation
      For the ordinary C++ header: for (int i = 0; i <= 10; i++) The tokens, split into two display lines, are: for, (, int, i, =, 0, ; i, <=, 10, ;, i, ++, ) There are 14 tokens, irrespective of spacing. The increment operator is one token. A comment contributes no ordinary parser token after preprocessing. Bank choices 4,5,9,10 omit the correct count.

  • COMP08

    Locate the error by evidence

    • Compiler-error classification
      • Lexical: no legal token formation
      • Invalid character; unterminated literal
      • Syntax: illegal token arrangement
      • Missing delimiter
      • Semantic: name, scope, type constraints
      • Wrong algorithms may compile
      • All-logical-errors detection trap
      👁 Full explanation
      A lexical error prevents forming a legal token, such as an invalid character or unterminated literal. A syntax error is an illegal token arrangement, such as a missing delimiter. A semantic error violates name, scope or type rules after grammatical recognition. A wrong algorithm can compile successfully; compilers do not detect all logical mistakes.
    • Malformed fro-line diagnosis
      • fro and lowercase o: legal identifiers
      • Misspelled keyword ≠ lexical error
      • Mismatched syntax: definite
      • Undeclared o: possible semantic diagnostic
      • Compiler-dependent recovery order and diagnostics
      • No silent fro→for or o→0 repair
      👁 Full explanation
      In the malformed C line fro ((I = o, I;, fro and lowercase o are legal identifier lexemes. Misspelling for does not turn fro into a lexical error; mismatched syntax is definite, and undeclared o can also produce a semantic diagnostic. Recovery order and exact diagnostics depend on the compiler. Do not silently replace o by 0 or fro by for.

  • COMP09

    CFGs, derivations and trees

    [Exam Focus]
    • CFG vocabulary and derivations
      • G=(N,T,P,S)
      • Nonterminals; terminals; productions; start
      • A→α: one nonterminal rewrite
      • Sentential form: any S-derived string
      • Sentence: terminals only
      • Leftmost/rightmost: corresponding remaining nonterminal
      👁 Full explanation
      A context-free grammar G=(N,T,P,S) has nonterminals N, terminals T, productions P and start S. A production A→α rewrites one nonterminal. A sentential form is any string of terminals/nonterminals derivable from S; a sentence contains only terminals. A leftmost derivation rewrites the leftmost remaining nonterminal; a rightmost one rewrites the rightmost.
    • Parse tree versus AST
      • Parse tree: production structure
      • Root S; internal nonterminals
      • Terminal leaves; optional ε leaves
      • Left-to-right yield: input
      • AST: removed scaffolding and punctuation
      • Operands: leaves; operators: internal nodes
      • Parser may construct either
      👁 Full explanation
      A parse tree shows grammar productions: root S, internal nonterminals, and terminal leaves, with ε sometimes shown for empty productions. Its left-to-right yield is the input. An AST omits grammar scaffolding and punctuation; expression operands are leaves and operators internal nodes. The parser can build either representation, depending on implementation.

  • COMP10

    Ambiguity, precedence and associativity

    [Exam Focus]
    • Grammar ambiguity
      • One terminal string, two parse trees
      • Equivalent: two leftmost derivations
      • Same-tree derivation order insufficient
      • E→E+E|E*E|id
      • id+id*id: alternative grouping
      👁 Full explanation
      A grammar is ambiguous if at least one terminal string has two different parse trees, equivalently two leftmost derivations. Merely changing derivation order on the same tree does not establish ambiguity. E→E+E|E*E|id allows different trees for id+id*id.
    • Precedence, associativity and dangling else
      • E→E+T|T; T→T*F|F; F→(E)|id
      • Multiplication precedence; left association
      • a−b−c: (a−b)−c
      • Dangling else: alternative nested-if attachments
      • Nearest-unmatched-if policy or grammar rewrite
      • Leftmost derivation alone ≠ disambiguation
      👁 Full explanation
      Use E→E+T|T, T→T*F|F, F→(E)|id to give * higher precedence and both operators left associativity. For subtraction, a−b−c then groups (a−b)−c. The dangling-else grammar permits else to attach to either nested if; a nearest-unmatched-if rule or grammar rewrite resolves it. Taking a leftmost derivation by itself does not resolve ambiguous interpretation.

  • COMP11

    Top-down parsing

    [Exam Focus]
    • Top-down parsing
      • Start S → input expansions
      • Usually leftmost derivation
      • Recursive descent: procedure per nonterminal
      • General descent may backtrack
      • Predictive: lookahead choice without backtracking
      • LL(1): Left-to-right, Leftmost, one lookahead
      👁 Full explanation
      Top-down parsing starts with S and expands productions toward the input, usually constructing a leftmost derivation. Recursive descent typically has one procedure per nonterminal. A general recursive-descent implementation can backtrack; a predictive parser chooses a production using lookahead without backtracking. LL(1) scans Left to right, produces a Leftmost derivation and uses one lookahead token.
    • Nonrecursive predictive parsing
      • Explicit grammar-symbol stack
      • Parsing-table consultation
      • Same predictive language class
      • Recursive/table-driven: linear for suitable fixed grammar
      • Names alone do not rank efficiency
      👁 Full explanation
      A nonrecursive predictive parser stores grammar symbols on an explicit stack and consults a table. It is another implementation of predictive parsing, not a wholly different language class. Table-driven and recursive predictive implementations can both be linear for a fixed suitable grammar. Efficiency cannot be ranked from their names alone.

  • COMP12

    Left Recursion and Prefix Factoring

    [Exam Focus]
    • Left-recursion elimination
      • Immediate A→Aα
      • A→Aα|β; β not A-leading
      • A→βA′; A′→αA′|ε
      • Generated language preserved
      • Changed tree shape
      • Semantic actions preserve intended association
      • Indirect cycles through other nonterminals
      • Ordinary predictive descent needs removal
      👁 Full explanation
      Immediate left recursion has A→Aα. For A→Aα|β, where β does not start with A, introduce a new nonterminal A′ and use: A→βA′ A′→αA′|ε This preserves the generated language; tree shape changes, so semantic actions must preserve intended associativity. Indirect left recursion follows a cycle through other nonterminals and also needs removal for ordinary predictive descent.
    • Left factoring and parser suitability
      • A→αβ|αγ ⇒ A→αA′
      • A′→β|γ
      • Common-prefix choice postponed
      • Factoring ≠ guaranteed unambiguity/LL(1)
      • LR handles suitable left recursion
      • Unmodified descent: infinite recursion before input
      👁 Full explanation
      Left factoring rewrites A→αβ|αγ using: A→αA′ A′→β|γ It postpones a choice until after the common prefix. It does not by itself remove ambiguity or guarantee LL(1). LR parsers can handle suitable left-recursive grammars; ordinary unmodified recursive descent can recurse forever before consuming input.

  • COMP13

    Compute FIRST and FOLLOW

    [Exam Focus]
    • FIRST of a sequence
      • Beginning terminals
      • ε when sequence vanishes
      • Add each FIRST excluding ε
      • Continue across nullable symbols
      • ε only if all nullable
      👁 Full explanation
      FIRST(α) contains terminals that can begin strings derived from α, plus ε when α can vanish. For a sequence, add FIRST of each symbol except ε, continue while symbols are nullable, and add ε only if every symbol is nullable.
    • FOLLOW fixed-point computation
      • Next terminals after A
      • End marker $, never ε
      • $∈FOLLOW(S)
      • B→αAβ: FIRST(β)−{ε} into FOLLOW(A)
      • Nullable β: FOLLOW(B) into FOLLOW(A)
      • Repeat until no growth
      👁 Full explanation
      FOLLOW(A) contains possible next terminals after A, plus end marker $ where appropriate; never ε. Put $ in FOLLOW(S). For B→αAβ, add FIRST(β)−{ε} to FOLLOW(A); if β is nullable, add FOLLOW(B). Repeat all rules until no sets grow.
    • Worked example FIRST/FOLLOW worked grammar
      • S→AB; A→a|ε; B→b
      • FIRST(A)={a,ε}
      • FIRST(S)={a,b}
      • FOLLOW(A)={b}
      • FOLLOW(B)={$}
      👁 Full explanationSmall grammar
      S→AB, A→a|ε, B→b gives FIRST(A)={a,ε}, FIRST(S)={a,b}, FOLLOW(A)={b}, FOLLOW(B)={$}.

  • COMP14

    Build and use an LL(1) table

    [Exam Focus]
    • LL(1) table construction
      • A→α entries under FIRST(α) terminals
      • Nullable α: entries under FOLLOW(A)
      • Multiple productions per cell: conflict
      • SELECT=FIRST(α)−{ε}
      • Nullable: add FOLLOW(A)
      • Pairwise disjoint SELECT sets
      • Two nullable alternatives also conflict
      👁 Full explanation
      For every A→α, put it in M[A,a] for each terminal a in FIRST(α). If α is nullable, also enter it under every symbol in FOLLOW(A). More than one production in a cell is a conflict. Pairwise SELECT sets must be disjoint; SELECT(α)=FIRST(α)−{ε}, plus FOLLOW(A) when α is nullable. This also detects two nullable alternatives.
    • Predictive stack trace
      • Initialize $S
      • Terminal match and pop
      • Nonterminal row plus lookahead
      • Push selected RHS reversed
      • ε production: no input consumed
      • Accept: stack/input both $
      • A→a|ε: a-lookahead selects a
      • b∈FOLLOW(A): b-lookahead selects ε
      👁 Full explanation
      Initialize stack with $S. Match and pop terminals; for a nonterminal consult its row and lookahead, then push the chosen RHS in reverse. An ε production consumes no input. Accept when stack and input reach $. For A→a|ε with b∈FOLLOW(A), choose a on lookahead a and ε on b.
    • Exam trap LL(1) conflict traps
      • Useful ambiguous grammars not LL(1)
      • Overlapping FIRST
      • FIRST/FOLLOW conflicts
      • Left recursion
      • A-and-B-only key: insufficient exclusion
      👁 Full explanation
      Ambiguous useful grammars are not LL(1). Overlapping FIRST, FIRST/FOLLOW conflicts and left recursion cannot be dismissed by an “A and B only” key.

  • COMP15

    Bottom-up actions and handles

    [Exam Focus]
    • Bottom-up parsing and handles
      • Input reduced toward S
      • Reverse rightmost derivation
      • Handle: next correct RHS occurrence
      • Context determines valid reduction
      • Arbitrary matching RHS ≠ handle
      👁 Full explanation
      Bottom-up parsing starts from input and reduces toward S, constructing a rightmost derivation in reverse. A handle is a production RHS occurrence whose reduction is the next step of that reverse derivation. Not every substring matching a RHS is a handle in the current context.
    • Shift-reduce actions and GOTO
      • Shift: next token and state
      • Reduce: RHS → LHS, then GOTO
      • Accept: complete; error: invalid situation
      • A→XYZ: pop three symbols/states
      • Exposed q → push A,GOTO[q,A]
      • Go ≠ separate standard ACTION
      • GOTO: essential table machinery
      👁 Full explanation
      Shift pushes the next input token and a state; reduce replaces a recognized RHS by its LHS and consults GOTO; accept recognizes completion; error reports an invalid situation. For A→XYZ, pop three grammar symbols and their states, expose state q, then push A and GOTO[q,A]. “Go” is not a separate standard shift-reduce ACTION, although GOTO is essential table machinery.

  • COMP16

    Construct LR(0) item states

    [Exam Focus]
    • LR(0) augmentation and closure
      • S′→S
      • Item A→α·β: production progress
      • Dot before B triggers B→·γ
      • Repeat CLOSURE additions
      👁 Full explanation
      Augment the grammar with S′→S. An LR(0) item A→α·β records progress through a production. CLOSURE(I) repeatedly adds B→·γ whenever an item has its dot before nonterminal B and B→γ is a production.
    • LR(0) canonical collection
      • GOTO(I,X): advance dots, take closure
      • Initial CLOSURE({S′→·S})
      • Nonempty GOTOs for all grammar symbols
      • Iterate until no new states
      • Canonical collection: item-set collection
      • GOTO alone ≠ canonical collection
      👁 Full explanation
      GOTO(I,X) moves the dot past X in every eligible item and takes closure. Start with CLOSURE({S′→·S}); repeatedly compute nonempty GOTO sets for all grammar symbols until no new state appears. The resulting set of item sets is the canonical collection, not GOTO itself.
    • Worked example LR(0) state example
      • S→a
      • I0={S′→·S,S→·a}
      • GOTO(I0,a)={S→a·}
      • GOTO(I0,S)={S′→S·}
      • Complete item set: one state
      • One-state-per-item trap
      👁 Full explanationOne transition
      For S→a, call the initial closure I0: I0 = {S′→·S, S→·a} GOTO(I0,a) = {S→a·} GOTO(I0,S) = {S′→S·} Each complete set above is one state, not one state per item.

  • COMP17

    LR families and conflicts

    [Exam Focus]
    • LR parser families
      • SLR(1): LR(0) states, FOLLOW reductions
      • Canonical LR(1): context-specific item lookaheads
      • LALR(1): merge equal LR(0) cores
      • Combined lookaheads
      • Merging may introduce reduce/reduce conflicts
      • LR(0)⊆SLR(1)⊆LALR(1)⊆LR(1)
      • Increasing capability, often larger tables
      👁 Full explanation
      SLR(1) uses LR(0) states and FOLLOW(A) for reduction by a completed A production. Canonical LR(1) attaches context-specific lookahead to items. LALR(1) merges canonical states with the same LR(0) core, combining lookaheads; merging can introduce reduce/reduce conflicts. The standard grammar-class hierarchy is LR(0)⊆SLR(1)⊆LALR(1)⊆LR(1), with increasing capability and often table size.
    • Parser conflicts and limits
      • Shift/reduce: consume or reduce
      • Reduce/reduce: two reductions
      • SLR/LALR conflict ≠ ambiguity proof
      • LR(1) handles LR(1) grammars
      • Not every unambiguous CFG
      • Suitable expression conflicts: precedence/associativity
      • Parser renaming ≠ universal ambiguity repair
      👁 Full explanation
      A shift/reduce conflict offers both consuming a token and reducing; reduce/reduce offers two reductions. An SLR or LALR conflict does not by itself prove the grammar ambiguous. Canonical LR(1) handles LR(1) grammars, not every unambiguous CFG. Precedence and associativity can resolve suitable expression conflicts; changing parser names alone does not repair all ambiguity.

    Parser limits and operator grammars

    [Exam Focus]
    • Nesting and deterministic parser limits
      • LL; LR; recursive descent: suitable nesting
      • Explicit/implicit stack supports unbounded nesting
      • LL and LR: tables possible
      • Deterministic LL/LR: unambiguous grammars
      • Ambiguous grammar: rewrite or disambiguation

      • Not every allocation algorithm NP-complete

      👁 Full explanation

Restricted interference graphs or SSA formulations can have different properties. Do not describe every possible register-allocation algorithm as NP-complete merely because a general model is difficult.

    [Exam Focus]
    • Runtime storage and frames
      • Static: entire execution lifetime
      • Stack: nested calls and recursion
      • Heap: beyond-call lifetimes

  • COMP38

    Inlining and dynamic dispatch

    [Exam Focus]
    • Inlining benefits and limits
      • Suitably renamed function-body copy
      • Preserved argument evaluation, returns, side effects
      • Reduced call overhead
      • Exposed optimization opportunities
      • Increased code size/cache pressure
      • Recursive expansion cannot be unlimited
      👁 Full explanation
      Inlining replaces a call with a suitably renamed copy of its body, preserving argument evaluation, returns and side effects. It can remove call overhead and expose optimization opportunities, but may increase code size and instruction-cache pressure. A recursive function cannot simply be expanded without limit.
    • Dynamic dispatch and devirtualization
      • Overridden method: receiver runtime class
      • Common per-class virtual-method table
      • Object pointer to table
      • Load selected entry
      • Implementation strategy, not universal requirement
      • Name mangling: linker-symbol distinctions/overloads
      • Mangling ≠ runtime method selection
      • Proven receiver type: devirtualization
      👁 Full explanation
      Virtual dispatch chooses an overridden method based on a receiver’s runtime class. A common implementation uses a per-class virtual-method table and an object pointer to the table; the call loads the selected entry. This is an implementation strategy, not a universal language requirement. Name mangling distinguishes linker symbols, often for overloads; it is not itself runtime method selection. Proven receiver types may permit devirtualization.

    Recovery and compiler-construction tools

    • Error recovery methods
      • Panic mode: skip to synchronizing token
      • Semicolon or closing brace
      • Phrase-level: local insertion/deletion
      • Location and cause reporting
      • Avoid diagnostic cascades
      • Lexical, syntax, semantic error detection
      • Error handling: shared service
      👁 Full explanation

Scanner generation does not replace the CFG parser.

    Overlapping Parser Choices

    • Overlapping parser choices
      • Shift-reduce and LR: both bottom-up
      • Negative top-down question: multiple answers
      • Recursive/nonrecursive predictive: both potentially efficient
      • Nesting/tables: not uniquely LR
      • LR choice ≠ ambiguity removal
