Fault management restores failures; performance management measures service behavior; configuration management tracks settings; security management controls access; accounting tracks usage.

  • NSA02

    Network foundations for administrators

    • Client/server and peer roles
      • Client: requests; server: provides
      • Peer-to-peer: both roles
      • Server may request DNS/backups
      • Dedicated server ≠ never client
      • Network OS ≠ dedicated-server-only
      • Clients require networking support
      • Centralized service software versus participant OS
      👁 Full explanation
      Clients request services; servers provide them. Peer-to-peer systems can do both. A server can also be a client of DNS or backups, so dedicated role does not mean it never makes requests. A network OS is not universally installed only on a dedicated server: clients also require networking support. Specify centralized service software versus the OS on all participants.
    • Forwarding, transport and diagrams
      • Switching: LAN frames by MAC
      • Routing: inter-network IP packets
      • TCP: ordered reliable byte stream
      • UDP: datagrams, no equivalent guarantee
      • Ports: application endpoints, not connectors
      • Diagram switches, links, subnets, gateways
      • Service hosts and dependencies
      • Topology shape ≠ security guarantee
      👁 Full explanation
      Switching normally forwards frames using MAC addresses within a LAN; routing forwards IP packets between networks. TCP supplies an ordered reliable byte stream, while UDP preserves datagrams without that guarantee. Ports distinguish application endpoints, not physical connectors. Draw switches, links, subnets, gateways, service hosts and dependencies in a network diagram. A topology’s shape alone does not guarantee security.

  • NSA03

    Addresses, prefixes, gateways and loopback

    • IPv4 addressing rules
      • IPv4: 32 bits
      • CIDR prefix determines network
      • Network=address AND mask
      • Remote subnet: route/gateway
      • Private: 10/8,172.16/12,192.168/16
      • Private ≠ directly Internet-routable
      • IP/class label alone ≠ subnet
      👁 Full explanation
      An IPv4 address is 32 bits; a CIDR prefix determines its network. Compute network=address AND mask; devices use a route/gateway for remote subnets. Private ranges are 10/8,172.16/12 and 192.168/16; private addresses are not directly Internet-routable. Neither IP alone nor a class label determines today’s subnet.
    • Loopback meaning and test limits
      • 127.0.0.1: conventional local IPv4 loopback
      • 127/8 reserved
      • Tests local protocol processing
      • No cable/switch/remote reachability proof
      • Local service use
      • Multiple loopback descriptions may fit
      • Multiple 127/8 choices may fit
      👁 Full explanation
      127.0.0.1 conventionally names the local IPv4 loopback interface; 127/8 is reserved for loopback. Loopback tests local protocol processing, not cable, switch or remote reachability. Programs can use it for local services. Several loopback descriptions or several 127/8 addresses may be valid; compare each with the stated role.
    • Worked example Subnet-boundary example
      • 192.168.2.70/26
      • Block size: 64 addresses
      • Network .64; broadcast .127
      • Ordinary hosts .65–.126
      • Gateway requires appropriate reachable route
      • NAT ≠ missing-route repair
      👁 Full explanationWorked microexample
      192.168.2.70/26 has 64-address blocks: network .64, broadcast .127, ordinary host range .65–.126. A gateway must be reachable through an appropriate route; NAT does not repair a missing route.

  • NSA04

    DHCP exchange and lease lifecycle

    [Exam Focus]
    • DHCP initial allocation
      • Addresses and configuration options
      • Discover→Offer→Request→ACK
      • Scope/pool and allocated leases
      • Exclusions and reservations
      • Mask, gateway, DNS options
      • Dynamic lease: specified interval
      • Lease ≠ forever
      👁 Full explanation
      DHCP supplies addresses and configuration options. Typical initial IPv4 allocation is Discover→Offer→Request→ACK. The server manages its scope/pool, allocated leases, exclusions and reservations; options may include mask, gateway and DNS servers. A dynamic lease lasts for a specified interval, not forever.
    • Lease renewal and reuse
      • Renew before expiry
      • Failed renewal: later rebinding
      • Disconnected host ≠ perpetual renewal
      • Expiry: address eligible for reuse
      • Server-policy conditions
      • Reconnection: validate/renew/new allocation
      • Expiry alone ≠ persistent failure
      • Reservation: known client, predictable address
      • DHCP configuration retained
      👁 Full explanation
      A client renews before expiry; it later tries rebinding if renewal fails. A disconnected host does not automatically renew forever. On lease expiry the address becomes eligible for reuse, subject to server policy. Reconnection normally triggers validation/renewal/new allocation, so an expired lease alone does not prove persistent failure. A reservation gives a predictable address to a known client while retaining DHCP configuration.
    • Worked example Expired disconnected-client example
      • Expiry while other clients allocate
      • Old address may be reassigned
      • Validate configuration before reuse
      • No unvalidated old-address resumption
      👁 Full explanationWorked microexample
      If a disconnected client’s lease expires while other clients obtain addresses, its old address may be reassigned. It must not simply resume using it without validating its configuration.

  • NSA05

    DHCP deployment and diagnosis

    [Exam Focus]
    • DHCP deployment rules
      • Subnet-matching scope
      • Exclude manual server/router addresses
      • Correct configuration options
      • Relay: broadcasts across router
      • Static and DHCP coexist
      • Avoid address conflicts
      • Less repetitive administration
      • Availability/security: deployment-dependent
      • Rogue-reply protection
      • Location change ≠ guaranteed connectivity
      👁 Full explanation
      Use a scope matching the subnet, exclude manually assigned server/router addresses, set correct options and provide a relay when client broadcasts must cross a router. Static assignments and DHCP can coexist; avoid address conflicts. DHCP lowers repetitive administration but availability/security depend on deployment and protection from rogue replies. It does not guarantee connectivity whenever a device changes location.
    • DHCP returning-client diagnosis
      • Inspect current lease/address
      • Server/relay reachability
      • Free pool capacity and logs
      • New devices: possible pool exhaustion
      • Exhaustion requires evidence
      • Link-local fallback: 169.254.2.33 example
      • Same-link communication
      • Not ordinary routed Internet access
      • 0.0.0.0: unspecified
      • 255.255.255.255: limited broadcast
      👁 Full explanation
      For a returning client, inspect current lease/address, reachable server/relay, free pool capacity and logs. New devices can exhaust a pool, but absent observations this is only a hypothesis. Some clients self-configure IPv4 link-local addresses such as 169.254.2.33 after DHCP failure; these support same-link communication, not ordinary routed Internet access. 0.0.0.0 is unspecified and 255.255.255.255 is limited broadcast.

  • NSA06

    DNS resolution and diagnostic evidence

    [Exam Focus]
    • DNS record roles
      • Forward: name→address
      • A: IPv4; AAAA: IPv6
      • Reverse: address→name
      • PTR: reverse namespace
      • CNAME: alias
      • MX: mail exchangers
      • NS: authoritative name servers
      • Forward/reverse: independent existence
      • Not necessarily perfect inverses
      👁 Full explanation
      Forward resolution obtains an address from a name, using A for IPv4 and AAAA for IPv6. Reverse lookup uses a PTR record in the reverse namespace to obtain a name from an address. CNAME aliases a name, MX identifies mail exchangers and NS identifies authoritative name servers. Forward and reverse records need not both exist or be perfect inverses.
    • DNS caching and diagnosis
      • Resolver caching: TTL
      • nslookup name
      • Explicit DNS-server query
      • Configured resolver versus authoritative answer
      • Address ping succeeds, lookup fails
      • Naming/configuration trouble suggested
      • Ping by name: resolved address possible
      • nslookup: direct DNS diagnostic
      • Resolving includes forward resolution
      👁 Full explanation
      Resolvers cache answers for their TTL. Query nslookup name or specify the DNS server explicitly; compare the configured resolver with the authoritative answer when appropriate. A successful ping by address but failed name lookup suggests naming/configuration trouble. Ping by name may display a resolved address, but nslookup is the direct DNS diagnostic. “Resolving” is a general term that includes forward resolution.

  • NSA07

    Commands and observable state

    [Exam Focus]
    • Address-configuration commands
      • Windows ipconfig: address/mask/gateway
      • ipconfig /all: complete adapters
      • Physical/MAC, DHCP, DNS information
      • /renew: request renewal
      • /release: dynamic address release
      • /flushdns: client DNS cache clearing
      • Linux ip addr: addresses
      • Linux ip route: routes
      • Persistent configuration: distribution-specific
      👁 Full explanation
      Windows ipconfig shows addresses, mask and gateway; ipconfig /all adds complete adapter configuration including physical/MAC address, DHCP and DNS information. /renew requests renewal, /release releases a dynamic address and /flushdns clears the client DNS cache. Linux ip addr and ip route show interface addresses and routes; exact persistent configuration varies by distribution.
    • Connection and path diagnostics
      • netstat: endpoints/protocols/TCP states
      • netstat -ano: numeric addresses/ports/PIDs
      • Literal netstart ≠ netstat
      • Ping: IP reachability probes
      • traceroute/tracert: responding hops
      • TTL/hop-limit expiry
      • ICMP filtering: replies may fail
      • Missing reply ≠ service-down proof
      • nslookup: DNS inspection
      👁 Full explanation
      netstat displays connections/endpoints/protocols and TCP states; netstat -ano displays numeric addresses/ports and PIDs. Use the exact command name netstat rather than netstart. ping probes IP reachability; traceroute/tracert reveals responding hops using TTL/hop-limit expiry. ICMP filtering can prevent replies without proving the service is down. nslookup inspects DNS.

  • NSA08

    Repeatable troubleshooting procedure

    [Exam Focus]
    • Evidence-led troubleshooting sequence
      • Symptom, scope, time, recent changes
      • Configuration, baseline, logs
      • Testable hypothesis
      • Least disruptive explanation first
      • Isolate failing component
      • Targeted fix; verify user service
      • Document results
      • One relevant factor at a time
      • Reboot may hide evidence
      • Reboot ≠ diagnosis
      👁 Full explanation
      Define the symptom, scope, time and recent changes; gather the configuration, baseline and logs. Form a testable hypothesis, test the least disruptive explanation, isolate the failing component, apply a targeted fix, verify the user service and document the result. Change one relevant factor at a time when possible. A reboot can hide evidence and is not a diagnosis by itself.
    • Troubleshooting approaches
      • Bottom-up: physical link first
      • Top-down: application errors first
      • Divide-and-conquer: test middle layer
      • Narrow working/failing boundary
      • Divide-and-conquer ≠ random trial-and-error
      • Reboot/update/reset/scan: context-dependent actions
      • No fault evidence: no unique ranking
      👁 Full explanation
      Use bottom-up checks from physical link, top-down checks from application errors, or divide-and-conquer by testing a middle layer. Divide-and-conquer narrows the working/failing boundary; it is not random trial-and-error. Rebooting, updates, resetting settings and scanning can all be troubleshooting actions in suitable circumstances; use fault evidence to choose among them.
    • Worked example Scope-based diagnosis examples
      • One client fails: inspect client
      • Link, address and policy first
      • All name lookups fail
      • Server IPs still reachable
      • Inspect shared DNS/configuration first
      • Cable replacement: unsupported by naming-only failure
      👁 Full explanationWorked microexample
      One client fails while others work: inspect that client’s link, address and policy first. All clients fail name lookup but reach server IPs: inspect shared DNS/its configuration before replacing every cable.

  • NSA09

    Connectivity diagnosis by layers

    [Exam Focus]
    • Layered connectivity checklist
      • Power, cable/connector, link state
      • NIC and driver state
      • VLAN membership
      • Address/prefix and local gateway
      • Route, DNS, application port/authentication
      • Recognized NIC: driver absence less likely
      • Recognition ≠ working physical link
      • Ethernet: commonly RJ45
      • RJ11 telephone jack ≠ expected Ethernet
      👁 Full explanation
      Check power, cable/connector and link state, then NIC/driver state, VLAN membership, address/prefix, local gateway, route, DNS and finally application port/authentication. A recognized NIC makes a missing driver less likely, not proof of a working physical link. Ethernet commonly uses RJ45 connectors; an RJ11 telephone jack is not the expected Ethernet connection.
    • Interpreting connectivity symptoms
      • Local works, remote fails
      • Inspect gateway/routes/filtering
      • Application works, ping fails
      • ICMP filtering plausible
      • Port refused: destination reachable enough
      • Inspect service/listener policy
      • Timeout: loss/filtering/down host possible
      • Timeout requires further evidence
      👁 Full explanation
      If same-subnet traffic works but remote traffic fails, compare gateway/routes and filtering. If ping fails but the application connection works, ICMP filtering is plausible. If an application port is refused, the destination is reachable enough to reject it; inspect service/listener policy. A timeout can result from loss, filtering or a down host and needs more evidence.
    • Worked example Post-replacement NIC example
      • Recognized/enabled adapter; no link light
      • Try known-good Ethernet cable
      • Try known-good switch port
      • Recognition ≠ one defective-cable diagnosis
      👁 Full explanationWorked microexample
      After NIC replacement, recognized/enabled adapter but no link light: try a known-good Ethernet cable and switch port. Merely knowing that the OS recognizes the NIC cannot prove one particular cable is defective.

  • NSA10

    Service catalog and remote access

    [Exam Focus]
    • Service protocol roles
      • DNS: names; DHCP: host configuration
      • SMTP: mail send/relay
      • IMAP/POP: mail retrieval
      • FTP: named file-transfer protocol
      • HTTP also transfers files
      • File transfer ≠ exclusive FTP description
      • HTTP/HTTPS: web resources
      • SSH: encrypted remote login
      • SFTP: file transfer over SSH
      • SFTP ≠ FTP/FTPS
      👁 Full explanation
      DNS resolves names; DHCP supplies host configuration. SMTP sends/relays mail, while IMAP/POP retrieve it. FTP is a named file-transfer protocol; HTTP also transfers files, so “transfers files” is not an exclusive FTP description. HTTP/HTTPS serve web resources. SSH provides encrypted remote login; SFTP transfers files over SSH and differs from FTP or FTPS.
    • VPN, media and service administration
      • VPN: private connectivity over another network
      • Secure tunnel: encryption/authentication
      • Protocol/configuration conditions
      • RTP: real-time timing/sequence information
      • Often over UDP
      • RTP ≠ timely-delivery guarantee
      • Network printers: shared services
      • Service accounts, permissions, configuration
      • Monitoring and recovery
      👁 Full explanation
      A VPN extends private connectivity over another network; secure tunneling commonly encrypts/authenticates traffic but depends on protocol/configuration. RTP carries real-time media timing/sequence information, often over UDP; it does not guarantee timely delivery. Network printers expose services shared by clients. Provide accounts, permissions, configuration, monitoring and recovery for each service, not just its protocol name.

  • NSA11

    Routing, NAT and port translation

    • Routing versus NAT/PAT
      • Routing: destination-prefix next-hop selection
      • NAT: address rewriting
      • PAT/NAPT: many-to-one address-and-port translation
      • Distinct bindings on one public address
      • Two private sockets→ports 40001,40002
      • Replies translated to correct clients
      👁 Full explanation
      Routing selects a next hop using a destination prefix; NAT rewrites addresses. Many-to-one address-and-port translation (PAT/NAPT) maps internal flows to one public address using distinct port bindings. For example, two private client sockets can appear as public-address ports 40001 and 40002, with replies translated back to the correct clients.
    • NAT scope and limits
      • Private IPv4→public networks: common use
      • NAT ≠ gateway/route/firewall/authentication replacement
      • One-to-one NAT
      • Destination translation
      • NAT ≠ always many-to-one
      • Public LAN addresses: NAT not automatic
      • Unsolicited inbound service: explicit mapping possible
      • Filtering requirements
      👁 Full explanation
      NAT is often used when private IPv4 clients access public networks; it does not itself replace a gateway, route, firewall or authentication. One-to-one NAT and destination translation are other forms, so NAT does not always mean many hosts share one address. Public addressing inside a LAN does not automatically require NAT. Unsolicited inbound service access may require explicit mapping and filtering.

  • NSA12

    Proxies, gateways and QoS

    • Proxy and gateway functions
      • Proxy: client/backend representative
      • Cache, filter, mediate application requests
      • Default IP gateway: next-hop router
      • Application gateway: possible protocol translation
      • Gateway ≠ mandatory modem/router combination
      • Functions may coexist on one machine
      👁 Full explanation
      A proxy acts on behalf of a client or backend service and can cache, filter or mediate application requests. A default IP gateway is a next-hop router; an application gateway may translate protocols. It need not be a modem/router combination. These terms describe functions that can coexist on one machine.
    • QoS and mixed-category questions
      • QoS: classify, queue, prioritize traffic
      • Low-delay/limited-loss objectives
      • Operates across layers
      • Supports applications
      • QoS ≠ exclusively application-layer service
      • New-service installation: administrative action
      • Email configuration: administrative action
      • Proxies/agents: components
      • Mixed taxonomy: unique exclusion needs scope
      👁 Full explanation
      QoS classifies, queues and prioritizes traffic to meet performance objectives such as low delay or limited loss. It can operate across layers and support applications, so it is not exclusively an application-layer service. Installing a new service is an administrative action; email configuration is another action and proxies/agents are components. Distinguish service-management actions from components using a stated taxonomy.

  • NSA13

    Workgroups, domains and directories

    [Exam Focus]
    • Workgroup versus domain
      • Workgroup: per-machine local accounts
      • Local credentials and per-host sharing
      • Domain: centralized identities/policies
      • Directory infrastructure
      • Administrative arrangement ≠ physical topology
      • Recommended size ≠ hard protocol limit
      • HomeGroup: historical Windows sharing
      • HomeGroup ≠ AD domain
      👁 Full explanation
      A workgroup has locally managed accounts on individual machines; sharing may require local credentials and per-host configuration. A domain centralizes identities and policies through directory infrastructure. These are administrative arrangements, not physical topologies. Avoid treating an old recommended workgroup size as a hard protocol limit. HomeGroup is a historical Windows sharing feature, not another name for an AD domain.

      • Controller: AD DS
      • Domain authentication and directory replication

      • Two virtual controllers, one physical host
      • Shared host failure ≠ independent availability
      • Provisioning: addressing, DNS, time
      • Supported OS/hardware
      • Version minima ≠ universal architecture rules
      👁 Full explanation
      A domain controller runs AD DS, authenticates domain accounts and participates in directory replication. Redundant controllers improve service continuity only if dependencies and failure domains are considered; two virtual controllers on one failed physical host are not independent availability. Provisioning requires correct addressing, DNS, time and supported OS/hardware; version-specific minimum sizes are not universal architecture rules.

  • NSA14

    LDAP and secure directory access

    • LDAP operations and transport protection
      • Entries/attributes: distinguished names
      • Bind: session authentication
      • Search: matching entries
      • Compare: attribute-value test
      • Add/delete/modify: entry changes
      • Modify-DN: rename/move
      • Unbind: end session
      • StartTLS: upgrade connection where supported
      • LDAPS: TLS from setup
      • Protect credentials; verify server identity
      👁 Full explanation
      LDAP accesses directory entries/attributes identified by distinguished names. Bind authenticates a session; search retrieves matching entries; compare tests an attribute value; add/delete/modify change entries; modify-DN renames or moves; unbind ends the session. StartTLS upgrades a connection to TLS where supported; LDAPS uses TLS from connection setup. Protect credentials and verify server identity.
    • Directory ports and security caveats
      • LDAP: commonly TCP 389
      • LDAPS: commonly TCP 636
      • Acronym/port ≠ secure authentication
      • AD also uses DNS/Kerberos
      • LDAP ≠ entire directory product
      • LDAPS-retired-with-LDAPv2 claim: unreliable
      • Modern TLS-protected LDAP distinction
      👁 Full explanation
      LDAP commonly uses TCP 389 and LDAPS TCP 636; an acronym/port alone does not make authentication secure. AD also uses DNS and Kerberos; LDAP is not identical to the entire directory product. Do not equate modern TLS-protected LDAP or LDAPS with retired LDAPv2.

  • NSA15

    AD structure and delegation

    • Directory objects and logical hierarchy
      • Objects: users/computers/groups/resources
      • Schema-defined attributes
      • Security principals: SIDs
      • Display name ≠ sole security identity
      • Domain: objects plus replicated database
      • Tree: contiguous DNS namespace domains
      • Forest: grouped trees
      • Shared schema/configuration
      • Global-catalog framework
      👁 Full explanation
      A directory object represents a user, computer, group or resource and has schema-defined attributes. Security principals have SIDs; display names are not the sole security identity. A domain groups directory objects and a replicated domain database. A tree groups domains in a contiguous DNS namespace; a forest groups trees with a shared schema/configuration and global-catalog framework.
    • OUs, groups and schema restrictions
      • OUs: object organization
      • Delegation and Group Policy scopes
      • OUs ≠ separate forests/security boundaries
      • Groups: access assignment
      • OUs: policy/delegation structure
      • Schema changes: broad propagation, care
      • Ordinary objects: deletion possible
      • Schema-definition restrictions: special scope
      • Schema restrictions ≠ all object restrictions
      👁 Full explanation
      OUs organize objects and provide convenient scopes for delegated administration and Group Policy; they are not separate forests/security boundaries. Use groups to assign access and OUs to structure policy/delegation. Schema changes require care because they propagate broadly; ordinary directory objects can be deleted, unlike the special restrictions on schema definitions. Apply schema restrictions to the specific directory object type being discussed.

  • NSA16

    Sites, replication and trusts

    • AD sites and replication
      • Sites: grouped IP subnets
      • Network locality model
      • Controller selection
      • Replication traffic management
      • Sites ≠ domains/OUs
      • Replicate changes among controllers
      • Intrasite notification-triggered pulls
      • Intersite schedules/link costs
      • Replication ≠ prior-good-state backup
      👁 Full explanation
      Sites group IP subnets to model network locality, influence controller selection and manage replication traffic. They are distinct from domains/OUs. AD replicates directory changes among controllers; notification can trigger pulls within a site while schedules/link costs influence traffic between sites. Replication is not an independent backup of previous good states.
    • Trust direction and permissions
      • A trusts B
      • B identities authenticate for A resources
      • Permissions still required
      • Trust ≠ automatic file access
      • One/two-way direction
      • Transitive/nontransitive extension
      • Direction and transitivity: independent
      • Explicit trust ≠ fixed direction/transitivity
      • Trust type/configuration determines behavior
      • State direction before drawing arrows
      👁 Full explanation
      If domain A trusts B, B’s identities can be authenticated for resources in A, subject to permissions. Trust alone grants no automatic file access. Direction (one/two way) and transitivity (extends/does not extend) are independent. An explicit trust is not necessarily one-way or nontransitive; the trust type/configuration determines that. State the direction in words before drawing arrows.

  • NSA17

    Accounts, rights and password diagnosis

    [Exam Focus]
    • Account lifecycle and access models
      • Named accounts
      • Only needed groups/rights
      • Disable departed users
      • Audit privileged activity
      • Authentication: verify account
      • Authorization: permitted operations
      • User right: remote logon
      • File permission: object-specific
      • Groups easier to review than individual grants

      • RAID0: striping, capacity/throughput

      For changes, validate the desired output, preserve a known-good copy, write to a temporary file in the same filesystem, then atomically replace the target where supported. Check permissions and configuration syntax, reload the affected service, verify and retain a rollback. Merely appending the same setting on every run is not idempotent.

    Regex analysis and log rotation

    [Exam Focus]
    • Regex contracts and log rotation
      • Text patterns, not encryption/compression/rotation
      • search: match anywhere
      • fullmatch: entire string
      • Raw strings: backslash-heavy patterns
      • Capture needed fields only
      • Explicit unmatched/malformed-line handling
      • Rotation: bounded size, historical segments
      • Parsing and rotation: complementary
      👁 Full explanation
      Regex recognizes textual patterns; it does not encrypt, compress or rotate logs. search finds a match anywhere, while fullmatch requires the entire string to fit. Use raw Python strings for backslash-heavy patterns, capture only the needed fields and treat unmatched/malformed lines explicitly. Log rotation bounds file size and preserves historical segments; it is complementary to parsing.
    • Log-analysis evidence
      • Count requested event
      • Correlate timestamps and hosts
      • No matches ≠ unreadable log
      • Security and performance uses
      • Neither purpose universally exclusive
      👁 Full explanation
      Count the event actually requested, use timestamps/hosts to correlate, and separate absence of matches from failure to read the log. Logs support security and performance analysis, so neither purpose is universally exclusive.

      • 200 and 503: one each
      • Noise deliberately ignored
      👁 Full explanationWorked microexample

    CPU and memory measurements

    [Exam Focus]
    • Interval CPU measurement
      • Cumulative counters: two samples required
      • Lifetime total ≠ current utilization
      • Linux /proc/stat: CPU categories
      • Define idle categories
      • Avoid guest-field double counting
      • Busy_fraction=1−Δidle/Δtotal
      • Chosen nonbusy: idle+iowait
      • Iowait interpretation limitations
      👁 Full explanation
      A cumulative CPU counter must be sampled twice to calculate interval use; a single lifetime total is not current utilization. On Linux /proc/stat exposes cumulative CPU categories; define which categories count as idle and avoid double-counting guest fields. A simple convention is busy fraction=1−Δidle/Δtotal using idle+iowait as the chosen nonbusy categories. Iowait interpretation has limitations.
    • Available-memory measurement
      • /proc/meminfo: MemAvailable
      • Estimate without swapping
      • MemFree excludes reclaimable memory
      • Windows Performance Counters/OS APIs
      • Analogous metrics, different interfaces
      • System calls/counters/log parsing: complementary
      • Only-technique claim requires platform/API
      👁 Full explanation
      /proc/meminfo exposes MemAvailable, an estimate of memory available without swapping; MemFree alone excludes reclaimable memory. Windows Performance Counters and OS APIs expose analogous measurements through different interfaces. System calls, counters and log parsing can all contribute; selecting one as the only monitoring technique is unjustified without a platform/API.
    • Worked example Measurement calculation example
      • Δtotal=1000 ticks; Δidle=250
      • Busy≈75%
      • MemTotal=8192 MiB; MemAvailable=2048 MiB
      • Approximate unavailable/used=75%
      • MemAvailable ≠ exact-allocation success guarantee
      👁 Full explanationWorked microexample
      If total CPU counters grow by 1000 ticks and chosen idle counters by 250, measured busy≈75%. If MemTotal=8192 MiB and MemAvailable=2048 MiB, approximate unavailable/used fraction is75%, not a prediction that an allocation of exactly 2048 MiB must succeed.

    Backup scheduling and restore verification

    [Exam Focus]
    • Recurring-job scheduling
      • Unix: cron/systemd timers
      • Windows: Task Scheduler
      • User crontab: minute,hour,day-of-month,month,day-of-week,command
      • Absolute paths and known environment
      • Protected inputs and logs
      • Bounded runtime
      • Lock unsafe overlapping jobs
      • Interactive PATH/CWD/credentials: not assumed
      👁 Full explanation
      Schedule recurring work using cron/systemd timers on suitable Unix systems or Task Scheduler on Windows. A user crontab uses minute,hour,day-of-month,month,day-of-week then command. Use absolute paths, known environment, protected inputs, logs, bounded runtime and a lock when overlap is unsafe. Do not assume an interactive PATH, current directory or stored credentials exist in a scheduled job.
    • Backup verification and tool purposes
      • Compression: data packaging
      • Scheduling: operation timing
      • Check exit status and archive contents
      • Restore sample into isolated destination
      • Command success ≠ usable backup proof
      • Script version control: review aid
      • Version control ≠ data backup
      👁 Full explanation
      Compression packages data; scheduling chooses when the operation runs. Test exit status and the archive contents, then restore a sample into an isolated destination. A successful command alone does not prove a usable backup. Version control of scripts helps review but does not replace data backup.

      • 0 2 * * *
      • Daily 02:00, scheduler timezone
      • Runs as crontab owner
      • /usr/bin/python3 /opt/backup.py /srv /bak
      • Source/destination arguments
      • >>/var/log/bak.log: append output
      • 2>&1: stderr joins stdout
      • Command kept on one line
      • Paths/permissions/logging/program: preconfigured
      • User crontab: no username field
      • System crontab: username possible
      👁 Full explanationWorked microexample
      One user-crontab entry (keep the command on one line): 0 2 * * * /usr/bin/python3 /opt/backup.py /srv /bak >>/var/log/bak.log 2>&1 This runs daily at 02:00 in the scheduler’s timezone as the crontab owner. The script takes its configured source and destination arguments. Paths, permissions, logging and the backup program must already be configured.     Constructing a bounded backup script

    [Exam Focus]
    • Backup-script structure and limitations
      • Separate parsing, preconditions, archive creation, reporting
      • Source directory required
      • Destination outside source
      • Unique output names
      • Failed partial ≠ completed backup
      • Application consistency and capacity checks
      • Retention and independent protected copies
      • Teaching script: directory packaging
      • No silent scheduled-job installation
      👁 Full explanation
      Separate argument parsing, preconditions, copying/archive creation and result reporting. Require a source directory, avoid putting the backup inside that source, create unique output names and ensure a failed partial file is not mistaken for a completed backup. Real backup policies also need application consistency, capacity checks, retention and independent protected copies. The following teaching script packages a directory; it does not silently install a scheduled job.
    • Worked example Backup-script trace and verification
      • argparse source/destination: Path
      • resolve(): absolute source/destination
      • is_dir(): existing directories required
      • dst==src or src in dst.parents
      • Reject destination inside/equal source
      • UTC timestamp name; microseconds
      • shutil.make_archive: gztar, root_dir=src
      • OSError: remove partial .tar.gz
      • unlink(missing_ok=True)
      • p.exit(1): failure report
      • print completed archive path
      • Verify archive members
      • Restore into different empty directory
      • Compare selected files
      👁 Full explanationWorked microexample
      import argparse, shutil from pathlib import Path from datetime import datetime, timezone p = argparse.ArgumentParser() p.add_argument("source", type=Path) p.add_argument("destination", type=Path) a = p.parse_args() src, dst = a.source.resolve(), a.destination.resolve() if not src.is_dir() or not dst.is_dir(): p.error("source and destination must be existing directories") if dst == src or src in dst.parents: p.error("destination must be outside source") name = datetime.now(timezone.utc).strftime("copy-%Y%m%dT%H%M%S%fZ") base = dst /name try: archive = shutil.make_archive(str(base), "gztar", root_dir=src) except OSError as exc: base.with_suffix(".tar.gz").unlink(missing_ok=True) p.exit(1, f"backup failed: {exc}\n") print(archive) # Run against a teaching directory, verify archive members, then restore # into a different empty directory and compare selected files.
