  • ADB01

    Objects, identity, classes and persistence

    [Exam Focus]
    • Object identity, state, behavior
      • Class → attributes/operations
      • Object → class instance
      • OID independent of attribute values
      • Lifetime-stable OID
      • Equal values/different identities
      • Name change ≠ identity change
      👁 Full explanation
      An object combines identity, state and behavior. A class specifies the attributes and operations of its instances; an object is one instance. The object identifier (OID) distinguishes objects independently of their attribute values and remains stable over that object's lifetime. Two objects can have equal values and different identities; changing a name does not create a new identity.
    • Persistence and database approaches
      • Object survives creating program
      • OODBMS durable storage/transactions
      • Querying/controlled sharing
      • Objects not primarily rows/tables
      • Object-relational → richer relational types
      • ORM → objects mapped to tables
      • Three distinct approaches
      • Complex CAD/multimedia suitability
      • M:N alone needs no relational abandonment
      👁 Full explanation
      Persistence lets an object survive beyond the program execution that created it. An OODBMS adds durable storage, transactions, querying and controlled sharing to object concepts. It does not primarily present objects as rows and tables. An object-relational DBMS extends a relational system with richer types; ORM maps programming objects into relational tables. These three approaches differ. Complex CAD or multimedia structures can suit an object model, but many-to-many relationships alone do not require abandoning relational design.

  • ADB02

    Encapsulation, abstraction and object associations

    [Exam Focus]
    • Encapsulation versus abstraction
      • Encapsulation → state plus operations
      • Controlled implementation access
      • Account.withdraw(amount) → balance rule
      • Hidden storage details
      • Abstraction → relevant operation contract
      • What versus implementation how
      • Overlapping information hiding
      • Combining state/methods → encapsulation
      👁 Full explanation
      Encapsulation groups state with operations and controls access to implementation details. Account.withdraw(amount) can enforce a balance rule while hiding its storage. Abstraction presents the relevant contract—what withdrawal does—without exposing how it is implemented. These ideas overlap in information hiding, but combining state and methods specifically describes encapsulation.
    • Object associations and collaboration
      • References link objects
      • Department.employees → Employee objects
      • Association ≠ inheritance
      • Inheritance → is-a types
      • Methods invoke other-object operations
      • Class → structure/behavior
      • Attribute → state
      • Method → operation implementation
      • Part names ≠ whole object
      👁 Full explanation
      An association links objects, often through references; Department.employees can reference Employee objects. It is different from inheritance, which means an is-a relationship between types. Methods can invoke operations on other objects, supporting collaboration. A class defines structure and behavior; an attribute describes state; a method implements an operation. Do not treat each of these as an interchangeable name for the whole object.

  • ADB03

    Inheritance, polymorphism and safe substitutability

    [Exam Focus]
    • Inheritance versus association
      • Subtype from superclass
      • Reuse applicable attributes/behavior
      • GraduateStudent is-a Student
      • Student belongs-to Department
      • EER inherited attributes/relationships
      • Programming object model adds behavior
      👁 Full explanation
      Inheritance derives a subtype from a superclass, reusing applicable attributes and behavior. GraduateStudent is a Student; association instead says Student belongs to Department. EER teaches inherited attributes and relationships, while a programming object model also specifies behavior.
    • Subtype polymorphism
      • Superclass/interface reference → compatible subclasses
      • Common operation/different implementations
      • Shape.area() dispatch
      • Actual Circle.area()/Rectangle.area()
      • No arbitrary unrelated-class conversion
      • No dynamic class mutation
      • Inheritance → structural subtype prerequisite
      • Polymorphism → runtime common-interface use
      • Ambiguous MCQ needs requested distinction
      👁 Full explanation
      Subtype polymorphism lets a superclass/interface reference denote objects of different compatible subclasses. The same operation can dispatch to different implementations: Shape.area() calls Circle.area() or Rectangle.area() according to the actual object. This is not arbitrary conversion of an object into an unrelated class, nor dynamic class mutation. Inheritance establishes a subtype relationship; polymorphism uses that relationship through a common interface. If a question asks whether treating subclasses as a superclass is inheritance or polymorphism, clarify whether it asks about the structural prerequisite or the runtime use.

      • Integer/real/Boolean/string
      • Tuple → named component values
      • (Street:'A',City:'B')
      • Structured record ≠ record collection

      In a common object model, an object is described by (OID,type constructor,state). An atom is one basic value, such as an integer, real, Boolean or string.   • ADB06

    Transactions, ACID and state transitions

    • Transactions and ACID
      • Logical database-work unit
      • Read-only transactions included
      • Atomicity → all effects or none
      • Consistency → correct integrity-preserving work
      • Isolation → concurrent interference control
      • Durability → committed effects survive failure
      • DBMS cannot repair incorrect business logic
      👁 Full explanation
      A transaction is a logical unit of database work, including read-only work. Atomicity means all effects or none; consistency means correct work preserves integrity rules; isolation controls concurrent interference; durability preserves committed effects despite failure. A DBMS cannot automatically make incorrect business logic consistent.
    • Transaction states and responsibilities
      • Active → executing operations
      • Partially committed → last operation finished
      • Durability not yet assured
      • Committed → commitment succeeded
      • Failure → Failed
      • Rollback → Aborted
      • Terminate or restart new attempt
      • Concurrency control → isolation
      • Recovery → atomicity/durability
      • Transaction management broader
      • Broad responsibility answers can overlap
      👁 Full explanation
      Active means operations are executing. Partially committed means the last operation finished but durable commitment is not yet assured. Committed means commitment succeeded. A failure leads to Failed, then Aborted after rollback; a transaction may terminate or be restarted as a new attempt. Concurrency control primarily enforces isolation; recovery supports atomicity and durability. Transaction management is the broader subsystem, so both it and recovery management can be legitimate answers to broad responsibility questions.
    • Worked example Requested transfer versus invariant
      • Initial A=5,000/B=8,000
      • Transfer 750 A→B
      • Final A=4,250/B=8,750
      • Total=13,000
      • Unchanged/reverse balances also preserve total
      • Correct debit/credit required
      👁 Full explanationWorked example
      A=5,000 and B=8,000 become 4,250 and 8,750 after transferring 750 from A to B. Both balances total 13,000. Unchanged or reverse-transfer balances can also preserve that sum; only the requested debit/credit implements the specified successful transfer.

  • ADB07

    Read/write operations, buffers and log records

    • Item operations and buffer policy
      • read_item(X) → locate page
      • Fetch absent page into buffer
      • Copy X into program variable
      • write_item(X) → variable into buffered page
      • Mark page dirty
      • Disk flush may occur later
      • write_item ≠ immediate disk flush
      • Insert/delete modify data
      • Sorting → query processing
      • Sorting ≠ primitive item update
      👁 Full explanation
      read_item(X) locates X's page, brings it into a buffer if absent, and copies X into a program variable. write_item(X) copies the new program value into the buffered page, marking it dirty. Writing that page to disk can occur later according to the buffer policy; write_item is not inherently an immediate disk flush. Insert and delete also modify data; sorting is a query-processing operation rather than a primitive item update.
    • Log records and images
      • START/UPDATE(T,X,old,new)
      • COMMIT/ABORT/END
      • Before-image → undo
      • After-image → redo
      • Physical/logical record alternatives
      • Not every read needs logging
      • COMMIT → successful completion
      • ABORT may only start rollback
      • ABORT ≠ completed undo proof
      👁 Full explanation
      A conceptual log can contain START, UPDATE(T,X,old,new), COMMIT, ABORT and END records. Before-images support undo; after-images support redo. Real systems may use physical or logical records, and need not log every read. COMMIT records successful completion; an ABORT record can mark the start of rollback rather than prove every undo step is complete.

  • ADB08

    Diagnose concurrency anomalies from a trace

    • Lost update versus dirty read
      • Both read 500
      • T2 +200 → writes 700
      • T1 stale +100 → writes 600
      • Correct serial result 800
      • Dirty read → other's uncommitted write
      • Writer abort → reconsider dependent work
      • Own changes ≠ dirty read
      👁 Full explanation
      Lost update: T1 and T2 both read 500; T2 adds 200 and writes 700; T1 adds 100 to its stale value and writes 600. Correct serial execution yields 800. Dirty read: T2 reads a value written by uncommitted T1; if T1 aborts, dependent work must be reconsidered. Reading one's own changes is not a dirty read.
    • Read and summary anomalies
      • Nonrepeatable → same-row committed change
      • Phantom → changed predicate result set
      • Matching insert/delete/update
      • Incorrect summary → inconsistent versions
      • Transfer 10: A=100/B=100
      • Old A=100 plus new B=110
      • Observed 210 versus invariant 200
      • Single committed B=20→50 insufficient
      • Invalid-summary 90 needs more evidence
      👁 Full explanation
      Nonrepeatable read means a repeated read of one row sees a committed change. A phantom means repeating a predicate query finds a changed qualifying set after another transaction inserts, deletes or changes matching rows. Incorrect summary mixes mutually inconsistent versions: a transfer moves 10 from A=100 to B=100; a sum reading old A=100 and new B=110 gets 210 instead of the invariant 200. A single committed update from B=20 to B=50 does not alone prove an invalid summary of 90.

  • ADB09

    Serial schedules, conflicts, and precedence graphs

    • Serial versus serializable
      • Serial → consecutive transaction operations
      • Serializable → equivalent serial order
      • Interleaving permitted
      • Same final value insufficient
      • Accidental coincidence possible
      • Conflict → different transactions
      • Same item/at least one write
      • Read/read nonconflicting
      👁 Full explanation
      A serial schedule executes each transaction's operations consecutively. A serializable schedule is equivalent to some serial order; it may interleave transactions. Equality of one final value is insufficient evidence because different executions can accidentally coincide. Two operations conflict when they belong to different transactions, access the same item and at least one writes. Read/read pairs do not conflict.
    • Precedence graph test
      • Vertex per transaction
      • Earlier/later conflict → Ti→Tj
      • Acyclic → conflict-serializable
      • Topological order → valid serial order
      • Cycle → not conflict-serializable
      • View serializability weaker test
      • Read-from relationships/final writers
      • Some blind-write schedules permitted
      👁 Full explanation
      For conflict serializability, make one graph vertex per transaction. For every earlier conflicting operation of Ti and later operation of Tj, add Ti→Tj. Acyclic means conflict-serializable; a topological ordering gives a valid serial order. Cyclic means not conflict-serializable. This test is stronger than view serializability, which also compares read-from relationships and final writers and may permit some schedules with blind writes.
    • Worked example Worked conflict graphs
      • r1(X),w2(X),r2(Y),w1(Y)
      • X → T1→T2
      • Y → T2→T1
      • Cycle → not conflict-serializable
      • r1(X),w1(X),r2(X),w2(X)
      • Only T1→T2
      • Acyclic → conflict-serializable
      👁 Full explanationWorked example
      r1(X), w2(X), r2(Y), w1(Y) gives T1→T2 on X and T2→T1 on Y, a cycle. r1(X), w1(X), r2(X), w2(X) gives only T1→T2 and is conflict-serializable.

  • ADB10

    Recoverable, cascadeless and strict schedules

    • Commit-dependency schedule hierarchy
      • Recoverable → reader commits after writer
      • Avoid committed dependency on aborted writer
      • Cascadeless → read committed writes only
      • No cascading aborts
      • Strict → no other's uncommitted-item reads
      • No other's uncommitted-item overwrites
      • Strict ⇒ cascadeless ⇒ recoverable
      👁 Full explanation
      Recoverable means if Tj reads Ti's value, Tj cannot commit before Ti commits. Otherwise Ti might abort after Tj already committed dependent work. Cascadeless means a transaction reads only values written by committed transactions, avoiding cascading aborts. Strict means no other transaction reads or overwrites an item written by an uncommitted transaction. Strict ⇒ cascadeless ⇒ recoverable.

      • w1(X),r2(X),c2,a1
      • Dirty dependency committed → unrecoverable
      • c2 after c1 → recoverable dependency
      • Earlier dirty read remains
      • Not cascadeless
      • Serializability → equivalent order
      • Recoverability → safe commit/rollback dependencies
      • Separate tests
      👁 Full explanation
      For w1(X), r2(X), c2, a1, T2 committed a dirty dependency, so the schedule is unrecoverable. Moving c2 after c1 makes that dependency recoverable, but the earlier dirty read still makes it not cascadeless. Serializability and recoverability are separate tests: one concerns equivalent transaction order and the other safe commit/rollback dependencies.

  • ADB12

    Two-phase locking variants

    • Basic two-phase locking
      • Growing → acquire/upgrade
      • Shrinking → release/downgrade
      • Any release → no new acquisition
      • Lock point → final lock obtained
      • Well-formed 2PL → conflict serializability
      • Deadlock possible
      • Basic 2PL may allow cascading aborts
      👁 Full explanation
      Basic 2PL has a growing phase that acquires/upgrades locks and a shrinking phase that releases/downgrades them. Once any lock is released, no new lock may be acquired. The lock point is the instant the final lock is obtained. 2PL guarantees conflict serializability for well-formed transactions, but can deadlock and basic 2PL alone need not prevent cascading aborts.
    • 2PL variants versus 2PC
      • Strict → X until commit/abort
      • Rigorous → S/X until commit/abort
      • Conservative/static → all locks beforehand
      • No execution with partial lock set
      • Prevents hold-and-wait deadlock
      • Requires known lock set
      • May reduce concurrency
      • 2PL → data-access ordering
      • 2PC → distributed commit decision
      👁 Full explanation
      Strict 2PL retains exclusive locks until commit/abort. Rigorous 2PL retains both shared and exclusive locks until that point. Conservative/static 2PL obtains all needed locks before execution and does not begin while only a subset is available, preventing hold-and-wait deadlock. It requires knowing the lock set and can reduce concurrency. Two-phase locking orders access to data; two-phase commit coordinates a distributed commit decision.

  • ADB13

    Deadlock detection, prevention and starvation

    • Deadlock detection and repair
      • T1 holds X/wants Y
      • T2 holds Y/wants X
      • Wait-for Ti→Tj → held-lock wait
      • Cycle → ordinary lock-wait deadlock
      • Select victim/abort/undo/release locks
      • Repeat for remaining cycles
      • Aborting all also works
      • Aborting all wastes more work
      👁 Full explanation
      Deadlock requires a waiting cycle: T1 holds X and wants Y; T2 holds Y and wants X. In a wait-for graph, an edge Ti→Tj means Ti waits for a lock held by Tj. A cycle indicates deadlock under the ordinary lock-wait model. Abort a suitable victim, undo its effects and release its locks; repeat if other cycles remain. Aborting every deadlocked transaction also breaks cycles but wastes more work.
    • Deadlock prevention versus starvation
      • Fixed resource ordering
      • Conservative 2PL prevents cycles
      • No-wait → abort incompatible request
      • No age timestamp needed
      • Timeout → abort long waits
      • Slow progress mistaken for deadlock
      • Starvation → indefinite postponement
      • Other work continues/no required cycle
      • Fair queues/sensible victim selection
      • Retain original retry timestamps
      • Deadlock freedom ≠ fairness
      👁 Full explanation
      Fixed resource ordering and conservative 2PL prevent cycles. A no-wait policy aborts immediately on an incompatible lock request and needs no age timestamp. A timeout aborts long waits but may mistake slow progress for deadlock. Starvation is indefinite postponement while other work proceeds, without a required cycle. Fair queues, sensible victim selection and retaining original transaction timestamps on retry reduce starvation; deadlock freedom alone does not prove fairness.

  • ADB15

    Basic timestamp ordering tests

    • Basic timestamp-ordering tests
      • Assign TS(T)
      • read_TS(X) → largest successful reader timestamp
      • write_TS(X) → latest successful writer timestamp
      • Read abort: TS(T)<write_TS(X)
      • Otherwise read/update read_TS
      • Write abort: TS(T)<read_TS(X)
      • Or TS(T)<write_TS(X)
      • Otherwise write/set write_TS
      • Preserve timestamp order
      👁 Full explanation
      Assign each transaction TS(T). For item X track read_TS(X), the largest timestamp of a successful reader, and write_TS(X), that of its latest successful writer. A read by T aborts if TS(T)<write_TS(X); otherwise it succeeds and updates read_TS. A write aborts if TS(T)<read_TS(X) or TS(T)<write_TS(X); otherwise it succeeds and sets write_TS. These tests preserve timestamp order.
    • Timestamp example and protocol limits
      • TS(T)=10/write_TS(X)=20
      • Read aborts → logically later write
      • Older transaction can abort
      • Younger-always-aborts claim false
      • Thomas rule → obsolete write ignored
      • Different protocol must be stated
      • No lock-wait deadlocks
      • Repeated restarts possible
      👁 Full explanation
      For TS(T)=10 and write_TS(X)=20, T cannot read X: it would observe a logically later write. Thus the transaction aborted can be older, contrary to the guides' blanket younger-always-aborts claim. The Thomas write rule can ignore an obsolete write instead of aborting in one case, but that is a different protocol and must be stated. Basic timestamp ordering avoids lock-wait deadlocks but may cause repeated restarts.

  • ADB16

    Optimistic control, versions, and lock granularity

    • Optimistic and multiversion control
      • Private reads/computation
      • Validate read/write sets
      • Check overlapping transactions
      • Validation success → publish
      • Failure → retry
      • Uncommon conflicts favorable
      • High contention → wasted aborted work
      • MVCC → multiple versions
      • Reader uses appropriate snapshot
      • Snapshot isolation ≠ automatic serializability
      • Different-row writes can violate shared invariant
      👁 Full explanation
      Optimistic/validation control reads and computes privately, validates its read/write sets against overlapping transactions, then publishes if validation succeeds; otherwise it retries. It works well when conflicts are uncommon, but high contention wastes work on aborts. Multiversion control keeps versions so a reader can use an appropriate snapshot. Different operating systems are possible but do not define the distinction. Same DBMS does not imply identical local schemas, automatic replication or immediate synchronization.

      • No automatic semantic reconciliation

ODBC and JDBC provide connectivity interfaces; they do not automatically solve semantic differences or create one distributed transaction. Locality, expansion and replicated availability are potential benefits. Distribution adds communication, coordination and security costs; a site outage can still make needed data unavailable if no usable replica exists.

    Replication policies and their costs

    [Exam Focus]
    • Replication extent and backup distinction
      • Full → whole database/relevant sites
      • Partial → selected fragments/selected sites
      • Nonredundant → one copy/fragment
      • Read locality/possible availability gains
      • Storage/update-propagation costs
      • Mistakes can propagate
      • Replication ≠ independent backups
      👁 Full explanation
      Full replication places the whole database at every relevant site; partial replication copies selected fragments to selected sites; nonredundant allocation stores each fragment once. Copies improve read locality and can improve availability but require storage and update propagation. They can also spread mistakes, so replication does not replace independent backups.
    • Replication timing and transfer policies
      • Eager/synchronous → propagation before commit/ack point
      • Higher update latency
      • Lazy/asynchronous → later propagation
      • Stale reads/conflict resolution
      • Snapshot → periodic copy
      • Incremental → changes only
      • Policy dimensions can coexist
      • Commonly-used stem not unique
      • Full replication ≠ simultaneous updates
      • State synchronization rule
      👁 Full explanation
      Eager/synchronous replication coordinates propagation before the specified commit/acknowledgment point, increasing update latency. Lazy/asynchronous replication propagates later and may expose stale reads or need conflict resolution. Snapshot replication transfers a copy at intervals; incremental replication transfers changes. These dimensions can coexist, so commonly used does not identify one unique policy. Full replication does not inherently mean every copy is updated simultaneously; its synchronization rule must be stated.

    Distributed atomic commit and Oracle roles

    [Exam Focus]
    • Two-phase commit protocol
      • Prepare → durable commit promise
      • All yes → coordinator durably records commit
      • Then inform participants
      • Otherwise decide abort
      • Prepared participant retains decision-following state
      • Coordinator/communication failure → in-doubt blocking
      • Wait until decision learned
      • Post-prepare timeout ≠ invented commit/abort
      👁 Full explanation
      Two-phase commit (2PC) first asks participants to prepare and durably promise they can commit. If all vote yes, the coordinator records commit durably and tells participants; otherwise it decides abort. A prepared participant must retain enough state to obey the final decision. Coordinator/communication failure can leave it in doubt and block progress until the decision is learned. Timeout after preparation is not permission to invent a commit or abort.
    • Atomic commit versus isolation
      • 2PC → atomic outcome
      • Locking/other concurrency protocols → isolation
      • Oracle COMMIT_POINT_STRENGTH
      • Higher eligible strength → commit point site
      • Oracle-specific 2PC role selection
      • Not lock phase/checkpoint setting
      • Coordinator → decision coordination
      • Not every site's physical row storage
      👁 Full explanation
      2PC coordinates atomic outcome; locking/other concurrency protocols provide isolation. Oracle's COMMIT_POINT_STRENGTH helps choose the commit point site in its distributed transaction mechanism, with higher eligible strength preferred. This is an Oracle-specific 2PC role rule, not a lock phase or checkpoint setting. The transaction coordinator coordinates decisions rather than physically storing every site's rows.
